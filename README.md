# pix68k
Bare Metal X68000 emulator for Raspberry Pi

pix68k emulates the Sharp X68000 on Raspberry Pi 3 / 4 / 5 without an OS
(bare metal, built on Circle). Besides the 68000 models, it runs X68030
(68030 + 68882) and 060turbo (68060) configurations. A host build (SDL2)
for macOS and Linux is used for development and testing.
IPL ROM, CGROM and disk images are not included; use your own.
The documentation is in Japanese. License: GPLv3.

文中の #番号 は、開発用の非公開リポジトリの issue と PR の番号。

## ビルドとテスト (ホスト)

```sh
tools/fetch_sst.sh          # 68000 のテスト (SingleStepTests) を ~/.cache/pix68k/sst に取得・変換
cmake -S . -B build
cmake --build build -j
(cd build && ctest)         # SingleStepTests と、例外・割り込みなどの単体テスト
./build/bench               # ホスト上での CPU コアの速度 (68000)
./build/cpu020_bench        # 68030 / 68060 のコアだけの速さ (周辺機器なし。--cpu 68030 で 68030)
./build/machine_bench --profile   # X68000 全体 (CPU、周辺機器、画面と音の合成) の速さと内訳
./build/pix68k -0 disk.xdf  # ホスト版 (SDL2)。X68000 を実時間で動かす。IPL ROM と CGROM は ~/.cache/pix68k/rom から読む (-r で変える。
                            # IPL ROM がなければテストパターンを出す)。オプションの一覧は host/main.cpp の先頭、入力は下の「ホスト版の入力」
```

ホスト版には SDL2 が要る (`brew install sdl2`)。見つからなければホスト版だけビルドしない。

Linux (Ubuntu 26.04 の GCC 15 で確かめている) では、次のパッケージを入れると同じ手順でビルドできる。

```sh
sudo apt install build-essential cmake ninja-build libsdl2-dev python3
```

CI は `.github/workflows/ci.yml`。開発用の非公開リポジトリでは持ち主の機械の self-hosted runner で動かし、公開リポジトリ (j3tm0t0/pix68k) に
書き出すときに、`ci.yml` を GitHub のホストの runner の設定に差し替える。公開リポジトリの CI の job は 3 つある。
IPL ROM、CGROM、ディスクのイメージは置いていないので、それが要る試験は飛ばされる。

- `host-linux` (Ubuntu、GCC): ホスト版のビルドと ctest、`pico_kbd` のホストの試験
- `host-macos` (macOS、clang): ホスト版のビルドと ctest
- `baremetal` (Ubuntu、`aarch64-linux-gnu-gcc`): ベアメタル版 (QEMU 用の Pi 3、Pi 3 の 68000 だけの版、Pi 3、Pi 4、Pi 5) のビルドと、
  ROM の要らない QEMU での起動の確認 (`tools/qemu_smoke.sh`)。ベアメタル版は `PREFIX64=aarch64-linux-gnu-` でビルドする

音 (OPM の FM 音源と ADPCM) はホスト版では SDL2 で 48kHz で出す。`--no-audio` で出さない。`--wav out.wav` で、出す代わりに WAV に書く
(`--no-wait` と組み合わせられる)。`x68k_boot` も `--wav` で WAV を書ける。
RTC の時刻は、既定ではホストの今の時刻から始まる。ゲームによっては RTC の値で動きが変わる (悪魔城ドラキュラは、起動した
時刻の秒によって約 10 秒からの音が変わる) ので、WAV や画面を前の版と比べるときは、`pix68k` も `x68k_boot` も
`--time 秒数` で時刻を決めておく。秒数は地方時の 1970-01-01 00:00:00 からの秒数として、時間帯を見ずにそのまま RTC に
入れる (`--time 1700000000` は、どの時間帯のホストでも 2023-11-14 22:13:20 になる)。
RTC が表せるのは 1980〜2079 年なので、その外の秒数は端 (1980-01-01 00:00:00 か 2079-12-31 23:59:59) にする。
`machine_bench` は IPL ROM と Human68k の起動ディスク (`~/.cache/pix68k`) で、起動、プロンプトのまま、計算のループ、
512x512 の画面とスプライトと OPM 8 チャネルを使う場面を動かし、実時間の何倍で動くか、最も重いフレームの時間、
場面の終わりの状態のチェックサム (タイミングを変えない変更の前後で同じになるはず) を出す。Pi では先頭の注釈の手順でビルドする。
Pi 3B+ の Linux (16MHz、画面と音の合成込み、1.2GHz と 1.4GHz が混じる) では、プロンプトのままと計算のループで実時間の約 2.5 倍、
gfx の場面 (512x512 で 4 ページ + スプライト 128 枚 + BG、OPM 8 チャネル) で約 1.08 倍。
`--render-thread` を付けると、画面の合成を別のスレッドで行う (ベアメタル版でコア 2 に置くのと同じしくみ。`src/x68k/video_replay.h`)。
`--sound-thread` を付けると、音の合成を別のスレッドで行う (コア 3 に置くのと同じしくみ。`src/x68k/sound_replay.h`)。
`--pin 1 2 -1` で 2 つのスレッドを別の CPU に固定して測ると、Pi 3B+ の Linux で gfx の場面が約 1.03 倍から約 1.76 倍に、
プロンプトのままで約 2.3 倍から約 3.1 倍になった (チェックサムは同じ。PR #27 の音の直流を切るフィルタなどを入れたあとの値)。
gfx の場面では合成するスレッドがほぼ休まず動いていて、Pi 3 で合成だけを受け持つコアの上限が実時間の約 1.8 倍になる。
`--sound-thread --pin 1 2 3` で音の合成も別の CPU に置くと、gfx の場面が約 1.83 倍、プロンプトのままで約 3.4 倍になった。
OPM の合成の速さは `./build/opm_bench` で測る (Pi 3B+ の Linux で、8 チャネルすべてを鳴らして 1 秒分に約 85ms、鳴っていなければ約 7ms)。

ホスト版の入力:

- キーボード: ホストのキーを物理的な位置で X68000 の JIS 配列のキーにする (`src/x68k/keyboard.cpp`)
- マウス: ウィンドウの中を左クリックすると、ホストのマウスを X68000 のマウスにする (カーソルが消え、ウィンドウから出なくなる)。
  中ボタンのクリックか、Ctrl と Alt (Mac は control と option) を同時に押すと元に戻る。フォーカスが外れたときも戻る
- ジョイスティック: SDL のゲームコントローラ (つないだ順にジョイスティック 1、2)。十字キーと左スティックが上下左右、A / X がトリガ A、B / Y がトリガ B。
  `--joy-keys` を付けると、カーソルキーと Z / X をジョイスティック 1 にする (そのキーは X68000 のキーボードには送らない。既定では送る)
- `--clock 10` で CPU を 10MHz (初代〜SUPER) にする。既定は 16MHz (XVI)。16MHz は 16.0MHz で動かす (実機の XVI は 16.67MHz)。
  68000 の機種では、VRAM、I/O、SRAM、ROM の読み書きのウェイトと、メインメモリの DRAM リフレッシュで遅れる分を入れている
  (値と出どころは `src/x68k/machine.cpp` の `setupBusWaits()` と `refreshWait()`)。TOMY さんの cpupower.r で測ると、
  10MHz で CPU / I/O / グラフィック VRAM / テキスト VRAM が 100.00% / 98.78% / 98.65% / 98.72% (実機の XVI 10MHz がすべて 100%)、
  16MHz で 160.67% / 106.58% / 143.14% / 148.08% (説明書の XVI 16.67MHz の値をクロックの比 16 / 16.67 で直すと 161.5% / 106.5% / 143.0% / 148.6%)
- 既定 (`--sram-memsize fix`) では、起動するときに SRAM のメインメモリの容量をエミュレータの容量 (4MB) に書き換える。`--sram-memsize keep` なら SRAM の値を変えない
- キーボードの LED (CAPS、かな、INS など) は、点灯しているものをウィンドウのタイトルに出す

68000 の CPU コアは、SingleStepTests と食い違う所では、WinUAE (Amiga のエミュレータ) の動作か実機の計測値 (DIVS のオーバーフローのサイクル数など) に合わせている。
合わせた結果テストと合わないもの (ASR のフラグ、ADDQ.l #,An のサイクル数、除算のオーバーフロー・ゼロ除算の未定義フラグ、PC 相対オペランドのアドレスエラーの FC など) は
`tests/sst/expected_failures.txt` に理由付きで載せている。一覧は `tools/classify_sst.py` で作る。

### X68030 (68030 と 68882)

`--cpu 68030` で X68030 として動かす (68030 25MHz、FPU は 68882、IPL ROM 1.3)。IPL ROM は `IPLROM30.DAT` を読む
(`--ipl` で場所を指定できる。XEiJ の `data/IPLROM30.DAT` が使える)。内蔵 SCSI の ROM ($FC0000) は IPL ROM から作る
(X68030 の SCSI のドライバは IPL ROM にあり、$FC0000 には入り口のアドレスと `SCSIIN` の文字列だけを置く)。XEiJ の説明書の
更新履歴 (history.htm) にも、SCSIINROM.DAT を IPLROM30.DAT から作るとある。この作りで IPL ROM 1.3 が SCSI のディスクから
Human68k を起動することは、ctest の `x68k_boot_scsi30_stream` で確かめている。
ホスト版の SRAM の既定は `~/.cache/pix68k/sram30.dat`。`--high-mem 16` で $01000000 から 16MB のハイメモリを置く。

```sh
./build/pix68k --cpu 68030 --ipl ~/x68k/xeij/data/IPLROM30.DAT -0 ~/.cache/pix68k/disk/HUMAN302.XDF
./build/machine_bench --cpu 68030 --ipl ~/x68k/xeij/data/IPLROM30.DAT
```

68030 のコア (`src/m68k/cpu020.*`) は 68000 のコアとは別のクラスで、68000 のコアの処理は変えていない。
命令単位で動かし、サイクル数は概算 (68000 で同じ命令にかかるサイクル数の 3/5)。実機で測った値ではない。
68020 / 68030 の命令 (ビットフィールド、CAS / CAS2、CHK2 / CMP2、PACK / UNPK、64 ビットの乗除算、拡張したアドレッシングなど)、
例外のフレーム、VBR、CACR / CAAR に対応する。ベアメタル版では Pi 3 / Pi 4 / Pi 5 のどのビルドにも入れる (`pix68k.cfg` の `cpu=68030`、
SRAM は `SRAM30.DAT`)。`PIX68K_CPU020=0 tools/build_baremetal.sh 3` のように実行すると、68030 / 68060 のコアを入れない
68000 だけのカーネルになる (`PIX68K_NO_CPU020`)。

68030 / 68060 では、CPU を止めて周辺機器を進める間隔の上限を、X68000 の時間で 25.6us にしている (68030 は 640 サイクル、
68060 は 1280 サイクル。10MHz の 68000 の 256 サイクルと同じ時間。`Machine::run()`)。周辺機器の割り込みは、周辺機器を
進めたときに CPU に届くので、割り込みの要求が出てから CPU に届くまでの遅れは、割り込みの種類で次のようになる:

- ラスタに合わせて起きるもの (H-SYNC、V-DISP、CRTC のラスタ割り込み、V-DISP を数える MFP のタイマ A): その時刻で CPU を
  止めるので、要求が出たときに実行していた命令が終わったところで届く (68000 の機種も同じ)
- MFP のタイマ (ディレイモード) と OPM のタイマ: 要求を出す時刻を先に計算し、その時刻でも CPU を止める (`Machine::nextTimerIrq()`)。
  見るのは、割り込みが許可されていて (MFP の IER) マスクされていない (IMR) タイマだけ (OPM は、$14 の IRQEN が立っていて、
  MFP が GPIP3 の割り込みを受け付ける設定のとき)。MFP の GPIP から TDDR までのレジスタか、OPM の $10-$14 を書いた命令でも
  CPU を止めて、時刻を計算し直す (`Cpu020::endRun()`)。これで、要求が出たときに実行していた命令が終わったところで届く。
  ctest の `timer_irq_test` は、割り込みの処理ルーチンの最初の命令で MFP のタイマのカウンタ (1us ごとに 1 減る) を読んで確かめる:
  200us の周期のタイマ C では、要求が出てから読むまでがいつも 68030 で 2us、68060 で 1us (この時刻で止めないと 1us から 21us の間でばらつく)
- DMAC、FDC、SASI、SCSI、SCC、MIDI ボード、ネットワークボード、キーボード (MFP の USART): 時刻を先に計算していないので、
  次に周辺機器を進めるまで待つ。遅れは最大 25.6us (10MHz の 68000 と同じ)

68000 の機種は 256 サイクルごと (10MHz で 25.6us、16MHz で 16us) のままで、MFP と OPM のタイマの割り込みもその間隔まで遅れる。
Pi 3 (Pi 3B+、1.4GHz) でも 68030 25MHz は実時間で動く。Human68k のコマンド行で 1 フレームの処理は 8.4ms (16.7ms のうち)、
最高速モードでは 25MHz の 211% (52.75MHz 相当) まで上がった。起動とフロッピーディスクを読む間は 68000 より重く、
起動から 10 秒の区間で遅れたフレームが 130 あった。グラフィックの多いゲームはまだ確かめていない。
060turbo (`cpu=68060`) は Pi 3 でも起動するが、実時間には届かない (Human68k のコマンド行で 1 フレームの処理が平均 87ms。
68060 のサイクル数を実機に合わせる前の値。合わせたあとの Pi での値は未確認。1 フレームに実行する命令の数は、ホスト版で
数えるとコマンド行で前の 0.13 倍 (キャッシュ無効) から 0.37 倍 (キャッシュ有効)。下の「68060 のサイクル数」を参照)。
060turbo には Pi 4 か Pi 5 を使う。

確かめ方:

- XEiJ の `misc/instructiontest.x` (実機の 68030 の結果を持つ) を `build/run_x --cpu 68030 instructiontest.x all` で動かし、
  548 個がすべて通る (未定義のフラグも比べる `hard` の指定でも通る)。ctest の `m68030_instructiontest` はその一部を動かす
- `tests/m68k/musashi_diff.cpp` で Musashi の 68030 と 1 命令ずつ比べる。`tools/fetch_musashi.sh` で Musashi を
  `~/.cache/pix68k/musashi` に置くとビルドし、ctest の `musashi_diff` で 20 万命令を比べる (CI でも動かす)。
  違いはすべて、XEiJ と実機の結果に合わせた動きか、Musashi の誤りだった。命令ごとの違いの数と理由は
  `tests/m68k/musashi_expected.txt` に書き、これより増えたら失敗にする
- ctest の `x68k_boot_x68030` は X68030 で Human68k を起動して DIR を打つ

FPU (`src/m68k/fpu.*`、計算は `src/m68k/fpu_math.*`) は、拡張精度 (64 ビットの仮数) を整数で計算する。
単精度、倍精度、拡張精度、パック 10 進、整数のすべての形式を読み書きでき、超越関数は 128 ビットの仮数で計算して最後に 1 回だけ丸める。
精度:

- XEiJ の `misc/fputest.x` の既定の設定 (最後のビットの 1 単位 = 1 ulp までの差を許す) で、すべての命令が通る。
  XEiJ の説明書によると、fputest.x の期待値は計算で求めた値で、実機の 68882 の結果と一致するとは限らない (FMOVECR は次の項目)。
  丸め、例外のフラグ (アンダーフローを丸めの前に判定するか後か、正確な結果でも INEX2 を立てるかなど) も fputest.x の期待値に合わせた
- FMOVECR のマニュアルにないオフセット ($01〜$0A、$10〜$2F) は、FMOVE.X で書き出した値と条件コードを fputest.x の期待値に合わせた。
  XEiJ の説明書によると、fputest.x の FMOVECR の期待値は実機の値 (合わなければエラーにする)。$08 は、fputest.x では
  見分けられない bit62 を 0 にした (シグナリング NaN。FMOVE.X では bit62 を立てて書く)。bit62 の実機の値は確かめていない。
  このため、$08 を読んだあとの FMOVE.X や演算は FPSR の SNAN と AIOP を立て、SNAN の例外を許可していればベクタ 54 になる。
  $08 のほかのオフセットは次のとおり。
  - $09、$0A、$10〜$2F は、FMOVE.X で書き出した値が fputest.x の期待値 ($43F3/$E000…、$4072/$C000…、0) になる、
    正規化した形でレジスタに持つ。FMOVEM で書き出したときの形とレジスタの中の値は、実機で確かめていない
  - $03 は正規化しない形 ($2000/$7FFFFFFF…) のまま FMOVE.X で書き出す (fputest.x の期待値)
- 1 ulp の差も許さない `hard` でも、すべての命令が通る (`build/run_x --cpu 68030 fputest.x hard all` で 3028872 件)
- ctest の `fpu_math_test` は、四則演算と平方根が倍精度でホストの計算とビット単位で一致すること (4 つの丸めのモードすべて)、
  超越関数が libm との差 1 ulp 以内 (tan は 2 ulp。macOS の libm の tan が 2 ulp ずれる) に収まることを確かめる

できていないこと:

- MMU のアドレス変換はしない (レジスタの読み書きと PMOVE などの命令はあるが、変換は常に切ったまま)。X68030 の MPU は MMU のない MC68EC030
  (XEiJ の説明書 feature.htm の機種の節)
- 命令キャッシュとデータキャッシュの動き (CACR の値は保つが、キャッシュの内容は持たない)
- FPU と CPU の並行動作 (FPU が計算している間に CPU が先に進むこと)。FSAVE は NULL と IDLE のフレームだけを書く (命令の途中の状態は持たない)
- 68030 のサイクル数とメモリのウェイトは概算。I/O とスプライトの読み書きは、実機の si.r の system performance に合わせて
  1.6 マイクロ秒ごとの区切りまで待たせる (下の「X68030 と 060turbo の本体のバス」)。グラフィック VRAM とテキスト VRAM の
  ウェイトは入れていない
- バスエラーのフレームはいつも長いフレーム ($B)。RTE は命令を始めからやり直す (命令の途中で動かしたアドレスレジスタは、
  フレームを積む前に命令の始めの値に戻す)。処理ルーチンが SSW の DF を 0 にして RTE したときは、バスエラーになった
  アクセスだけを行わずに命令を終える。ただし、1 つの命令にバスエラーになるアクセスが 2 つ以上あると (MOVE.L (A0),(A1)
  で両方など)、毎回 DF を 0 にして RTE しても命令が終わらない。実機と違う点は `src/m68k/cpu020.cpp` の `pushBusFault()` の注釈を参照。
  処理ルーチンから見えるアドレスレジスタは命令の始めの値 (MOVE.L (A0)+,D0 のバスエラーなら A0 は進む前) で、
  MC68030UM はこの値を決めていないので、実機と同じかは分からない。RTE で戻らずに (An)+ の An からバスエラーの
  番地を知るソフト (メモリの大きさを調べるものなど) では、結果が実機と違うかもしれない
- FPU の例外は MC68881/MC68882 UM 6 章の表のとおり、FPn に書く命令の例外は次の FPU の命令 (FMOVEM、FMOVE の制御レジスタ、
  FSAVE、FRESTORE を除く) を始めるときに起こす。FMOVE FPn,<ea> の例外と BSUN はその場で起こす

X68030 で動かないソフト:

- Human68k 3.00 より前 (1.00、2.0x) で起動するディスク。たとえば Gradius (Human68k 1.00) や test_sion2 (Human68k 2.03) は、
  DOS コールの途中で止まる。Human68k 1.00 / 2.03 の DOS コール ($FFxx の命令。F ライン例外の処理ルーチンで受ける。2.03 では
  $7F58 から) は、例外のフレームを 68000 の 6 バイトとして読み (68030 は 8 バイト)、スーパーバイザモードから呼ぶと引数を
  2 バイトずれたところから読む。`_SUPER` もフレームを 6 バイトとしてコピーする。MPU の種類を見ていないため、実機の X68030 でも同じく止まるはず (実機では確かめていない)。
  68000 (`--cpu 68000`) で動かすか、Human68k 3.0x のディスクで起動する

### 060turbo (68060)

`--cpu 68060` で、X68030 に 060turbo (68060 50MHz) を載せた構成で動かす。$10000000 から 060turbo のローカルメモリを置く
(`--local-mem MB`、既定 128MB、最大 256MB)。$10000000-$1FFFFFFF のうちメモリのないところは、読むと $FF で書き込みは捨てる
(060turbo.sys が書いて読み直して容量を調べるため)。`--ram MB` で本体のメモリを変えられる (既定 4MB、最大 12MB)。
ホスト版の SRAM の既定は `~/.cache/pix68k/sram060.dat`。ベアメタル版は `pix68k.cfg` に `cpu=68060`
(`local_mem=128` でローカルメモリの容量、SRAM は `SRAM060.DAT`)。

```sh
./build/pix68k --cpu 68060 --ram 12 -0 human060.xdf   # human060.xdf は 060turbo.sys を CONFIG.SYS で組み込んだ起動ディスク
./build/pix68k --cpu 68060 --clock 75 -0 human060.xdf # 68060 を 75MHz にする
./build/machine_bench --cpu 68060
```

68060 のクロックは 50MHz (既定、実機の 060turbo) と 75MHz から選べる。75MHz は、実機の 060turbo をオーバークロックして
使う人がいる構成。ホスト版は `--clock 75`、ベアメタル版は `pix68k.cfg` に `clock=75` (`cpu=68060` のとき。設定メニューの
Clock でも 50 / 75 を切り替えられる)。`clock=` は CPU ごとに読む: 68000 では 10 / 16、68060 では 50 / 75 で、CPU に合わない値
(`cpu=68060` で `clock=16` など。`clock=` を書かなければ 16 のまま) はその CPU の既定 (68060 は 50MHz) にする。
クロックで変わるものは次のとおり (`Machine::Config::setClockMHz`):

- X68000 の時間とサイクル数の換算は `Config::cpuHz` で行う。75MHz では X68000 の 1 秒が 7500 万サイクルで、周辺機器
  (MFP、OPM、画面のタイミングなど) の時間は 50MHz と同じ。命令のサイクル数 (MC68060UM の表) は変えないので、同じ時間に
  実行する命令の数は 1.5 倍になる
- 本体のバスに出す読み書き 1 回のサイクル数 (`busWait060`) は 6 から 9 にする。本体のバスは 68060 のクロックを上げても
  25MHz のままで、1 回 (25MHz の 3 クロック、120ns) の時間は変わらないため
- I/O の読み書きが終わる時刻をそろえる周期 (`busArea` の `period`、1.6 マイクロ秒) は、80 サイクルから 120 サイクルにする
  (下の「X68030 と 060turbo の本体のバス」。これも本体の時間で、クロックでは変わらない。si.r の system performance は 75MHz でも 177.82%)
- キャッシュを切ったときのメモリの読み書きの時間 (下の「68060 のサイクル数」) も、時間が同じになるようサイクル数を
  1.5 倍にする (本体のメモリ 10.5 → 15.75 サイクル、ローカルメモリ 6 → 9 サイクル)。ローカルメモリは、実機でクロックを
  上げたときの値が見つかっておらず、DRAM の時間で決まるものとした推定
- IOCS のワークの $0CB8 は、50MHz の 8333 をクロックに比例させて 12500 にする (cpuHz / 6000。si.r の表示は 75.0MHz)。
  IOCS `_MS_ONTM` の待ちのループの回数は $0CB8 から決まるので、1 単位は 75MHz でも 1ms になる (`iocs_wait060 --clock 75` で
  1000 単位 999.4ms)。75MHz の実機の 060turbo で $0CB8 がいくつになるかは確かめていない
- `speed060`、`max_speed_limit`、最高速モードの速さは、選んだクロックの実機の 68060 を 100 とした % (75MHz の 100 は、
  命令の速さでは 50MHz の 150 にあたる)。最高速モードのログと終了時の表示は「max speed: N% of a real 68060 (75 MHz)」になる。
  OSD とログの速さの % (実時間の何 % か) は X68000 の時間で数えるので、クロックによらず 100% が実時間
- ステートのヘッダには CPU のクロックが入っているので、50MHz と 75MHz のステートは互いに読まない (「CPU clock differs」)。
  ステートの版は変えていない

60MHz や 66MHz などは入れていない。足すときは `Config::valid060MHz()` と `settings.h` の `kClockValues` に値を足し、
設定メニューの切り替え (`menu.h` の `I_CLOCK`) を直す。時間で決まる値は上のとおり `cpuHz` から決まる。

IPL ROM は 68060 で動くもの (`IPLROM060.DAT`) を先に探し、なければ X68030 の `IPLROM30.DAT` を使う。
X68030 の IPL ROM (1.3) は 68060 にない命令 (MOVEP) を使い、060turbo.sys は IPL ROM のバージョンが 1.4 以上でないと
組み込まれない。そのため `IPLROM30.DAT` を使うときは、メモリの上で次の 6 つを変える (ファイルは変えない。`x68k/machine.cpp` の `patchIplFor060`):

- IOCS `_ROMVER` が返す値を $13921127 から $14921127 にする
- ベクタ 61 (未実装整数命令) が IPL ROM を指している間は、68060 にない整数命令をその場で実行する。060turbo.sys が
  060SP (Motorola の M68060 Software Package) を組み込んだ後は、060SP が実行する。その場で実行するときの CHK2 / CMP2 の
  未定義の N と V は、V を 0、N を Rn の符号にする (持ち主の決定)。資料の裏付けはない (060SP は N と V を変えない。68060 の実機の値もない)
- 起動時に IOCS のワークの MMU の有無 ($CBE) を「あり」にする (IPL ROM 1.3 は 68030 の命令で MMU を調べるので、
  そのままでは IOCS `_SYS_STAT` が MMU なしと答える)
- 起動時に IOCS のワークの $0CB8 (ROM の上の dbra のループの 1ms あたりの回数) を 8333 にする。実機の 060turbo は si.r が
  50.0MHz と表示し、si.r は $0CB8 x 6 を MHz の 1000 倍として表示するので、8333 は実機の表示から逆算した推定の値
  (実機の $0CB8 を読んだわけではない。IPL ROM 1.3 が pix68k で測る値は 16683。下の「68060 のサイクル数」)
- IPL ROM が CACR に書く 68030 の値 (ビット 0 = 命令キャッシュ、ビット 8 = データキャッシュ) を、68060 の CACR の EIC (ビット 15) と
  EDC (ビット 31) に読み替える (起動時、IOCS `_SYS_STAT` のキャッシュの設定と取得、IOCS `_MS_ONTM` / `_MS_OFFTM` の待ちのループ)。
  そのままでは 68060 のキャッシュが無効になる。待ちのループの前 (68030 では命令キャッシュだけ有効) は、EIC と EDC の両方を
  立てる (68060 では本体のメモリの読み込みがデータキャッシュなしだと遅く、待ちが長くなりすぎるため)。060turbo の ROM が
  どうしているかは資料がなく、どれも推定の手当て。実機 (060turbo.sys がキャッシュを設定した 68060) とは次のところが違う:
  起動時と `_SYS_STAT` の設定は EIC と EDC だけを決め、ストアバッファ (ESB) と分岐キャッシュ (EBC) は有効にしない
  (060turbo.sys を組み込むと、060turbo.sys が設定し直す)。待ちのループの間は ESB と EBC が落ちる (終わると戻る)。
  待ちのループの回数を決める定数 (`divu.w #834,d2`。$FFAC6E、$FFACDA) は 583 に書き換える。68060 ではループの 1 周の
  サイクル数が違い (EIC と EDC が有効で約 35 サイクル)、834 のままだと 1 単位が 1ms でなく約 0.70ms になるため。
  実機の待ちの長さは分かっていない (下の「68060 のサイクル数」)。
  IPL ROM がキャッシュを消すために $0808 を立てて書く所は、68060 ではキャッシュを消さない
- SCSI IOCS のデータの転送を、バッファが本体の 16MB の外 (ローカルメモリ) にかかるときはソフト転送にする。DMAC は
  本体のバスの 24 ビットのアドレスしか出せないので、DMA のままではローカルメモリの代わりに本体のメモリを読み書きする。
  060turbo.sys の拡張モード (`-xm`) は Human68k のメモリをローカルメモリに広げるので、これがないと SCSI のディスクから
  COMMAND.X を読み込んだところで止まる

フロッピーディスクの読み書き (DMAC のチャネル 0) には IPL ROM にソフト転送がないので、ROM は書き換えず、68060 のときは
IPL ROM によらず (`IPLROM30.DAT` でも `IPLROM060.DAT` でも)、チャネル 0 の MAR がローカルメモリの中を指していれば、DMAC の
転送をローカルメモリへ届ける (`x68k/machine.cpp` の `dmaMemAddr`)。IPL ROM 1.6 もフロッピーディスクは DMA で読むので、
`-xm` で COMMAND.X の読み込み先がローカルメモリになると、これがないと止まる。内蔵 SCSI と SASI (チャネル 1) も、68060 の
ときは同じ扱いにする。`IPLROM060.DAT` と組で使う `ROM30_060.DAT` の SCSI IOCS は、バッファがローカルメモリでも DMA で
転送するので、SCSI のディスクから `-xm` で起動すると、これがないと本体の例外ベクタを書いて止まる (#167)。`IPLROM30.DAT` の
ときは上の SCSI IOCS の書き換えでソフト転送になるので、チャネル 1 にローカルメモリのアドレスは来ない。
ローカルメモリの範囲 ($10000000-$1FFFFFFF) のうち SIMM を積んでいないところは、
CPU から見たときと同じく、読むと $FF で、書いても変わらない (本体のメモリには折り返さない)。チャネル 2 と 3 と、ほかの構成では、
MAR の下位 24 ビットだけを使う。

SCSI の書き換えとフロッピーディスクの扱いは、060turbo の ROM や実機の動きを写したものではなく (実機の DMAC はローカルメモリに
届かない)、エミュレータの側の互換の処理。SCSI の書き換えは `IPLROM30.DAT` を 68060 で使うときだけ、フロッピーディスクと
チャネル 1 の扱いは 68060 のときいつも行う。060turbo の ROM や、IPL ROM 1.6 を使う実機・XEiJ が、ローカルメモリへの転送をどう扱うかは
確かめていない。060turbo.sys には `-dv` (デバイスドライバの転送を、DMA の届く転送バッファ経由にする。大きさは `-bs`、
既定 64KB) があり、`-xm -dv` なら、この互換の処理がなくても IPL ROM 1.3 でも 1.6 でも起動する (060turbo.sys 0.56 を
逆アセンブルして確かめた)。実機は `-xm` だけではフロッピーディスクから起動せず、`-dv` が要る見込み (逆アセンブルからの
推定で、実機では確かめていない)。フロッピーディスクの互換の処理は `-dv` の代わりで、`-dv` なしでも起動できるようにする
ためのもの。SCSI も同じで、060turbo.sys の SCSI IOCS を包む処理は `-ss` (と `-np`) のフラグが立っていなければ何もせず、
`-xm` は `-ss` のフラグも `-dv` のフラグも立てない (0.56 と 0.61 を逆アセンブルして確かめた)。
`IPLROM060.DAT` と `ROM30_060.DAT` では、`-xm -ss` でも `-xm -dv` でも、チャネル 1 の互換の処理なしで SCSI のディスクから
起動した。`-xm` だけでは実機でも止まる見込み (推定で、実機では確かめていない)。X68000 の側のメモリは使わない。MAR やバッファのアドレスをそのまま物理アドレスとして見るので、060turbo.sys の `-ls`
などで 16MB より下の論理アドレスをローカルメモリに割り当てた場合は扱わない。060turbo.sys 0.61 (2025-10-31) は、
IOCS `_SCSIDRV` のベクタが IPL ROM の中 ($00FFxxxx) を指しているときは、`-ss` を付けても SCSI IOCS を差し替えない
(060turbo.sys を逆アセンブルして確かめた。`-xm -ss` でも同じところで止まる)。

SRAM が空のとき (SRAM のファイルを新しく作るとき) は、060turbo ではキャッシュの設定 ($ED0090) を命令・データとも有効 (3) に
する。X68030 の IPL ROM が空の SRAM に書く初期値では 0 (どちらも無効) で、060turbo.sys はこの値に従って CACR を設定する。
中身のある SRAM は変えない (SWITCH.X などで変えた設定はそのまま使う)。

`IPLROM060.DAT` には XEiJ の IPLROM 1.6 (060turbo のときに XEiJ が組み立てる IPL ROM) が使える。XEiJ のライセンスに従い、
ROM はリポジトリにも配布物にも入れない。各自が XEiJ から次のどちらかで取り出す:

- XEiJ を 060turbo の構成 (`-model=060turbo -iplrom16=on`) で起動し、メニューの「ROM ファイルの作成」で `XEIJIPLROM.DAT`
  ($FE0000-) と `XEIJROM30.DAT` ($FC0000-) を作る (XEiJ の説明書 iplrom16.htm)
- `python3 -I tools/make_romdump_dir.py ~/.cache/pix68k/disk/HUMAN302.XDF romdump` で、ROM を書き出すプログラム
  (`ROMDUMP.X`) を自動で動かす Human68k の起動ディレクトリを作り、
  `java -jar XEiJ.jar -model=060turbo -iplrom16=on -boot=hf0 -hf0=romdump` で起動する。`romdump` に `IPLROM.DAT` ($FE0000-) と
  `ROM30.DAT` ($FC0000-) ができる (XEiJ のウィンドウを前に出していないと進まないことがある)

できたファイルを `~/.cache/pix68k/rom/IPLROM060.DAT` と `ROM30_060.DAT` (ベアメタル版は SD カードの `/pix68k/IPLROM060.DAT`) に置く。
`ROM30_060.DAT` はホスト版と `x68k_boot` が $FC0000 からの ROM として読む (なければ X68030 と同じく IPL ROM から作る)。

68060 の違い (MC68060UM による):

- 68060 にない整数命令 (MOVEP、CHK2 / CMP2、CAS2、ずれたアドレスの CAS、64 ビットの MULU / MULS / DIVU / DIVS) はベクタ 61
- FPU にない命令 (超越関数、FMOD / FREM、FSCALE、FGETEXP / FGETMAN、FMOVECR、FScc、FDBcc、FTRAPcc など) はベクタ 11
  (フォーマット $2)、FPU が扱わない実効アドレス (#imm の拡張精度とパック 10 進、FMOVEM の動的なリスト) はベクタ 60、
  パック 10 進はベクタ 55。FSxxx / FDxxx、FSAVE / FRESTORE の 3 ロングのフレーム、PCR の DFP、条件の OR と NE の式も 68060 に合わせた
- 非正規化数・非正規化の値のオペランドはベクタ 55。アンダーフローと (丸める前にあふれる) オーバーフローは、許可されていなくても
  ベクタ 51 / 53 の例外にし、060FPSP に結果を作らせる (MC68060UM 6.5.2、6.6.4、6.6.5)。FPn に書く命令では、これらと、許可した
  SNAN / OPERR / DZ / INEX は EXCP の状態にするだけで、次の FPU の命令 (FSAVE 以外) を始めるときに例外にする (実機と同じく、
  例外の処理ルーチンが最初に FSAVE をしないと、FPU の命令のたびに同じ例外が起き続ける)。FMOVE OUT では
  すぐに命令の後の例外 (フォーマット $3) にする。拡張精度とパック 10 進の (An)+ / -(An) では An を動かさず、060FPSP が直す形の
  アドレスを積む
- 例外のフレームのフォーマット ($0 / $2 / $3 / $4。アクセスエラーは FSLW を持つ $4)。アクセスエラーなどで命令をやり直すときは、
  A0-A7 と CCR を命令の始めの値に戻してから例外にする ((An)+ / -(An) のほか、PEA、JSR、BSR、LINK、MOVEM -(An)、MOVE16 で
  動かした分も。68060 は命令を最初からやり直す)。ページの表を引く途中のバスエラーでは、もとのアクセスのアドレス、読み書き、FC、
  大きさを積む。ページをまたぐアクセスは、分けたうちのどこでエラーになっても元のアドレスと大きさを積み、FSLW の MA を立てる。
  MOVES で FC 0 / 3 / 4 / 7 を読み書きするときは、その FC を Bus に渡し、FSLW の TT を 2 にする
- 制御レジスタ (PCR、BUSCR、URP / SRP、TC、ITT / DTT、CACR)、MMU のアドレス変換 (ページテーブル、透過変換、ATC)、
  PFLUSH / PLPA、MOVE16、CINV / CPUSH (キャッシュの内容は持たないので何もしない)、LPSTOP、MOVES の FC の扱い
- サイクル数は、命令ごとに M68060 User's Manual (M68060UM/AD) の 10 章 Instruction Execution Timing の表の値を使う
  (下の「68060 のサイクル数」)。ローカルメモリ、本体のメモリ、ROM の読み書きには、CACR で命令キャッシュ / データキャッシュが
  有効な間はウェイトを入れない (キャッシュに当たったものとする)。無効な間は 1 回ごとにバスの時間を足す (下の節)。
  I/O、グラフィック VRAM、テキスト VRAM への書き込みは、キャッシュの設定によらず本体のバスを
  通るので、1 回 6 サイクル (50MHz。75MHz では 9 サイクル) を足す (`Machine::Config::busWait060`)。68030 の非同期バスの 1 回の読み書きは 25MHz で
  最低 3 クロック (50MHz の 6 サイクル) かかるため。I/O とスプライトの読み書きは、そのあと本体の 1.6 マイクロ秒ごとの
  区切りまで待つ (`Machine::Config::busArea`。下の「X68030 と 060turbo の本体のバス」)。VRAM は、本体のバスで延びる分が分からないので入れていない

確かめ方:

- `build/run_x --cpu 68060 instructiontest.x all`: 522 個がすべて通る (run_x には 060SP がないので、68060 にない命令はその場で実行する)
- `build/run_x --cpu 68060 fputest.x`: 68060 の FPU にある命令はすべて通る
- 060turbo.sys 0.56 を組み込んだ Human68k を起動し、DIR を打てる。その中で fputest.x を 060FPSP で動かした結果は issue #10 の PR の本文に書いた
- ctest: `m68060_instructiontest`、`m68060_fputest`、`x68k_boot_060turbo_plain`、`x68k_boot_060turbo_sys`、
  `x68k_boot_060turbo_xm` (拡張モード `-xm` でフロッピーディスクから起動する)、`x68k_boot_060turbo_xm_scsi` (同じく
  SCSI のハードディスクから)、`x68k_scsi_local_mem` と `x68k_scsi_local_mem_stack` (SCSI IOCS とフロッピーディスクの IOCS でローカルメモリへ読み書きする。
  後者はスーパーバイザスタックもローカルメモリに置く)、`x68k_boot_060turbo_75mhz_plain` と `x68k_boot_060turbo_75mhz_sys`
  (75MHz で、060turbo.sys なしとありで起動する)
  (060turbo.sys を `~/.cache/pix68k/060turbo/060TURBO.SYS` に置く。なければ飛ばす)

#### 68060 のサイクル数

68060 の命令にかかるサイクル数は、M68060 User's Manual (M68060UM/AD、Motorola 1994) の 10 章の表から作った
(`src/m68k/cpu060_cycles.inc`。オペコードごとの表は起動時に作る)。使った節と表:

| 節 | 表 | 内容 |
|---|---|---|
| 10.1.2 - 10.1.6 | 10-1 - 10-4 | 2 命令の同時実行 (スーパースカラ) の分類と条件 |
| 10.4 | 10-5 | 実効アドレス ((bd,An,Xi) は +1、メモリ間接は +3。ほかは 0) |
| 10.5 | 10-6 - 10-8 | MOVE、MOVE16 |
| 10.6 - 10.8 | 10-9 - 10-12 | ADD などの演算、乗除算 (MULx 2、DIVx.W 22、DIVx.L 38)、イミディエイト、単項、CLR |
| 10.9、10.10 | 10-13 - 10-16 | シフト、ビット操作、ビットフィールド |
| 10.11 | 10-17 - 10-19 | Bcc / BRA / BSR / DBcc、JMP / JSR、RTD / RTE / RTR / RTS |
| 10.12 - 10.14 | 10-20 - 10-24 | LEA / PEA / MOVEM、ADDX など、SR の命令、MOVES、MOVEC、NOP、STOP など |
| 10.15 | 10-25 | FPU (FADD 3、FMUL 3、FDIV 37、FSQRT 68、FMOVE 1 など) |
| 10.16 | 10-26 | 例外 (19、割り込みは 23) |

- 分岐は、分岐キャッシュ (CACR の EBC) の予測が当たったか外れたかで変える (表 10-17: Bcc は当たって分岐すれば 0、分岐しなければ 1、
  外れれば 7。予測がなければ後ろ向きの分岐は 3、前向きで分岐しなければ 1)。当たって分岐するときの 0 サイクルは、分岐でない命令と
  同じサイクルに折りたたまれる場合の値 (10.1.2) なので、分岐でない命令をはさまずに分岐が続くときは 1 つ 1 サイクルにする。分岐キャッシュは 256 個の表で、命令のアドレスごとに
  2 ビットの飽和カウンタを持つ (マニュアルの 5.11 は「5 つの状態」とだけ書いていて、移り方は書いていないので、ここは概算)。
  CACR に CABC を書くと全部、CUBC を書くとユーザモードで覚えた分岐を消す (5.2)。CINV / CPUSH で命令キャッシュを無効にした
  ときに一緒に消えること (5.11) は入れていない
- スーパースカラ (PCR の ESS が 1 のとき) は、表 10-2 の分類と、10.1.3 から 10.1.6 の条件のうちオペコードの 1 語めで決まるもの
  (sOEP で使えない PC 相対、メモリの読み書きは 2 命令で 1 つ、前の命令の結果のレジスタを後の命令が使わない) を見て、
  前の命令と同時に進む命令を 0 サイクルにする。インデックスレジスタと、フルフォーマットの拡張語かどうかは見ない。
  リセットのあとは ESS が 0 で、060turbo.sys が 1 にする
- MOVEM と FPU の命令は、サイクル数を命令の中で足す (MOVEM はレジスタ 1 つに 1 サイクル)。命令の中で 1 サイクルも
  足さなかった命令 (レジスタの数が 0 の MOVEM など。マニュアルの式では 0 サイクルになる) は 1 サイクルにする。これは近似で、
  分岐でない命令が必ず時間を進めるようにするため (0 サイクルに折りたたまれる分岐と組み合わせたループで、時間が進まなく
  なるのを防ぐ)
- 同時実行の表と、命令の間の状態の確かめ (`cpu060_test`):
  - `testTableAgainstExecution`: 同時実行に関わるすべてのオペコード (同時実行の相手にできる命令と、sOEP に入れる命令。
    34871 個) を 1 命令ずつ、値を変えて 2 回実行し、(1) データの読み書きをしたかどうかと表の「メモリの読み書きあり」、
    (2) 値が変わったレジスタが「書くレジスタ」に入っていること、(3) 「使うレジスタ」にないレジスタの値を変えても結果が
    変わらないこと、を比べる。見ないもの: サイクル数そのもの、同時実行に関わらない命令 (pOEP-only) と例外になる
    オペコード、インデックスレジスタ (表が見ないと決めている)、`MOVE.L <ea>,Dn` の Dn (10.1.6 の例外 1 で、書く
    レジスタに入れていない)、実行しても値が変わらなかったレジスタ、同じレジスタを書く 2 命令の組
  - `testRandomSequences`: 30 種類の命令からランダムに作った並び (400 個) を続けて実行し、命令ごとのサイクル数を、
    「数え方の状態を消してから 1 命令ずつ実行したときのサイクル数」と上の規則 (同時実行と、分岐の折りたたみ) から
    計算した値と比べる。命令と命令の間で、規則にない形でサイクル数が変わらないことを見る。見ないもの: Bcc / DBcc /
    JMP / JSR (分岐は BRA だけ)、例外と割り込み (別の試験)、命令キャッシュが無効のときの取り出し (別の試験)
- CACR で命令キャッシュ (EIC) / データキャッシュ (EDC) を切っているときは、命令の取り出し (命令の並びが新しいロングワードに
  入るたび、分岐のあとは同じロングワードでも) とデータの読み書きの 1 回ごとに、バスの時間を足す (`Cpu020::updateCacheCosts`)。
  本体のメモリと ROM は 10.5 サイクル、060turbo のローカルメモリは 6 サイクル (どちらも 50MHz の値。75MHz では時間が同じに
  なるよう 15.75 サイクルと 9 サイクル)。本体のメモリの値は、下の実機の 410% に
  合わせて決めた (1 周に取り出し 2 回とデータの読み出し 1 回で、1 + 3 x 10.5 = 32.5 サイクル)。ローカルメモリは実機の値が
  見つからず、マニュアルの 10.3.4 の「2 + w」で 60ns の DRAM の読み出しを w = 4 クロックとした仮の値。
  キャッシュが有効なら、いつも当たるものとして足さない (キャッシュの中身は持たない)。バスの時間なので、下の `speed060` と
  最高速モードの倍率は掛けない。I/O とグラフィック VRAM (Bus に出す読み書き) には、この時間は足さない (上の `busWait060` と、
  I/O とスプライトの `busArea`)。
  命令の取り出しとデータの読み書きを同じ 10.5 サイクルとしたこと、si.r が本体のメモリに読み込まれていたとしたことは仮定
  (実機の値が 1 つしかなく、2 つを分けられない)
- 数えていないもの: ATC のミス、整列していないアクセス、レジスタを書いた直後にアドレスの計算に使うときの待ち (10.2 の 3)、
  「<= k」と書かれた命令 (DIVx.W、CINV、CPUSH) の値による違い、FPU のオペランドの形 (整数、拡張精度) による +3 / +2

- processor performance のループは `addq.l #1,d0` / `tst.b (a0)` / `bne` (si.r のソース。[kg68k/si-ee](https://github.com/kg68k/si-ee))。
  表の値は 1 + 1 + 0 (予測が当たった分岐) で、前の 2 つは同時に進むので 1 周 1 サイクル。実機の 13348% は、XVI 10MHz の
  1 周 26.8 クロック (2.68 マイクロ秒) の 1/133.5 で、50MHz の 1.0 サイクルにあたる。実機の 410% は 1 周 約 32.4 サイクル。
  前の数え方 (68000 のサイクル数の 1/5) は 1 周 3.6 サイクルで、キャッシュが有効の実機の約 1/3.6、無効の実機の約 9 倍の速さだった
- si.r の MHz の表示は、68020 以上では測った値ではなく、IOCS のワーク ($0CB8。ROM が起動時に dbra の空ループを 1ms に
  何回回せるかを入れる) の 6 倍 (68030 の dbra は 6 クロックという前提)。060turbo.sys 0.56 のバイナリの中で $0CB8 を指すのは
  読み出しの 1 か所 (6 倍して返す処理) だけで、書き込みはない。実機の 50.0MHz ($0CB8 = 8333) は、060turbo の ROM 1.50 が
  入れた値と考えられる (測った値か決めた値かは未確認)。pix68k は、IPL ROM が測った値を 8333 に置き換える (上の
  `patchIplFor060` の説明)。置き換えなければ、IPL ROM が起動時に dbra のループで測った値が入る。測るときは命令キャッシュと
  データキャッシュが有効で (IPL ROM が起動時に有効にする)、分岐キャッシュは無効なので、dbra の 1 周は表 10-17 の
  「予測なし、後ろ向き」の 3 サイクルになり、$0CB8 は 16683、表示は 100.1MHz になる (8333 に置き換える処理だけを外して
  測った値)。50MHz と表示させるには 1 周を 6 サイクルにしなければならず、表の値と合わないので、サイクル数の側では
  合わせていない
- X68030 の IPL ROM (1.3) の IOCS `_MS_ONTM` / `_MS_OFFTM` の待ちのループ ($FFAC86 から) は、$0CB8 から回る回数を決める
  (1 単位は $0CB8 x 100 / 834 周。68030 では 1 周 50 クロックで、1 単位 1ms)。回っている間は CACR に 1 (68030 の
  「命令キャッシュだけ有効」) を書く。68060 にそのまま書くと、1 はどのキャッシュのビットでもないので、命令キャッシュ、
  データキャッシュ、分岐キャッシュがすべて無効になる (1 周 294 サイクル、1 単位 約 5.9ms)。pix68k は、この値を 68060 の
  EIC と EDC に読み替え (1 周 約 35 サイクル、834 のままなら 1 単位 約 0.70ms)、回数を決める 834 を 583 に書き換えて、
  1 単位を 1ms にする (上の `patchIplFor060` の説明。`iocs_wait060` で測ると 1000 単位で 999.5ms。ctest は 950ms から
  1050ms に入ることを確かめる)。1ms は IOCS の呼び出しの決まりの長さで、実機の 060turbo で測った値ではない。実機は ROM が
  違い (IPL ROM 1.50)、060turbo.sys 0.56 は `_MS_ONTM` / `_MS_OFFTM` を差し替えない (組み込んだあとも IOCS のベクタは
  ROM のまま) ので、実機の待ちの長さは ROM 1.50 の作りで決まる。その作りと、実機で測った値は見つかっていない
- IPL ROM 1.6 (68060 で動く IPL ROM) では、`_MS_ONTM` / `_MS_OFFTM` の 1 単位は 1ms にならず、50MHz で約 2.17ms、
  75MHz で約 3.12ms になる (`iocs_wait060 --any-rom` で 1000 単位 2170.7ms と 3117.0ms。#123)。pix68k は ROM に手を入れて
  いない (`patchIplFor060` は 1.3 のときだけ書き換える)。逆アセンブルで確かめた理由は次のとおり:
  - 回数の決め方は 1.3 と同じ ($FFAC6E と $FFACDA の divu.w #834。1 単位は $0CB8 x 100 / 834 周)
  - $0CB8 は、ROM が起動時に MFP のタイマ C / D で dbra のループの時間を測り、68060 では「1ms に回る回数 / 6」を入れる
    ($FEA930 からの MPU ごとの定数の表)。pix68k では 50MHz で 8329、75MHz で 12495 で、クロックに比例している
  - 回っている間のキャッシュは、ROM の $FEC706 が 68030 と同じ「命令キャッシュだけ有効」を 68060 の CACR に直して書く
    (EIC は立て、EDC は落とす。`iocs_wait060 --any-rom` が出すループの間の CACR は $20808000)。データキャッシュが
    無効なので、1 周に本体の RAM ($0A7A からの IOCS のワーク) を 9 回読み、どれも本体のバスに出る
  - 本体のメモリの読み出し 1 回は 210ns (50MHz の 10.5 サイクル。この節の上の、実機の si.r のキャッシュ無効の値から決めたもの) なので、
    1 周は 9 x 210ns = 1.89 マイクロ秒に、CPU の約 14 サイクルを足した長さになる (50MHz で約 2.18 マイクロ秒、
    75MHz で約 2.08 マイクロ秒)。周の数はクロックに比例して増えるのに、1 周の長さはほとんど縮まないので、75MHz の方が長い。
    試しに読み出し 1 回を 0 にすると 1000 単位 280ms、6 サイクル (120ns) にすると 1359ms で、この見積もりと合う
  - 本体のバスの最短のバスサイクル (120ns) でも 1 単位は約 1.36ms (上の 1359ms。バスの時間だけで約 1.08ms、それに CPU の
    サイクルが加わる) で、本体のメモリをデータキャッシュなしで読む限り、
    060turbo でこのループが 1ms になることはない。2.17ms という値は ROM の作りと、si.r から決めた読み出しの時間から出したもので、
    IPL ROM 1.6 を積んだ実機の 060turbo で測った値ではない
  1.3 のように回数を書き換えて 1ms にすることはしない。1.6 はもともと 68060 で動かすための ROM で、待ちの作りはその ROM の
  ままにした。1ms に合わせるなら、834 をクロックごとに変える (50MHz で約 1810、75MHz で約 2600) ことになる
- system performance と machine performance (RTC を読むループ。割り込みを止めて測るのが system、止めずに測るのが machine) は、
  I/O の読み書きを 1.6 マイクロ秒ごとの区切りにそろえて実機に合わせた (下の「X68030 と 060turbo の本体のバス」)。前は `busWait060`
  (120ns) だけで、キャッシュが有効のとき 2032.27%、無効のとき 508.07% だった
- cpupower.r (TOMY さん。XVI 10MHz 比) は、キャッシュが有効のとき CPU 7150.00%、I/O ($E8A001) 736.36%、GV-RAM 663.64%、
  TV-RAM 3850.00%。無効のとき CPU 325.00%、I/O 289.29%、GV-RAM 260.71%、TV-RAM 220.00%。前はどちらの設定でも
  CPU 2860.00%、I/O 675.00%、GV-RAM 608.33%、TV-RAM 3850.00%。実機の 060turbo の cpupower.r の値は見つけられなかった
  (これらは I/O を 1.6 マイクロ秒ごとの区切りにそろえる前の値で、そのあとは測り直していない。I/O は RTC を続けて読むので、
  1 回 1.6 マイクロ秒になり、XVI 10MHz の約 1.01 マイクロ秒に対して 63% 前後になるはず)
- 命令ごとの表を持たずに、68000 のサイクル数を一定の割合に縮める概算は採らなかった。その方式では実機の si.r の値と
  合わないので、実機の値を優先した

大きく変わる。

測ったときの条件:

- 「今」の値は、周辺機器を進める間隔の上限を 25.6us にし、MFP と OPM のタイマの時刻で CPU を止めるようにしたあと
  (上の「X68030」の節) に測り直した。「前」は測り直していない
- コマンド行の 2 つの値は、060turbo.sys 0.56 を組み込んだディスクを `x68k_boot --cpu 68060 --ipl IPLROM30.DAT` で起動し、
  2000 フレームめから 3000 フレームめの命令の数。「無効」は `--sram-cache 0`、「有効」は `--sram-cache 3` (SRAM の $ED0090)。スーパースカラと分岐キャッシュは
  060turbo.sys が有効にする
- machine_bench の値は、`machine_bench -s 5 --cpu 68060 --ipl IPLROM30.DAT` (ディスクは HUMAN302.XDF、SRAM は空から始まり
  $ED0090 は 3) で、場面を boot、idle、cpu、user、gfx、fd の順に続けて動かしたときの値。060turbo.sys を組み込まないので、
  スーパースカラと分岐キャッシュは無効 (PCR は $04300600)。cpu、gfx、fd の場面は、始めた時点の CACR のまま動き、
  `-s 5` では $80008000 (命令キャッシュとデータキャッシュが有効) だった。
  `-s 3` では idle の終わりが $00008000 (データキャッシュだけ無効) になり、cpu が 186376、gfx が 158795、fd が 139651 になる
  (idle は 130123)。前は `-s 3` で $80008000 だった (割り込みの届く時刻が変わり、切り替わる時刻がずれた)
- コマンド行で待っている間は、CACR のデータキャッシュのビット (EDC) が何度も切り替わる (060turbo.sys なしでは $80008000 と
  $00008000、ありでは $A0808000 と $20808000 の間。IPL ROM の CACR の読み替えを入れる前に数えて、1 フレームに約 690 回)。
  場面を始めた時点でデータキャッシュが無効だと、値が変わる。boot の直後 (900 フレームめ) は $00008000 で、
  `machine_bench ... cpu` のように boot のすぐあとに cpu を動かすと、1 フレーム 約 186000 命令になる
- コマンド行でキャッシュが有効のときに前より少ないのは、上の切り替わりで、データキャッシュが無効の間のデータの読み書きに
  バスの時間が足されるため。実行する命令の内訳は、バスの時間を足さない数え方 (359305) と同じで、回る回数だけが
  約 1/3 になる。$0CB8 を書き換えても命令の数は変わらなかった。どのプログラムが CACR を書いているかは調べていない

速さは設定で変えられる。ホスト版の `--speed060 N`、`pix68k.cfg` の `speed060=N` (5 から 3200、既定 100) で、68060 の命令の速さを
実機の N% にする (1 サイクルの長さを 100/N 倍にする。命令どうしの比は変わらない)。100 より小さくすると実機より遅くなり、
ホストの負荷が下がる。`machine_bench --cpu 68060 --speed N` も同じ単位。

#### X68030 と 060turbo の本体のバス

060turbo の 68060 は、ローカルメモリ以外 (本体のメモリ、VRAM、I/O) を X68030 の本体のバスを通して読み書きする。
pix68k が足す時間は 2 つ (`Machine::Config`):

- `busWait060`: Bus に出す読み書き 1 回 (16 ビット) に 120ns (50MHz の 6 サイクル、75MHz の 9 サイクル)。68030 の非同期の
  バスサイクルの最短 (25MHz の 3 クロック)。I/O、スプライト、グラフィック VRAM、テキスト VRAM への書き込みに足す
- `busArea`: I/O ($E80000-$EAFFFF、$EC0000-$ECFFFF) とスプライト ($EB0000-$EBFFFF) の読み書きは、上の 120ns のあと、
  1.6 マイクロ秒ごとの区切り (電源を入れてからの時間を 1.6 マイクロ秒で割り切れる時刻) まで待つ。外付け SCSI ボードの ROM
  ($EA0020-$EA1FFF) は I/O の範囲にあるが、ほかの ROM と同じく待たせない
- 本体のバスは 16 ビットなので、32 ビットの読み書きは 2 回に分かれる。待つ場所を続けて読み書きする場合、32 ビットあたり
  3.2 マイクロ秒かかる (最初の 1 回は、区切りまでの残りの時間だけ待つので短くなる)
- DMA の転送 (DMAC がするメモリと I/O の読み書き) には、どちらの時間も足さない (足すのは CPU の読み書きだけ)

どちらも本体の時間で決まるので、68060 のクロック (50 / 75MHz)、`speed060`、最高速モードでは変わらない。

`busArea` は、場所の種類ごとの表になっている。種類は、グラフィック VRAM、テキスト VRAM、I/O のデバイスごと (CRTC、DMAC、
MFP、RTC、OPM、FDC、SCC など、8KB ごと)、拡張スロット ($EC0000-$ECFFFF)。同じ 8KB の中でも、パレット ($E82000-$E823FF) と
ビデオコントローラ ($E82400 から)、スプライトのレジスタ ($EB0000-$EB07FF) と BG のレジスタ ($EB0800 から) は分ける。
スプライトの残りは PCG ($EB8000-$EBBFFF) と BG のテキストエリア ($EBC000-$EBFFFF)。種類ごとに、読みと書きで別に `pre`、
`period`、`post` (ns) を持ち、読み書き 1 回が終わる時刻を「(始まる時刻 + `pre`) を `period` の倍数に切り上げ + `post`」とする
(`period` が 0 なら切り上げない)。`pre` だけなら長さの決まった待ち、`period` だけなら上の区切りになる。
今の既定は、I/O とスプライトの種類がどれも `period` = 1600 (68030 は `pre` = 120 も)、VRAM は全部 0 で、表にする前と
同じ動きになる。場所ごとの実機の値が分かったら、この表の値だけを変える。`period` は、CPU のサイクル数に直した値が
240 の約数になるようにする (下の、ステートを読むときの時刻の直し方のため)。

X68030 (68030 25MHz) にも同じ表を使っている (25MHz の 40 サイクルごと)。待つ場所は 060turbo と同じ (スプライトも待つ)。
060turbo と同じく、待つ場所の読み書き 1 回には先に 120ns (3 クロック) を足してから、次の区切りまで待つ。足さないと、
32 ビットの読み書きの 2 回目が 1 回目と同じ区切りで終わってしまう。待たない場所 (VRAM など) には何も足さない。

1.6 マイクロ秒の出どころは、実機の si.r の system performance。si.r のループは `addq.l #1,d1` / `cmp.b (a0),d0` / `beq` で、
a0 は RTC の秒のレジスタ ($E8A001)。100% は 1 秒に 351472 周 (si.r のソースの定数。[kg68k/si-ee](https://github.com/kg68k/si-ee))。
実機の値 ([X68030 / 040turbo / 060turbo のキャッシュとパフォーマンス](http://tomoretropc.blogspot.com/2020/06/x68030-040turbo-060turbo.html)):

| 機種 | 命令 / データキャッシュ | processor | system | machine |
|---|---|---|---|---|
| X68030 (25MHz) | off | 261.59% | 177.81% | 176.13% |
| X68030 (25MHz) | on | 554.13% | 177.82% | 176.61% |
| 040turbo (25MHz) | off | 345.41% | 175.78% | 175.25% |
| 040turbo (25MHz) | on | 1672.83% | 177.82% | 177.65% |
| 060turbo (50MHz) | off | 413.36% | 177.81% | 177.32% |
| 060turbo (50MHz) | on (060turbo.sys なし) | 818.65% | 177.82% | 177.52% |
| 060turbo (50MHz) | on | 13349.22% | 177.82% | 177.34% |

177.82% は 1 秒に 625000 周で、1 周がちょうど 1.6 マイクロ秒 (10MHz の 16 クロック)。CPU の種類やキャッシュの設定で
命令の時間は 1 周 0.02 マイクロ秒から約 1 マイクロ秒まで変わるのに、system は変わらない。RTC の読み出しが
「CPU が読み始めてから決まった時間で終わる」のなら、命令の時間の分だけ値が変わるはずで、たとえば 1 回 1580ns を足すだけの
作りでは、キャッシュが有効のとき 177.82% でも、無効のときは 140.85% になる (ホスト版で測った)。そこで、読み書きは本体の側の
1.6 マイクロ秒ごとの時刻で終わるものとした。こうすると、命令の時間と 120ns の合計が 1.6 マイクロ秒より短いかぎり、
1 周はいつも 1.6 マイクロ秒になる。

実機の値がなく、仮定で決めたこと:

- 待ち方: 「1.6 マイクロ秒ごとの決まった時刻で終わる」と「前の読み書きから 1.6 マイクロ秒たつまで次を始められない」は、
  si.r では区別できない。前者にした (状態を持たずに済み、ステートの形が変わらない)。続けて読み書きするときはどちらも
  同じ時間で、違うのは間のあいた 1 回だけ (前者は平均 0.8 マイクロ秒待つ)
- 周期: 0.8 マイクロ秒の周期で、読み書きに 0.76 から 0.8 マイクロ秒かかる作りでも上の表は説明できる。その場合、続けて
  読み書きするときの時間は半分になる。cpupower.r のように I/O を続けて読む測定の実機の値があれば決められるが、見つかっていない
- 場所: 実機の値は RTC の 1 か所だけ。ほかの I/O とスプライトは RTC と同じとした (68000 の機種でも、スプライトのウェイトは
  RTC より長い。`setupBusWaits()`)。グラフィック VRAM とテキスト VRAM は 120ns のまま (68000 の機種では VRAM のウェイトは
  I/O より短い。X68030 での値は見つかっていない)
- 040turbo のキャッシュが無効のときの 175.78% (1 周 1.619 マイクロ秒) だけは、この作りでは説明できない。合わせていない
- X68030 の processor performance (実機 554.13% / 261.59%) は合わせていない。pix68k の 68030 はキャッシュの有効 / 無効で
  時間を変えず、どちらも 617% になる (68030 のサイクル数は概算)

ステートを読むときに CPU の時刻を小さい値に直す量 (`state.h` の `STATE_CPU020_CYCLES_MAX`、`STATE_CPU_TIME_PAST`) は、
240 サイクル (80 と 120 の最小公倍数) の倍数にしてある。直したあとも、1.6 マイクロ秒の区切りの位置が変わらない。

X68030 の si.r 4.14 の値 (ホスト版、`x68k_boot --cpu 68030`。060turbo.sys を組み込まない Human68k 3.02):

| si.r | 実機 (キャッシュ on) | 実機 (off) | pix68k (前) | pix68k (今) |
|---|---|---|---|---|
| processor performance | 554.13% | 261.59% | 617.80% | 617.30% |
| system performance | 177.82% | 177.81% | 658.61% | 177.82% |
| machine performance | 176.61% | 176.13% | 656.13% | 177.03% |

pix68k の値はキャッシュの設定によらず同じ。processor が 0.08% 下がったのは、割り込みの処理の中の I/O の読み書きに
時間がかかるようになったため。

確かめ方: `bus_wait_test` が、ROM なしで si.r の 2 つのループを動かす (system は 50 / 75MHz、キャッシュの有効 / 無効、
`speed060` = 50、最高速モードのどれでも 0.1 秒に 62499 か 62500 周。processor は 1 周 1 サイクルのまま。68030 でも
system は 62500 周で、processor は待ちを入れる前と同じ。$EB0000 への 32 ビットの書き込みは、68030 でも 68060 でも
0.1 秒に 31250 周)。`x68k_boot` の
`--bus-sync ns`、`--bus-sync-areas n`、`--bus-wait N` で値を変えて試せる。場所の種類ごとの値は
`--bus-area 名前=pre,period,post` (例: `--bus-area pcg=750,0,0`。値は 0 から 1000000ns) で変えられる。

ゲームの速さへの影響を、CBX68 (自作の試験用のゲーム) の、柱が並ぶ区間の描画 1600 回にかかる垂直帰線の数で測った
(ホスト版、50MHz、キャッシュ有効、プログラムはローカルメモリ。30fps で間に合えば 3200):

| そろえる場所 | 垂直帰線の数 | 速さ (3200 / 数) |
|---|---|---|
| なし (前の動き、120ns だけ) | 3913 | 81.8% |
| I/O だけ | 4265 | 75.0% |
| I/O とスプライト (既定) | 5997 | 53.4% |
| I/O とスプライトと VRAM | 6156 | 52.0% |

差の大半はスプライト ($EB0000-$EBFFFF) への書き込みで決まる。スプライトを RTC と同じとしたのは仮定なので、
実機の 060turbo か X68030 でスプライトや VRAM の読み書きの時間が分かれば、この表の値は変わる。

#### 最高速モード

ホスト版の `--max-speed`、ベアメタル版の `max_speed=on` で、ホストが実時間に間に合う範囲で CPU を一番速く動かす
(`x68k/max_speed.h`)。68000 / 68030 / 68060 のどれでも使える。CPU のクロックを上げたのと同じで、
周辺機器と画面の時間は実時間のまま、フレームも飛ばさない。0.25 秒ごとに、ホストの使った時間が X68000 の時間の 85% に
なるよう速さを変える (100 が既定のクロック、上限は 3200)。`machine_bench --speed 200` のように速さを決めて測れる
(200 でクロックを 2 倍にしたのと同じ)。
060turbo では、速さは「選んだクロック (既定 50MHz、`clock=75` で 75MHz) の実機の 68060 の何 %」で数える
(100 で命令のサイクル数が MC68060UM の表どおり)。
下限は `speed060` の値で、上限は `--max-speed-limit N` / `max_speed_limit=N` で決められる (既定の 0 は上限なしで 3200 まで。
100 にすると実機の速さを超えない。ただし上限が `speed060` より小さいときは `speed060` のほうを使うので、`speed060` を
100 より大きくしていれば、その速さのままになる)。ログと終了時の表示は「max speed: N% of a real 68060 (50 MHz)」
(75MHz では「(75 MHz)」) になる。

- 68030 / 68060 は、命令にかかるサイクル数を減らす (`Cpu020::setSpeed`)。1 サイクルのコストは 1/12800 サイクルの単位の整数なので、
  実際の速さは指定より少しだけ (3200 でも 0.5% 未満) 大きくなることがある (前は 1/800 サイクルの単位で、68030 の 1000 を超えると 2〜7% 飛んだ。#131)。
  X68030 と 060turbo の本体のバスの時間 (`busWait060` と
  `busArea`。上の「X68030 と 060turbo の本体のバス」) は縮めない。I/O とスプライトの読み書きは 1 回 1.6 マイクロ秒のままなので、
  それを多く使うプログラムは、最高速モードでも命令の速さほどは速くならない (下の 68000 とは扱いが違う)
- 68000 はコアを変えず、X68000 の時間の「速さ / 100」倍のサイクル数を CPU に走らせ、走ったサイクル数を X68000 の
  時間に直す (`Machine::runCpu000Scaled`)。命令のサイクル数は速さ 100 のときと同じ。速さ 100 のときは今までと同じ処理を通る。
  VRAM や I/O のウェイトと DRAM リフレッシュの遅れ (上の `--clock` の項) も CPU のサイクル数として足すので、速さと同じ割合で縮む。
  実機をクロックアップしたときは I/O がクロックほど速くならないが、最高速モードは CPU をできるだけ速く動かすためのものなので、
  I/O の時間を実時間のまま残すことはしていない (`src/x68k/machine.cpp` の `setupBusWaits()` の注釈)
- ベアメタル版は、そのときの速さを 2 秒ごとにログ (syslog と `/log`) に出す (`max speed: 850% of 10 MHz (85.00 MHz)`)。
  ホスト版は終わるときに出す

TOMY さんの CPUPOWER.R で、10MHz の 68000 (速さ 100 で CPU 102%) を速さ 200 にすると 204%、1000 にすると 1021% になる (バスのウェイトを入れる前に測った値)。

### SASI のハードディスク (HDF) を作る

起動できる SASI のイメージ (HDF) は、手元の Human68k 3.02 のシステムディスクから作る (ROM もディスクのイメージも、このリポジトリには入っていない)。

```sh
python3 -I tools/make_sasi_hdf.py --size 20 ~/.cache/pix68k/disk/HUMAN302.XDF human302.hdf   # 10、20、40 (MB) を選べる
./build/x68k_boot -h human302.hdf -f 900 -o hd.ppm   # フロッピーディスクを入れずに、SASI のディスクから起動する
./build/pix68k -h human302.hdf                        # ホスト版。終わるときにファイルへ書き戻すなら --write-back
```

`make_sasi_hdf.py` は、ディスクの IPL と領域の IPL をシステムディスクの中の FORMAT.X から探して写し、フロッピーディスクの
ファイルを全部、領域の中に写す。ctest の `x68k_boot_sasi` は、こうして作ったイメージから起動し、「A>」が出ることを確かめる
(システムディスクか ROM がなければ飛ばす)。

レコード数 (10MB は 40788、20MB は 81048、40MB は 162096) と、管理情報 (ランプレコード、領域の開始と大きさ) は、FORMAT.X 2.31 が
空のイメージに書いた値を読んで合わせた (`x68k_boot -h 空のイメージ --save-hdf` の上で FORMAT.X を動かし、装置初期化と領域確保をした)。
逆に、FORMAT.X で初期化、領域確保、システムの転送をしたイメージからも起動できる (10MB、20MB、40MB で確かめた)。

SASI (`src/x68k/sasi.cpp`) と SCSI の SPC (`src/x68k/spc.cpp`) は、資料 (「Inside X68000」の SASI と SCSI の章、MB89352 のデータシート、
SCSI の規格) と、IPL ROM や Human68k を動かして見たレジスタの使い方だけから作ってある。資料で決まらず、動かした結果で決めたところ:

- SASI の割り込み (IOC のハードディスク割り込み) を出すとき: IPL ROM も Human68k も使わないので手がかりがない。ステータスフェーズに入ったときに出している
- SPC のセレクションタイムアウトのあと: IPL ROM のドライバは、TEMP に $00、転送カウンタに短い時間を書いて Time Out を消し、次の割り込みを待つ。
  転送カウンタが 0 でなければもう一度 Time Out にし、0 なら信号を戻す (MB89352 のデータシートの Select コマンドの説明のとおり)
- SPC のデータインのハード転送の終わりの割り込み: FIFO を読み終えたときに出す (IPL ROM のドライバは、割り込みが出たあとは DREG を読まない)
- 時間はかけない: セレクションも装置の処理も、レジスタを読み書きしたその場で終わる

### 増設メモリ、外付け SCSI ボード、CD-ROM

増設メモリ:

- 本体のメモリ ($000000-$BFFFFF) は `--ram MB` (ベアメタル版は `pix68k.cfg` の `ram=`) で 1MB から 12MB まで選べる。既定は 4MB。
  つないだ容量より先を読み書きするとバスエラーになる
- ハイメモリ (TS-6BE16 相当、$01000000 から 16MB) は X68030 だけ (`--cpu 68030 --high-mem 16`、`high_mem=16`)。
  68000 のアドレスバスは 24 本なので、68000 の機種では $01000000 は $000000 と同じ場所になり、ハイメモリは置けない
  (指定しても使わない)。060turbo はハイメモリの代わりにローカルメモリ ($10000000 から) を使う

外付け SCSI ボード (CZ-6BS1 相当) は、SASI の機種に SCSI をつなぐボード。$EA0001-$EA001F の奇数番地に SPC (MB89352)、
$EA0020-$EA1FFF に SCSI の ROM が見える。SPC は内蔵 SCSI と同じクラス (`src/x68k/spc.cpp`) をもう 1 つ持つ。割り込みはレベル 2、ベクタ $F6。
ボードをつながなければ、$EA0000 からはこれまでどおりバスエラーになる。

SCSI の ROM はリポジトリに入れていない。`~/.cache/pix68k/rom/SCSIEXROM.DAT` (ベアメタル版は boot パーティションの
`/pix68k/SCSIEXROM.DAT` か `/SCSIEXROM.DAT`) に置く。ファイルは $EA0000 からの 8192 バイトか、$EA0020 からの 8160 バイト。
ほかの大きさ (8192 バイトまで) は、`SCSIEX` の文字列が $EA0044 に来る位置に置く。

```sh
# 外付け SCSI ボードをつなぎ、ID 0 にハードディスク (HDS)、ID 6 に CD-ROM (ISO) をつなぐ
./build/pix68k --scsi-ex --sc 0 human.hds --cd game.iso
# 設定ファイルで指定する (pix68k.cfg と同じ形式)
./build/pix68k --config pix68k.cfg
```

- `--sc ID FILE` (`sc0=` から `sc6=`): SCSI のハードディスクのイメージ (HDS、512 バイト / ブロック)。書き込みは `--write-back` のときだけファイルに戻す
- `--cd FILE` (`cd=`): CD-ROM のイメージ。ISO (2048 バイト / セクタ) か、CUE シート (`.cue`) と、そこに書かれた BIN / WAV。
  読み出しだけ。ID は `--cd-id` (`cd_id=`、既定 6)。CD-ROM 装置は 1 台まで
- `--no-scsi-ex`: 設定ファイルの `scsi_ex=on` を打ち消し、外付け SCSI ボードをつながない
- `--cd` と `--sc` (`cd=` と `sc<N>=`) で同じ ID を指定すると、ホスト版はエラーで止まり、ベアメタル版は CD-ROM のほうをつなぐ
- つなぐ先は、外付け SCSI ボードがあればボード、なければ内蔵 SCSI (X68030 と 060turbo)。どちらもなければ、ホスト版はエラーで止まり、ベアメタル版は警告を出して無視する。ID 7 は本体が使う
- ホスト版の `--config FILE` は、ベアメタル版の `pix68k.cfg` と同じ形式のファイルを読む (キーは `src/platform/settings.h` の表。
  ファイル名の値は、`/` で始まらなければ設定ファイルのあるディレクトリから)。コマンドラインで指定したものが優先する

外付け SCSI のハードディスクから起動するには、SRAM の起動デバイスを ROM 起動、ROM 起動のアドレスを $EA0020 + ID x 4 にする
(Human68k の `SWITCH.X` の `BOOT` など)。`x68k_boot` では `--boot-rom EA0020` で同じ設定にして起動できる。

CD-ROM 装置 (`src/x68k/cd_drive.h`、コマンドは `src/x68k/spc.cpp`) は、SCSI-2 の規格 (X3T9.2/375R revision 10L) の次のコマンドに答える:
TEST UNIT READY、REZERO UNIT、REQUEST SENSE、INQUIRY (装置タイプ 5、取り外しできる媒体)、READ(6) / READ(10)、READ CAPACITY、
READ TOC (すべてのトラックとリードアウト、LBA と MSF)、READ SUB-CHANNEL (今の位置とオーディオステータス)、
MODE SENSE(6) / (10)、MODE SELECT(6) (受け取って捨てる)、START STOP UNIT、PREVENT ALLOW MEDIUM REMOVAL、SEEK、VERIFY、
PLAY AUDIO(10) / (12)、PLAY AUDIO MSF、PLAY AUDIO TRACK INDEX、PAUSE RESUME。
書き込みのコマンドは不正なコマンドとして断る。ブロックの大きさの変更、音量と出力の切り替え (MODE SELECT のページ 0Eh)、
メディアカタログ番号と ISRC はない。X68000 の CD-ROM のドライバが実際に出すコマンドは確かめていない (ドライバが手元にない)。

- PLAY AUDIO TRACK INDEX のインデックス: イメージから分かるのは 0 (プリギャップ) と 1 だけ。始まりが 0 ならプリギャップの始まりから、1 なら INDEX 01 から、2 以上なら次のトラックの始まりから鳴らす (鳴らすところがなければ、何もせずに正常に終わる)。終わりのインデックスは、0 でも 1 以上でも、終わりのトラックの終わりまで
- ハードディスクの MODE SENSE のページ: 03h (フォーマットのパラメータ) と 04h (ドライブの形)。イメージに形はないので、8 ヘッド、1 トラック 32 セクタとして、シリンダ数をブロック数から決める
- CD-ROM 装置の MODE SENSE のページ: 01h (読み出しのエラー回復)、0Dh (CD-ROM のパラメータ。1 分 = 60 秒、1 秒 = 75 フレーム)、
  0Eh (オーディオの制御。PLAY AUDIO は再生を始めたらすぐ終わる、次のトラックへ続けて再生する、音量は最大)。3Fh はこの 3 つをすべて返す
- CUE シート: `FILE` (BINARY / MOTOROLA / WAVE)、`TRACK` (AUDIO、MODE1/2048、MODE1/2352、MODE2/2336、MODE2/2352)、`INDEX`、
  `PREGAP`、`POSTGAP`、`FLAGS` を読む (`src/platform/cue_sheet.h`)。2352 バイト / セクタのデータトラックは、セクタごとにユーザデータの
  2048 バイトだけを返す。WAV は 44.1kHz、16 ビット、ステレオの PCM だけ。BIN / WAV は CUE シートと同じディレクトリから探す。
  ホスト版は `FILE` が複数の CUE シート (ISO + トラックごとの WAV など) も読む。ベアメタル版は `FILE` が 1 つの CUE シートだけ
  (複数のファイルを 1 つのイメージとして読む仕組みがない。警告を出して無視する)
- オーディオのトラックの再生: PLAY AUDIO で始め (始まりが FFFFFFFFh、PLAY AUDIO MSF では FF:FF:FF なら、今の位置から。SCSI-2 にはなく、あとの MMC の決まり)、PAUSE RESUME で一時停止と再開、START STOP UNIT (Start = 0 か LoEj)、READ、SEEK、REZERO UNIT、VERIFY で止まる。
  再生は X68000 の時間で進む (1 秒に 75 ブロック)。44.1kHz のステレオを、OPM のサンプル (62.5kHz) ごとに線形補間し、
  さらに出力のサンプリング周波数に線形補間して、1/2 にして出力のフレームに足す。MIDI の音源と同じく、X68000 の出力のフィルタ
  (直流を切るフィルタと低域通過フィルタ) は通さない (実機の CD-ROM 装置のオーディオは装置の出力から出て、X68000 の音声の回路を
  通らない)。足して 16 ビットを超えた分は、上限と下限で止める。音の合成を別のコア (`sound_core=on`) で
  行うときは、再生したフレームを X68000 を動かすコアがイメージから読んで、合成のコアに渡す (記録は、前のフレームとの差が
  14 ビットに入れば 1 フレームに 1 個、入らなければ 2 個)。大きなイメージでは使うチャンクだけを読み、
  チャンクを読み込んでいる間は再生の位置を進めずに待つ (その間は無音)。再生がデータトラックに入ると止まり、次のコマンドに
  CHECK CONDITION (BLANK CHECK) を 1 回返す
- 媒体の入れ替え: 設定メニューの CD-ROM でイメージを選ぶと、動かしたまま媒体を入れ替える (CD-ROM 装置をつないで起動したときだけ。
  `cd=` なしで起動したときは、次の起動から)。X68000 には、次のコマンドで UNIT ATTENTION (NOT READY TO READY TRANSITION,
  MEDIUM MAY HAVE CHANGED) が 1 回返る。(none) を選ぶと取り出し、媒体の要るコマンドは NOT READY (MEDIUM NOT PRESENT) になる。
  X68000 が START STOP UNIT (LoEj) でトレイを開けたときも同じで、閉じる (LoEj + Start) かメニューで入れ直すまで媒体はない。
  PREVENT ALLOW MEDIUM REMOVAL で禁止している間は、START STOP UNIT では開かない (メニューからの入れ替えは禁止していてもできる。禁止されていたことをメニューの下の行に出す)
- ステートに、トレイ、禁止、再生の状態と位置が入る (版 8 から。版 12 からは CD-ROM 装置をつないでいるときだけ)。イメージは入らないので、同じイメージをつないで読むこと
- ステートの版 12 で、SASI と SPC の状態の並びが変わった。版 11 までのステートも読める。SPC はレジスタ (BDID、SCTL、SCMD、PCTL、TEMP、転送カウンタ) だけを戻し、
  SASI と SPC のバスと転送の状態は読み飛ばして、バスフリーから始める。版 11 までのステートのうち、SCSI のコマンドの途中
  (SPC がターゲットと結合している間) で保存したものは読まない (`saved in the middle of a SCSI command by an older version`):
  コマンドの続きを戻せず、X68030 では IPL ROM のドライバが答えを待ち続けて止まる。SASI のコマンドの途中で保存したものは読める
  (その読み書きは続かないが、ドライバがやり直す)。
  前の実装で X68030 を SCSI のハードディスクから起動して保存した版 11 のステートを読み、そのあと SCSI のディスクにファイルを写せた

確かめたこと (上の 2 つは、ROM とイメージがなければ ctest では飛ばす):

- `x68k_boot_scsi_ex`: SASI の機種 (68000) で、外付け SCSI の ID 0 の HDS (`SCSI_EX_HDS`) から ROM 起動し、「A>」が出る
- `x68k_boot_scsi30_stream`: X68030 の内蔵 SCSI の ID 0 の HDS (`SCSI30_HDS`、既定 `~/.cache/pix68k/disk/HUMAN30.HDS`。なければ作らない) から、

- `x68k_scsi_ex_cdrom` (`tests/x68k/scsi_iocs.cpp`): Human68k を起動したあと、ROM の SCSI IOCS (`_S_INQUIRY`、`_S_READCAP`、
  `_S_READEXT`) で ID 6 の CD-ROM を読み、装置タイプ、容量、ブロック 16-17 の中身がイメージと合う
- `spc_test`: SPC のレジスタと転送、ハードディスクのコマンド、ボードのアドレス、ROM の置き方、割り込みのベクタ。CD-ROM のコマンドは `cdrom_test`。書き直す前のビルドが保存した古い版のステート (`tests/unit/old_scsi_state_data.h`。ROM なしの空の Machine) を読めることも確かめる
- susie.x 1.21A (GORRY さん) を `DEVICE = \SUSIE.X -ID6 *:` で組み込み、X68030 の内蔵 SCSI の CD-ROM (ISO 9660 のイメージ) を

  ボードの ROM が手元にないので試していない
- `cdrom_test`: CUE シートの読み方、READ TOC、2352 バイト / セクタのデータトラックの読み出し、MODE SENSE のページ、媒体の入れ替えと
  取り出し、オーディオのコマンド (再生したフレームがイメージの PCM と同じ)、使うチャンクだけを読むイメージでの読み出しと再生、
  1kHz / 500Hz の正弦波を再生したときの出力 (48kHz) の実効値と周波数、10kHz の正弦波の振幅が補間だけで決まる値になる
  (出力のフィルタを通らない) こと、足して 16 ビットを超えた分が上限と下限で止まること (MIDI の音源があるときと、OPM と CD だけのとき)、
  フレーム 1 つだけを入れたときの補間の両端と止まる条件、ステートを読んだ直後 (止まっていたときと、別のところを再生していたとき) の出力、音の合成を別のコアで行うときの音が 1 つのコアのときと同じこと、
  ステートの保存と読み込み
- `sound_thread_test`: 起動、OPM、ADPCM に続けて CD-ROM のオーディオを再生し、音の合成を別のスレッドで行っても同じ音になる
- `host_cdrom` (`tests/host/cdrom_test.sh`): ホスト版 (X68030) で CUE シートをつなぎ、メニューで入れ替え、取り出し、読めない CUE シートを選ぶ
- ベアメタル版の CUE シートの読み込みとメニューでの入れ替え、実機の音は確かめていない (ビルドだけ)

ベアメタル版は、SCSI と SASI のイメージを起動のときに全体を読まず、使う 16KB のチャンクだけを SD カードから読む
(1MB 以下のイメージは全体をメモリに読む。下の「大きなイメージ」を参照)。メモリに入るイメージは、イメージ全体の大きさの
キャッシュを用意し、読んだチャンクを追い出さない。残りのチャンクは、X68000 を動かしながらコア 0 が裏で先頭から順に読む
(1 フレームに 128KB まで、1 秒に 7MB ほど。X68000 が読みたいチャンクがまだなら、それを先に読む)。読み終えるとログに
`sc0: the whole image is in memory` を出し、それからは SD カードを読まない。書き込みは、これまでと同じくメモリの上のチャンクに書いて
ファイルに書き戻す (下の「ディスクの書き戻し」。電源を切ったときに失う範囲は変わらない)。メモリの使い方:

- Pi 4 / Pi 5 でメモリが 1GB より多いとき: キャッシュの中身を 1GB より上のヒープ (Circle の `HEAP_HIGH`。Pi 4 は 3GB まで、
  Pi 5 はメモリの終わりまで) に置く。空きを調べ、16MB 残して入るイメージ (4GB - 16KB まで。Circle のヒープの 1 つのブロックの上限) は全体を置く。チャンクの表など
  (64MB のイメージで 70KB ほど) は 1GB より下に置く。SD カードからは 1GB より下のバッファ (16KB) に読んでから写す
- Pi 3 と、メモリが 1GB の Pi 4、1GB より上に入らないとき: 1GB より下のヒープに置く。ここは Circle の `new` が使うヒープで、
  060turbo のローカルメモリ、SoundFont、MT-32 / SC-55 の ROM なども同じところから取り、足りないと全体が止まる。
  そこで確保する前に空きを調べ、32MB 残して入るときだけ全体を置く。64MB より大きいイメージは、その空きの半分までに
  収まるときだけ全体を置く
- どちらにも入らないイメージは、4MB のキャッシュ (256 チャンク) に使うチャンクだけを読む (読むコマンドの範囲と、その後ろの
  2 チャンクを先に読む)

起動のときのログの `sc0: ... (... bytes; read on demand, N KB cache above 1 GB, the rest is read in the background; ...)` で、
キャッシュの大きさ、置いたところ、全体を読むかどうかが分かる。フロッピーディスクのイメージ (1〜2MB) は、これまでどおり
入れたときに全体を読む。CD-ROM のイメージも同じキャッシュを使う。メニューで CD-ROM を入れ替えたときは、1GB より上に全体が
入ればそこに置き、入らなければ 4MB のキャッシュにする (一度作ったキャッシュは次の媒体にも使い回す)。
イメージは `sc0=` から `sc6=`、`cd=` の ID の順に読む。
読み込みの途中で失敗したときは、そのとき確保したメモリが戻らない (Circle は 512KB を超えるブロックを解放しても使い回さない) ので、
残りの SCSI のイメージは読まない。0 バイトのファイルは警告を出して飛ばし、次のイメージを読む。

### ディスクの書き戻しと大きなイメージ (ベアメタル版)

X68000 がフロッピーディスクとハードディスク (SASI、SCSI) に書いた内容は、SD カードのイメージのファイルに書き戻す (`write_back=on`、既定)。
`write_back=off` にすると書き込みはメモリの上だけで、電源を切ると消える (前の版と同じ)。

- 書く時期: 書き込みが 2 秒止んだとき (書き続けていても 30 秒ごと)。ほかに、フロッピーディスクの入れ替えと取り出し、
  設定メニューの Reset、Restart、Save settings、Save state のとき。設定メニューを開いている間 (X68000 は止まっている) は、
  書いていない分を待たずに書く。フロッピーディスクを入れ替えるときは、新しいイメージを読む前に今のディスクを書く
  (同じファイルを入れ直しても、書き戻す前の古い内容を読まない)。書き終えるとログに `fd0: image file replaced` や `hd0: written back` を出す
- コア 1 (X68000) は SD カードに触らない。コントローラは書いたバイトの 16KB のチャンクの dirty フラグを立てるだけで、コア 1 はフレームの切れ目で
  dirty フラグの立ったチャンクを 1 フレームに 64KB まで受け渡しのバッファに写し、コア 0 が FatFs で書く (`src/platform/disk_sync.h`)
- 書き方: ハードディスクはファイルの中の書いたチャンクだけを上書きし、まとめて `f_sync` する。数百 MB のファイルを毎回書き直すわけには
  いかないので上書きにする。途中で電源が切れると、そのとき書いていたチャンク (多くて 64KB) は古い中身と新しい中身が混じることがある
  (本物のハードディスクで書いている途中に電源を切ったのと同じ)。ファイルの大きさとクラスタの並びは変えないので、FAT は壊れない。
  フロッピーディスク (1〜2MB) は全体を `<名前>.new` に書いてから元のファイルと置き換える (SRAM や pix68k.cfg と同じ手順。
  `src/platform/file_replace.h`)。途中で電源が切れても、前の内容か新しい内容のどちらかが残る
- 書けなかったとき: 書けなかった分は受け渡しのバッファ (フロッピーディスクはコア 0 の写し) に残し、1 秒から 30 秒まで間を延ばしながら
  書き直す (待つ間と続けて失敗した回数はディスクごとに持ち、書けないディスクがあっても、ほかのディスクのチャンクは書く。ただし受け渡しのバッファは 1 つなので、書けないディスクのチャンクが残っている間は、ほかのディスクの次のチャンクは写せない)。ハードディスクのファイルは開き直してから書き直す (FatFs は読み書きのエラーを開いたファイルに残し、
  そのファイルの以後の読み書きがすべて失敗するため)。書けないままのフロッピーディスクは取り出さず、Restart もしない (メニューに理由を出す)。
  SD カードに空きがないときなどに抜けられるよう、ほかの操作をはさまずに続けてもう一度同じ取り出し (同じドライブの一覧の [Eject]) か Restart を選ぶと、書き戻さずに取り出す / 再起動する
  (書けなかった内容は消える)。`tools/deploy_pi.sh` で起動したときの終わりの再起動 (`pix68k_deploy=秒数`) も、書けるまで X68000 を止めたまま
  1 秒ごとに書き直す。その間の入力は捨てる。メニューは開ける (閉じても X68000 は止めたまま)。書ければそのまま再起動し、メニューの Restart を 2 回選べば
  書き戻さずに再起動する
- ステートの読み込みは X68000 のメモリと周辺機器の状態だけを戻し、ディスクのイメージは戻さない (保存したあとに書いた内容は、ファイルに書き戻した
  ままになる)。ステートを保存したときと同じ中身のディスクで読み込む
- 書き込み禁止: ファイルの読み取り専用の属性、D88 のヘッダの書き込み禁止、`write_protect=fd1,sc0` (fd0 fd1 hd0 sc0〜sc6 を並べる) で
  書き込み禁止にする。同じファイルを 2 台のドライブに入れたときは、2 台目を書き込み禁止にする。CD-ROM は書かない
- 既定を `on` にした理由: SD カードの書き込みの回数より、X68000 で保存したものが電源を切ると黙って消えるほうが困るため。
  書き込みが止んでからまとめて書くので、書く回数は X68000 の書き込みの回数より少ない

ハードディスクと CD-ROM のイメージ (1MB を超えるもの。FAT32 の上限の 4GB まで) は、使う 16KB のチャンクだけをキャッシュに読む
(`src/x68k/disk_cache.h`)。キャッシュは、メモリに入るイメージならイメージ全体の大きさ (残りのチャンクは裏で読む)、
全体の大きさのキャッシュ (管理領域を含む) が入らないイメージは 4MB (入るかどうかの決め方は、上の「メモリの使い方」)。
以前は 64MB 以下のイメージを起動のときに全体を読んでいたが、SASI の 20MB のイメージで QEMU で 2.7 秒かかったので、起動を待たせないようにチャンクだけを読むようにした。コア 1 は SD カードを読めないので、まだ読んでいないチャンクに来ると、コントローラは REQ を出さず
(SPC は FIFO を空 / 一杯にし、DMAC にも要求を出さずに) コア 0 が読み終えるまで待つ。読み書きの範囲のチャンクと、その後ろの 2 チャンクは
コマンドを受けた時点で先に頼む。書いたチャンクは書き戻すまでキャッシュから追い出さない。読めなかったチャンクはエラーのステータス
(SASI はセンス 0x11、SCSI は MEDIUM ERROR) にする。FatFs は fast seek (`FF_USE_FASTSEEK`) を有効にしてビルドし
(`tools/build_baremetal.sh` が Circle の写しの `ffconf.h` を書き換える)、ファイルの中の位置を変えるときに FAT をたどらない。
`write_back=off` のときは、書いた内容をメモリに残すため、ヒープに入るイメージは起動のときに全体を読む。入らないイメージは書き込み禁止にする。
SASI の FORMAT DRIVE / FORMAT BLOCK も同じキャッシュを通して行い、まだ読んでいないチャンクに来ると、REQ を出さずに BSY のまま
コア 0 が読み終えるまで待つ (0 にしたチャンクは書き戻すまで追い出さないので、4MB のキャッシュでは書き戻しながら進む)。速さのログと一緒に、読んだチャンクの数と時間を出す
(`disks: N chunk reads (avg U us, max M us)`)。

SD カードの速さの見積もり: Pi 3 の Raspberry Pi OS で測ると、16KB のランダムな読み込みが 1 回 1.06ms (15MB/s)、順の読み込みが 15〜20MB/s だった
(Circle の SD のドライバの速さは実機で未確認)。X68000 の SCSI のハードディスクはシークに十数 ms かかり、転送は速くても 1〜2MB/s なので、
チャンクを待つ時間は本物のドライブより短いと見ている。

ハードディスクの DMA の転送 (DMAC のチャネル 1。内蔵 SCSI の ROM は SPC の DREG をオートリクエストで 256 バイトずつ、
SASI の IOCS はデータのレジスタを外部要求で読む) は、X68000 の時間を使わない。060turbo の速さで大きなファイルを読むと
1 フレームに 50 万バイトほどを転送し、1 バイトずつ転送すると、その時間でフレームが遅れた (Pi 5 で最悪 51ms。SD カードの
読み込みを待つ時間ではない)。そこで、デバイスから RAM への転送は、1 バイトずつ転送したときと結果 (メモリ、SPC / SASI の
状態、DMAC のレジスタ) が同じになる分だけをまとめて写す (`Spc::readData()`、`Sasi::readData()`、`Machine::dmaBlockToRam()`。
フロッピーディスクの読み込みと同じ仕組み)。X68000 から見た結果と時間は変わらない。RAM からデバイスへの転送 (書き込み) は
1 バイトずつのまま。`spc_test` と `sasi_test` で、まとめた転送と 1 バイトずつの転送の結果が同じことを確かめる。

ctest で使う ROM とイメージの場所は、CMake の `SCSI_EX_ROM` (既定 `~/.cache/pix68k/rom/SCSIEXROM.DAT`) と
`SCSI_EX_HDS` (既定 `~/.cache/pix68k/disk/HUMAN302.HDS`) で変えられる。

### 数値演算プロセッサボード、まーきゅりーゆにっと

どちらも拡張スロットに挿すボードで、おもに 68000 の機種で使う。既定ではつながない。`cpu=68030` / `68060` でもつなぐ (数値演算プロセッサボードは $E9E000 に CIR が見えるだけで、CPU の FPU とは別)。ホスト版は `--fpu-board` / `--mercury`
(`--no-fpu-board` / `--no-mercury` で設定ファイルの指定を打ち消す)、ベアメタル版とホスト版の設定ファイルは `fpu_board=on` / `mercury=on`。
数値演算プロセッサボードは 2 枚までつなげる。2 枚目は $E9E080-$E9E09F に CIR が見える。設定ファイルは `fpu_board=2`、ホスト版は `--fpu-board 2`
(`--fpu-board` だけなら今までどおり 1 枚)。設定メニューの FPU board は off、on、2 の順に切り替わる。

数値演算プロセッサボード (CZ-6BP1 相当、`src/x68k/fpu_board.cpp`) は MC68881 を 1 個載せたボード。68000 には
コプロセッサインターフェースがないので、Human68k のドライバ (システムディスクの `\SYS\FLOAT3.X`) が $E9E000-$E9E01F の
コプロセッサインターフェースレジスタ (CIR) を読み書きして使う。CIR の動きは MC68881/MC68882 User's Manual の 7 章に従い、
中の計算は X68030 の 68882 と同じもの (`src/m68k/fpu_core.cpp`) を使う。68882 との違いは、FSAVE のフレーム
(IDLE は 6 ロング、BUSY は 45 ロング) と、評価と転送のプリミティブがいつも CA = 1 なこと。
計算はコマンドやオペランドを受け取った時点ですぐ終わり、実機の計算の時間は待たせない。
2 枚目のボードは 1 枚目と同じ作りで、レジスタも手順も別々に持つ (片方の手順の途中で、もう片方を使ってもよい)。
$E9E000-$E9FFFF のうち、2 つの CIR の外 ($E9E020-$E9E07F、$E9E0A0 から上) と、つないでいないボードの CIR はバスエラーにする。
1 枚のときに $E9E020 から上をバスエラーにしていたのに合わせたもので、実機で確かめてはいない。
2 枚目の先頭が $E9E080 なのは、前からソースの注釈にあった XEiJ の説明書の記述による。2 枚目も 32 バイトの CIR を持ち、
1 枚目と同じに動くとしたのは推測。FLOAT3.X などのドライバが 2 枚目を使うかは確かめていない。

まーきゅりーゆにっと (`src/x68k/mercury.cpp`) は 16 ビットのステレオ PCM を出すボード。$ECC080 にデータを書き、
$ECC091 のコマンドで周波数 (44.1kHz / 48kHz / 32kHz と、その半分) とステレオ / モノラル、L / R の出力を選ぶ。
データは DMAC のチャネル 2 (外部要求) で送る。ボードの中のバッファに空きがあれば転送を要求し、選んだ周波数で取り出して
OPM と ADPCM の音に混ぜる。音の合成を別のコア (ベアメタル版のコア 3) で行うときも、書き込みを記録して同じ音を作る。
レジスタは公開されている互換ボードの説明 (下の参考) から作ったもので、バッファの大きさ (8 語) などは推測。
OPN (YMF288) と割り込みは作っていない。

確かめたこと:

- `boards_test`: CIR の手順 (レジスタどうし、メモリから / メモリへ、制御レジスタ、FMOVEM の静的 / 動的なリスト、
  条件と BSUN、演算の例外、FSAVE / FRESTORE の IDLE と BUSY、パック 10 進の動的な k ファクタ)、68000 の命令からの読み書き、
  2 枚目のボード (68000 と 68030 の命令から $E9E080 を読み書きして 1 枚目と別の値になること、CIR の外のバスエラー、ステートの保存と読み込み)、
  まーきゅりーゆにっとのレジスタと周波数、DMAC のチャネル 2 の転送の速さ、記録を当てた側の音が 1 つのコアのときと同じになること、
  DMAC のチャネル 2 の CSR の PCS に L / R のクロックが見えること
- `x68k_boot_float3` (`tests/x68k/boot_float3.sh`): システムディスクの CONFIG.SYS を `FLOAT3.X` に書き換えたイメージで起動し、
  ボードがあれば FLOAT3.X が組み込まれ、X-BASIC の `print sin(1.0),exp(1.0)` が FLOAT2.X (ソフトウェア) と同じ値になる。
  ボードがなければ FLOAT3.X は組み込まれない
- PCM8PP 0.83d (Tany さん) が常駐し (44.1kHz、ステレオ、16ch)、PCM8 のファンクションコール (trap #2) で鳴らした
  441Hz の矩形波 (16 ビット、44.1kHz、モノラル、1 秒) が WAV に出る。定位を左だけにすると右は 0 になる。68000 の 16MHz / 10MHz と
  X68030 で確かめた。MKMU.R (Mercury-Unit V4 用) のあとに常駐させても同じ。mercury.x では試していない
- 拡張スロットの EXPCL は DMAC のチャネル 2 の PCL につながっていて、CSR の bit0 (PCS) で読める。まーきゅりーゆにっとは
  ここにサンプリング周波数の L / R のクロックを出す (PCM8PP は常駐するときに PCS が 1 から 0 に変わるのを待つ)

参考にした資料: MC68881/MC68882 User's Manual (Motorola / Freescale) の 6 章と 7 章、Inside X68000 (桑野雅彦、ソフトバンク)
の数値演算プロセッサの章、XEiJ の説明書 (ボードのアドレス)、yunkya2 さんの wifipcm の README と pcm.c の説明
(GIMONS さんの PilederX をもとにした互換ボード)。レジスタの位置は、上に書いた PCM8PP と MKMU.R が実際に動くことで確かめた。

### ネットワークボード Neptune-X

Neptune-X (`src/x68k/neptune.cpp`) は、拡張スロットに ISA バスをつなぎ、NE2000 互換のイーサネットのコントローラ
(National Semiconductor DP8390 と 16KB のバッファメモリ) を載せたボード。既定ではつながない。設定ファイルは `neptune=on`、
ホスト版は `--neptune` (`--no-neptune` で設定ファイルの指定を打ち消す)。

- アドレスと割り込み: $ECE000-$ECE3FF (ISA のポート $200-$3FF を 2 バイトおきに置く)。NE2000 はポート $300 にあり、
  DP8390 のレジスタが偶数番地の $ECE200-$ECE21E、データポートが $ECE220 (16 ビット)、リセットポートが $ECE23E。
  割り込みは IRQ2 (レベル 2)、ベクタ $F9。外付け SCSI ボード (同じ IRQ2、ベクタ $F6) と同時に割り込みを要求したときは、外付け SCSI を先に応答させる
- MAC アドレス: 既定は `02:68:6b:00:00:01` (ローカル管理のアドレス)。`neptune_mac=` (ホスト版は `--neptune-mac`) で変える。
  ドライバは PROM (リモート DMA のアドレス $0000-$001F) から読む
- フレームの送受信先 (`neptune_link=`、ホスト版は `--neptune-link`):
  - `echo`: ネットワークにはつながず、相手の機械が 1 台だけあるものとして、ARP の問い合わせと ping に答える (試験用。ホスト版の既定)
  - `loopback`: 送ったフレームをそのまま返す (ホスト版だけ)
  - `pcap:IF` (ホスト版だけ): libpcap で、ホストのネットワークインタフェース IF とイーサネットのフレームを送受信する。BPF (`/dev/bpf*`) を読み書きする権限が要る
    (macOS なら Wireshark の ChmodBPF を入れるなど)。有線のインタフェースで使う。Wi-Fi は、ほかの MAC アドレスのフレームを
    アクセスポイントが通さないことが多い
  - `tap:NAME` (Linux のホスト版だけ): tap デバイスに出し入れする。あらかじめ作っておく
    (例: `sudo ip tuntap add tap0 mode tap user $USER && sudo ip link set tap0 up`。ホスト側でブリッジや NAT を組む)
  - `eth` (ベアメタル版の既定): Pi の有線の Ethernet (Pi 3B+ は LAN7800、Pi 3B は LAN9514、Pi 4 / Pi 400 は GENET、Pi 5 は RP1 の MACB)。ホスト版で `eth` を指定すると、警告を出して `echo` にする (ベアメタル版と同じ設定ファイルを使えるように)。
    コア 0 が Circle のネットワークデバイスでフレームを出し入れし、コア 1 とはロックのないリングで受け渡す (`baremetal/net_bridge.h`)。
    X68000 の MAC アドレス宛てのフレームを受け取るため、デバイスをプロミスキャスにする。`neptune_mac=pi` なら Pi の MAC アドレスを
    X68000 に使い、USB のもの (LAN7800、LAN9514) はプロミスキャスにせず、マルチキャストをすべて通す設定にする。Wi-Fi は使えない (Circle の WLAN はファームウェアを要し、ほかの MAC アドレスのフレームも通らない)
- ベアメタル版で `neptune_link=eth` のときは、ネットワークの口 (`net=on`。下の「ネットワークの口」を参照) は動かさない (同じ Ethernet のデバイスを使うため)
- ステートにはボードのレジスタとバッファメモリを入れる (ステートのヘッダで拡張ボードの有無を表すビットのうち、bit2 を使う)

作り:

- DP8390 のレジスタ (ページ 0〜2)、リモート DMA (16 ビット / 8 ビット、DCR の BOS)、受信リング (PSTART / PSTOP / BNRY / CURR、
  各フレームの前に置く 4 バイトのヘッダ)、受信のフィルタ (自分の MAC アドレス、ブロードキャスト、マルチキャストのハッシュ、
  プロミスキャス、MON)、受信リングがあふれたときの OVW と、取り落としたフレームの数 (CNTR2)、ISR と IMR による割り込み、TCR のループバック
- 受け取ったフレームは 60 バイトに満たなければ 0 で埋め、FCS (CRC-32) を付けてリングに書く。受信の時間は数えない。
  送信は、10Mbps の線で送る時間 (プリアンブルとフレームの間の時間を含む。60 バイトのフレームで約 67us) が過ぎてから送り終える
  (CR の TXP はそれまで 1 のまま)。すぐに送り終えると、ether_ne.sys 0.03 が送り終えたことを取りこぼし、二度と送らなくなる。
  受け取ったフレームは `Machine` が各ラスタの始まりで 1 つずつ取り込む。受信リングに入らないフレームは、実機と同じく捨てて ISR の OVW を立てる。ヘッダのバイト数はフレームと FCS で、ヘッダの 4 バイトは含まない (NetBSD の dp8390.c がバイト数を計算し直す式と合う)
- 資料で決められなかったところ (奇数番地、データポートのバイトの並び、リセットの後のレジスタの値など) は `src/x68k/neptune.h` の先頭に書いた

確かめたこと:

- `neptune_test`: NetBSD/x68k の起動プログラム (`sys/arch/x68k/stand/boot/ne.c`、`dp8390.c`) と同じ手順で、リセット、PROM からの
  MAC アドレスの読み出し、初期化、送信、受信リングからの読み出し (リングの終わりをまたぐもの) を行う。フィルタ、あふれ、ループバック、
  8 ビットの転送、BOS、ステート、68000 の命令からの読み書きとレベル 2 の割り込み、`echo` との ARP と ping の問い合わせと答え
- `tools/qemu_human68k.sh` の `NEPTUNE=1`: QEMU の raspi3b に USB の Ethernet (`-device usb-net`) をつなぎ、X68000 の MAC アドレスから出した
  ARP の問い合わせに QEMU のゲートウェイ (10.0.2.2) が答え、その答えがコア 0 に届く
- Human68k のドライバ ether_ne.sys 0.03 (Shi-MAD さん) と etherL12.sys (+M01 +1 +L12) を組み込み、計測技研の TCPPACKA の
  inetd.x、ifconfig.x で en0 を設定し、ping.x で `echo` の相手に 10 回 ping して 10 回とも答えが届く (`x68k_boot --neptune`。
  68000 の 16MHz / 10MHz と X68030)。`echo` はどの IP アドレスの ARP にも答えるので、本物のネットワークにつないだことにはならない。
  ether_ne.sys 0.03 では netstat.x -i がバスエラーになる (ドライバが統計のファンクションを作っていない。etherL12.sys の
  VersionUp.doc に直したとある)。実機の Pi の Ethernet では、まだ動かしていない

参考にした資料: National Semiconductor DP8390D (NIC) のデータシート、NetBSD/x68k の `neptune.c` と起動プログラムの `ne.c`、`dp8390.c`
と `GENERIC` の設定 (アドレス、ポートの置き方、割り込みのベクタ 249)。どれもコードは使っていない。範囲 ($ECE000-$ECE3FF)、
割り込みのレベル (2)、PROM の中身は、ether_ne.sys と etherL12.sys が動く値にした。実機のボードでは確かめていない。

### RS-232C (SCC のチャネル A)

X68000 の RS-232C は SCC (Z8530、$E98005 がコマンド、$E98007 がデータ) のチャネル A につながっている (チャネル B はマウス)。
相手は TCP の接続にする。既定ではつながない (`rs232c=off`)。設定ファイルは `rs232c=`、ホスト版は `--rs232c` で指定する。

- `rs232c=tcp:PORT`: TCP の PORT で待ち受け、つないできた相手 1 つとバイトをそのままやり取りする。ホスト版は 127.0.0.1 で待ち受ける。
  ベアメタル版はネットワークの口 (`net=on`。下の「ネットワークの口」を参照) の IP アドレスで待ち受け、`net_allow=` があればそのアドレス
  からだけ受ける (`net_token=` は見ない。家の中のネットワークだけで使う)。80 番 (HTTP) は使えない。Neptune-X が Ethernet を使うとき
  (`neptune=on` で `neptune_link=eth`) はネットワークの口が動かないので、RS-232C の TCP も使えない
- `rs232c=tcp:ADDR:PORT` (ホスト版だけ): ADDR で待ち受ける (`0.0.0.0` ならすべてのインタフェース。ほかの機械から届く)
- telnet の取り決め (IAC) はしないので、`nc` か `socat` でつなぐ (例: `nc 127.0.0.1 2324`)。`telnet` でつなぐと、取り決めのバイトが X68000 に届く
- つないでいる間は、X68000 から見た DCD と CTS が 1 になる (切れると 0)。つないでいない間に X68000 が送ったバイトは捨てる
- X68000 が受け取るのも送るのも、SCC に設定したボーレートの速さ (1 文字の時間に 1 バイト)
- 相手が読まないとき、X68000 は止めずに送り続け、あふれた分を捨てる (CTS は下ろさない)。ためておくのは、送信のリングの 4KB と、
  その先の送信待ちまで。ホスト版は送り出し待ちの 1KB と OS の TCP の送信バッファ。ベアメタル版は Circle の送信待ちで、
  上限 `TCP_CONFIG_TX_THRESHOLD` (64KB) を見てから 1KB までまとめて積むので、上限を最大で 1023 バイト超える
- X68000 が RTS (WR5 bit1) を下ろしている間は、届いたバイトを X68000 に渡さない。ホスト版は受信のリング (4KB) が満ちたら
  ソケットから読まず、OS の TCP が相手を待たせる。ベアメタル版は Circle が TCP の受信の窓を狭めない (読まなくても相手は
  送り続ける) ので、受信のリングを 64KB にしてため、あふれた分は捨てる (切れたときに捨てた数をログに出す)。
  X68000 はボーレートの速さでしか読まないので、相手が一度に 64KB を超えて送ると、RTS が上がっていても超えた分を捨てる。
  ベアメタル版につなぐ相手は、ボーレートより速く送らないか、一度に送るのを 64KB までにする
- 相手が切れたら、すぐ DCD と CTS を 0 にする (受信を止めていてリングが満ちていても)。届いてリングに入っていたバイトは
  X68000 が読むまで残す (送ってすぐ閉じる相手の最後まで届く)。ホスト版で、リングが満ちていて OS の受信バッファに残っていた分は捨てる。
  次の相手がつながったときに、まだ読んでいない前の相手のバイトを捨てる (次の相手のバイトと混ぜない)
- ベアメタル版の Pi の UART (GPIO 14 / 15) や USB シリアルにはまだつながない (UART はログと `midi_out=uart` が使っている)

```sh
# ホスト版: 2324 番で待ち受け、Human68k の AUX とやり取りする
pix68k -r ~/x68k -0 HUMAN302.XDF --rs232c tcp:2324
nc 127.0.0.1 2324
# X68000 で: ECHO HELLO > AUX (nc に HELLO が出る)、COPY AUX CON (nc で打った文字が出る。Ctrl+Z で終わる)
```

作り (`src/x68k/scc.cpp`。詳しくは `src/x68k/scc.h` の先頭):

- ボーレート: SCC のクロック (PCLK) を 5MHz とし、WR12 / WR13 の時定数 TC と WR4 のクロックの倍率 M から 5000000 / (2 × M × (TC + 2)) bps。
  1 文字の時間はスタートビット、データビット (WR5 / WR3)、パリティ、ストップビット (WR4) から数える。WR14 は見ない。同期モードは作らない
- 送信: 送信バッファとシフトレジスタ。シフトレジスタが空いたらバッファのバイトを移し、そのときに送信バッファ空の割り込み要求を出す。
  送り終えたら相手に渡す。WR5 bit3 (送信の許可) と WR3 bit5 (Auto Enables のときの CTS) を見る
- 受信: 3 バイトの FIFO。あふれたときは最後のバイトを上書きし、そのバイトが FIFO の先頭に来たら RR1 のオーバーラン (特殊受信条件) にする
- 割り込み: 受信 (最初の 1 文字 / すべての文字 / 特殊受信条件だけ)、特殊受信条件 (ベクタの符号 111、チャネル B は 011)、送信、
  外部 / 状態 (WR15 で選んだ DCD / CTS が変わったら RR0 を止めて要求を出し、Reset Ext/Status Interrupts で開く)。
  最初の 1 文字のモードの要求は、その文字を読み出したときに下ろす。01 と 11 のモードでは、特殊受信条件のバイトを読んだら Error Reset まで次のバイトを見せない。
  10 (すべての文字) のモードの特殊受信条件の要求は、そのバイトを読んだら下ろす (RR1 のオーバーランのフラグは Error Reset まで残る)
- レジスタを選ぶポインタは 2 つのチャネルで 1 つ (実物と同じ)
- ブレーク、ゼロカウント、送信アンダーランの割り込み、パリティとフレーミングの誤り (TCP の相手からは来ない) は作らない
- チャネル B (マウス) の送信は、前と同じく書いたらすぐ送り終えたことにする。チャネル B の DCD / CTS は 0 のまま
- ステートには SCC の状態をすべて入れる (送っている途中のバイトと、送り終える時刻も。ステートの版 14)。TCP の接続はステートに入らない

確かめたこと:

- `scc_test`: レジスタのポインタ、ボーレートと 1 文字の時間、送信バッファとシフトレジスタ、受信の速さと RTS、オーバーランと特殊受信条件の
  ベクタ、FIFO を止める動き、外部 / 状態の割り込み、ステート (版 13 と 14)
- `x68k_test` の `RS-232C interrupt`: 68000 の命令で SCC を設定して 1 バイト送り、送ったバイトを返す相手から受け取って、レベル 5 の割り込み (ベクタ $5C) が入る
- ホスト版で Human68k 3.02 (RS-232C DRIVER 2.02 を組み込んだフロッピーディスク) を起動し、`ECHO PIX68K_OUT > AUX` の文字列が TCP の相手に届き、
  相手から送った `HELLO_FROM_HOST` と Ctrl+Z が `COPY AUX CON` で画面に出た
- ベアメタル版の TCP は、QEMU で待ち受けと接続、切断のログが出ることまで確かめた。AUX の文字の受け渡しは、QEMU の usb-net でホストからの
  接続が届かないことがあり (#117)、まだ確かめていない

参考にした資料: Zilog の Z8530 SCC のデータシートとユーザーマニュアル (受信割り込みのモード、特殊受信条件、外部 / 状態のラッチ、WR15 のリセット値)。

### MIDI ボード CZ-6BM1 (YM3802)

MIDI ボード (`src/x68k/ym3802.cpp`) は、YM3802 を載せた CZ-6BM1 を作ったもの。既定ではつながない。設定ファイルは `midi=on`、
ホスト版は `--midi` (`--no-midi` で設定ファイルの指定を打ち消す)。レジスタは $EAFA01-$EAFA0F の奇数番地、割り込みは IRQ4。

- 作ったもの: レジスタ R0-R3 と、RGR で選ぶ群 0-9 の R4-R7、送信 FIFO (16 バイト) と、TRR / TMR で決まる速さでの送信
  (31.25kbps で 1 バイト 320us)、汎用タイマ (GTR) と MIDI クロックタイマ (MTR)、送信 FIFO が空・汎用タイマ・MIDI クロックの割り込み
- 作っていないもの: MIDI IN (受信)、クリックカウンタ、シーケンサのカウンタ、FSK、2 枚目のボード ($EAFA10- はバスエラー)
- 資料から決められずに推測で決めたことがある (クロックを 1MHz としたこと、タイマの刻み、割り込みの要因の立ち方など)

送ったバイトは時刻つきで音を作るコア (ベアメタル版ではコア 3) に渡し、そこで MIDI の音源を鳴らして OPM と ADPCM の音に混ぜる。
音源は SoundFont 2 (SF2) を [TinySoundFont](https://github.com/schellingb/TinySoundFont) (MIT、`external/tinysoundfont`) で鳴らす。
SF2 のファイルはリポジトリに入れていない。GM の音色がそろったもの (GeneralUser GS など) を用意して、設定で指定する。

- ホスト版: `--midi-sf2 FILE` (`--midi` も付けたことになる)、`--midi-voices N` (同時に鳴らすボイスの数、4-256、既定 48)。
  設定ファイルでは `midi_sf2=`、`midi_voices=`
- ベアメタル版: `midi=on` と `midi_sf2=GeneralUser-GS.sf2` (`/` で始まらなければ `/pix68k` から)。音を出す設定 (`pix68k_sound` が
  `off` でない) でなければ読まない。標本を float に直して持つので、ファイルの大きさの 2 倍ほどのヒープを使い、読んだあとも
  減ったままになる。読む間に確保する量を数え、ヒープの空き (32MB を残す) を超えるなら、確保する前に読むのをやめて警告を出す
  (MIDI は鳴らさずに続ける)。
  起動を遅らせないよう、SF2 は X68000 を動かし始めてから (USB の装置を探し終えてから) 読む。Pi 3B+ の実機で、GeneralUser GS
  (30.8MB) に 6.1 秒 (ファイルを読むのに 5.7 秒、標本を float に直すのに 0.5 秒) かかり、ヒープを 66MB 使った。読む間は画面を合成するコア (コア 2) が画面を写し、ほかのコアを遅らせないよう、SD カードからは
  256KB 読むごとに同じ時間だけ休む。読み終えるまでに MIDI ボードが送ったバイトの音は鳴らない。その間に送ったプログラムチェンジ、
  コントロールチェンジ、GS リセットなどは覚えておき、読み終えたときに音源に送り直す (`src/x68k/midi_shadow.h`。GS のパートの
  設定のような、リセット以外のシステムエクスクルーシブは送り直さないので、その間に送ったものは反映されない)。
  メニュー、ネットワークの口、Ctrl + Alt + Delete は読み終えてから扱う
  `midi_out=uart` なら、SoundFont では鳴らさず、UART から 31.25kbps で出して実機の MIDI 音源を鳴らす (下の「実機の音源 (UART)」)。
  `midi_out=none` なら捨てる

速さ (`tests/bench/midi_bench.cpp`、48kHz、GeneralUser GS (30.8MB)、ボイスの数だけ鳴らし続けたとき):

| ボイスの数 | Pi 3B+ (Linux、1.4GHz) | 1 つのコアに占める割合 |
|---|---|---|
| 16 | 16.9 倍 | 5.9% |
| 32 | 8.2 倍 | 12.2% |
| 48 | 5.5 倍 | 18.3% |
| 64 | 4.1 倍 | 24.3% |

同じ Pi 3B+ で OPM 8 チャネルと ADPCM の合成 (`opm_bench`) は 1 つのコアの 9.5% なので、既定の 48 ボイスでもコア 3 で実時間に収まる。
GeneralUser GS では、メモリに読んだ SF2 から音源を作る (標本を float に直す) のに Pi 3B+ の Linux で 0.6 秒かかる。
ベアメタル版のログの `read in N ms: file N ms, samples N ms` の samples がこの時間で、その間はハードディスクのイメージの
チャンクの読み書きが待つ (TinySoundFont の中なので分けられない)。

ステートを読んだときは、音源で鳴っている音を止め、ステートを保存したときの音源の設定 (プログラム、コントロールチェンジ、
ピッチベンド、RPN、ランニングステータス) を送り直す。音源の中の状態はステートに入れず、MIDI ボードが送ったバイトから覚えた
設定をステートに入れる (CC 121 で消すものは TinySoundFont の動きに合わせた。`src/x68k/midi_shadow.h`)。
送り直して同じ状態に戻せるよう、音源の扱いを 3 つ TinySoundFont から変えている (`src/platform/sf2_synth.h`)。RPN は RPN ごとに
データを持つ (TinySoundFont はデータを 1 つだけ持ち、チューニングを今の値から計算するので、受けた順で結果が変わる)。
RPN の番号を CC 100 だけ、または CC 101 だけで選んだときは、そのあとのデータエントリを捨てる。リセットのあとの RPN の番号は
CC 101、CC 100 とも 127 (RPN ヌル) で、送らなかった側は 127 のままになる (実物の GS 音源と同じ。TinySoundFont は送らなかった側を
0 とみなしていた)。
SF2 にないプログラムを選んだときは、前の音色のままにせず、バンク 0 のプログラム 0 にする。
RIFF の大きさにファイル全体の大きさ (正しい値 + 8) を書いた SF2 も読む。

確かめたこと:

- `midi_test`: レジスタの読み書き、リセット、割り込みのベクタ、68000 のプログラムから送ったバイトの並びと間隔 (320us)、
  汎用タイマの割り込みの回数、送信 FIFO が空の割り込み、音を作るコアに渡したときと直接鳴らしたときで音が同じこと、ステート、
  試験用の SF2 (正弦波) で鳴らした音の高さ、ノートオフ、ドラム、GS リセット、SF2 を読むときの確保の上限 (小さいファイルから
  大きく確保する SF2)、ステートを読んだときと途中で音源をつないだときの設定の送り直し、乱数で作った MIDI のバイト列 3 万通りで、
  途中で覚えた設定を別の状態の音源に送り直したときと直接送ったときで、16 チャネルの設定が同じになること、
  壊れたステート (いろいろな値で埋めたもの) を MT-32 に送り直したとき、ピッチベンドの幅が 0〜24 に収まり、データエントリは
  送り直しの中で RPN 0 を選んでから送ったものだけになること
- `tools/qemu_human68k.sh` の `MIDI_SF2=file.sf2`: QEMU の raspi3b で MIDI ボードがつながり、コア 3 の音源が SF2 を読むこと。
  読み終えたログが、コア 1 が動き出したログより後に出ること
- Pi 3B+ の実機で、悪魔城ドラキュラ (GS 音源を選ぶ) の曲が MIDI ボードを通して GeneralUser GS で鳴り、HDMI から録った音の
  大きさの変化がホスト版と同じだった

レジスタの並び、アドレス、割り込みのレベルとベクタは、悪魔城ドラキュラが鳴る値にした。実機のボードでは確かめていない。

#### MT-32 / CM-32L (Munt)

`midi_out=mt32` なら、SoundFont の代わりに Roland MT-32 / CM-32L を [Munt](https://github.com/munt/munt) の libmt32emu
(LGPL 2.1 以降、`external/munt`) で鳴らす (`src/platform/mt32_synth.cpp`)。MT-32 の音源を選ぶゲームのためのもの。
ROM はリポジトリに入れていない。CONTROL の ROM (64KB か 128KB) と PCM の ROM (512KB か 1MB) を用意して、設定で指定する。
Munt が知っている ROM (SHA-1 で見分ける) で、組になるもの (MT-32 の CONTROL と MT-32 の PCM、CM-32L の CONTROL と CM-32L の PCM)
でなければ鳴らさない。

- ホスト版: `--midi-mt32-ctrl FILE` と `--midi-mt32-pcm FILE` (`--midi` と `--midi-out mt32` も付けたことになる)。
  設定ファイルでは `midi_out=mt32`、`midi_mt32_ctrl=`、`midi_mt32_pcm=`
- ベアメタル版: `midi=on`、`midi_out=mt32`、`midi_mt32_ctrl=MT32_CONTROL.ROM`、`midi_mt32_pcm=MT32_PCM.ROM` (`/` で始まらなければ
  `/pix68k` から)。SoundFont と同じく、起動のときはファイルの大きさとヒープの空きだけを確かめ、X68000 を動かし始めてから読む
  (256KB 読むごとに休む)。Munt が確保する量は、ROM の大きさから決まる上限 (CONTROL + PCM × 2 + 4MB。MT-32 で 5.1MB、
  CM-32L で 6.1MB) を超えない (`mt32_test` で、Circle のヒープの区分けを真似て確かめている)。読む前にこの量がヒープの空き
  (32MB を残す) に収まるかを確かめ、収まらなければ読まない。ファイルがない、大きさが違う、知らない ROM、組にならない ROM の
  ときも、ログに書いて MIDI は鳴らさずに続ける

Munt の出力は 48kHz で、そのまま OPM と ADPCM の音に混ぜる (Munt の `AnalogOutputMode_ACCURATE` は 48kHz を出すので、周波数の
変換は通さない)。ほかの周波数 (ホスト版の 44.1kHz など) では、Munt の SampleRateConverter で変換する (ホスト版だけ。ベアメタル版は
48kHz に決まっているので入れていない)。MIDI のメッセージは、届いた時刻 (音を作るコアの何フレーム目か) を付けて Munt の待ち行列に
入れる。鳴らす間は確保しない (待ち行列の SysEx の領域と、リバーブの領域は開くときに取る)。4096 バイトを超える SysEx と、
待ち行列があふれたメッセージは捨てる。

ステートを読んだときと、読み終えて音源をつないだときの設定の送り直しは、MT-32 では次のように変える (`src/x68k/midi_shadow.h`):

- GS リセットとバンクセレクトを送らない
- プログラムチェンジは、それまでにプログラムチェンジを受けたチャネルだけに送る (MT-32 はプログラムチェンジでパッチを
  読み直すので、ほかのチャネルにも送ると、SysEx で変えたパートの音色が変わる)
- ピッチベンドの幅 (RPN 0) は、最後のプログラムチェンジのあとに RPN 0 のデータエントリを受けたときだけ、その値を送る
  (MT-32 の幅の初めの値はパッチの値 (多くは 12) で、プログラムチェンジでパッチの値に戻り、CC 121 では変わらない。
  GS の初めの値の 2 と同じでも送る)。RPN 1、2 は送らない

`midiReset()` (ステートを読んだときに鳴っている音を止める) は、Munt の待ち行列に残っているメッセージを先に処理してから、
9 つのパートにオールノートオフを送る (残っていたノートオンが、あとで処理されて鳴り続けないように)。

分かっている違いは次のとおり。

- MT-32 の CC 121 はボリュームとパンを戻さないが、送り直すための記録は GS 音源と同じく戻す。CC 121 のあとにボリュームと
  パンを送っていない曲では、送り直しで違う値になる。ステートを読んだときは前のまま、新しく開いた音源 (ROM を読み終えて
  つないだとき、別の起動で保存したステートを読んだとき) では初めの値になる (CC 121 の前に音量を 25 にしていても 80 になる)
- Munt は CC 121 で RPN の選択を消さないが、送り直すための記録では消す。CC 121 のあとに RPN を選び直さずに送った
  データエントリは、送り直しに入らない
- リズムのパート (初めはチャネル 10) では、Munt はプログラムチェンジを受けないのでピッチベンドの幅が変わらないが、
  送り直すための記録はプログラムチェンジで幅の記録を消す。たとえば `B9 65 00 B9 64 00 B9 06 17` (幅 23) のあとに
  `C9 xx` を送ると、直接送ったときの幅は 23 のままだが、送り直したあとは 23 にならない (新しく開いた音源では初めの値の 12)。
  リズムのパートのチャネルは SysEx で変えられるので、記録の側ではどのチャネルがリズムのパートか分からない
- MT-32 は GM / GS / XG のリセットを受けないが、送り直すための記録ではすべてのチャネルを初めの状態に戻す
- 音色やパッチを書き換える SysEx は送り直さない (ステートを読んだとき、Munt の中の音色は前のまま。ROM を読み終える前に
  送った SysEx も反映されない)

速さ (`tests/bench/mt32_bench.cpp`、48kHz、パーシャル 32 個のうち平均 27 個が鳴る重さ):

| | Mac (Apple Silicon) | 1 つのコアに占める割合 |
|---|---|---|
| pix68k のやり方 (ACCURATE、48kHz をそのまま) | 63 倍 | 1.6% |
| Munt の既定 (COARSE、32kHz を 48kHz に変換) | 68 倍 | 1.5% |

Pi 3B+ では測っていない。OPM の合成 (`opm_bench`、8 チャネル) は同じ Mac で 1 秒分に 3.6ms、Pi 3B+ の Linux で 85ms
(24 倍) なので、同じ比で見積もると、Munt は Pi 3B+ で 2.6 倍ほど (1 つのコアの 38% ほど) になる。OPM と ADPCM (9.5%) と
合わせて、コア 3 の半分ほど (パーシャルが平均 27 個鳴っているとき。32 個すべてが鳴るときはもう少し重い)。見積もりなので、
Pi で `mt32_bench` (ビルドの手順はファイルの先頭) を動かして確かめる。mt32-pi (Pi 3 などで Munt を動かす MIDI 音源) が
Pi 3 で動いていることも、収まる見込みの根拠になる。

確かめたこと:

- `mt32_test` (ROM がなくても動く): ROM の大きさの判定、知らない ROM と組にならない ROM を断ること、0 で埋めた ROM (SHA-1 だけ
  本物に見せる) で開いて、確保する量が上限を超えないことと、鳴らす間に確保しないこと、長すぎる SysEx と待ち行列があふれたときに
  捨てること、MT-32 への送り直しに GS リセット、バンクセレクト、受けていないプログラムチェンジが入らないこと
- `mt32_test` に本物の ROM を渡したとき (`PIX68K_MT32_CTRL`、`PIX68K_MT32_PCM`、`PIX68K_CM32L_CTRL`、`PIX68K_CM32L_PCM`):
  音が出ること、DT1 で書いた 128 バイトを読み戻せること、送り直したあとのパートの設定 (パッチの一時領域) が、直接送ったときと
  同じになること (ピッチベンドの幅: 幅 2、幅を変えたあとのプログラムチェンジ、幅を変えたあとの CC 121、乱数で作った 100 通り)、
  44.1kHz への変換、待ち行列にノートオンが残っているときの `midiReset()` で音が止まること、CM-32L の ROM で鳴ること、
  組にならない ROM と、CONTROL と PCM を逆にしたものを断ること
- `munt_libc_test`: ベアメタル版で Munt に渡す数学の関数など (`baremetal/munt_libc.cpp`。Circle には libm がない) がホストの
  libm と同じ値になること (sin、cos、exp、log は相対誤差 1e-15 ほど)、Munt の表がホストの libm で作ったものと同じになること
- ホスト版で、悪魔城ドラキュラ (MT-32 を選ぶ) の曲が鳴り、`--midi-out none` のときと比べて、MIDI の音だけが足されていること
- 実機と QEMU では確かめていない

#### SC-55mkII (Nuked-SC55)

`midi_out=sc55` なら、Roland SC-55mkII を [Nuked-SC55](https://github.com/nukeykt/Nuked-SC55) (GPL 2 以降、`external/nuked-sc55`)
で鳴らす (`src/platform/sc55_synth.cpp`)。GS の音源を選ぶゲームのためのもの。Nuked-SC55 は SC-55mkII の 2 つのマイコン
(H8/532 と M37450) と PCM の LSI を、ROM のプログラムを動かしてエミュレートする。MIDI のバイトは本物と同じく M37450 の
UART に入れる (31.25kbps の速さに合わせて 1 バイトずつ)。

ROM は利用者が用意し、5 つのファイルを 1 つのディレクトリに置く。Nuked-SC55 の名前 (`rom1.bin` など) を先に探し、なければ
大きさで見分ける (MAME などの部品の番号の名前のままでよい。`.` で始まる名前は見ない)。

| ファイル | 部品 | 大きさ |
|---|---|---|
| `rom1.bin` | R15199858 (H8/532 の中の ROM) | 32KB |
| `rom2.bin` | R00233567 (H8/532 のプログラム) | 512KB |
| `rom_sm.bin` | R15199880 (M37450 の中の ROM) | 4KB |
| `waverom1.bin` | R15209359 (波形 16Mbit) | 2MB |
| `waverom2.bin` | R15279813 (波形 8Mbit) | 1MB |

- ホスト版: `--midi-sc55 DIR` (`--midi` と `--midi-out sc55` も付けたことになる)。設定ファイルでは `midi_out=sc55`、`midi_sc55=`
- ベアメタル版: `midi=on`、`midi_out=sc55`、`midi_sc55=SC55` (`/` で始まらなければ `/pix68k` から)。MT-32 と同じく、起動のときは
  ファイルの大きさとヒープの空きだけを確かめ、X68000 を動かし始めてから 256KB ずつ読む。確保するのは 6MB まで (波形の ROM、
  H8/532 の ROM と SRAM など。`sc55_test` で、Circle のヒープの区分けを真似て確かめている)。読む前にこの量がヒープの空きに
  収まるかを確かめる (Circle の new は足りないと全体を止めるため)。ファイルがない、大きさが違う、H8/532 のリセットのベクタが
  おかしい (SC-55mkII の ROM でない) ときは、ログに書いて MIDI は鳴らさずに続ける

SC-55mkII は電源を入れてから GS リセットを受けられるようになるまでに 4 秒ほどかかる (それより前に送った GS リセットは、
受けてからしばらく音が出なくなる)。そのため、ROM を読んだあとに 5 秒分を進めておく (`sc55_bench` で、Mac で 0.7 秒、Pi 5 の Linux で 2.3 秒。
ホスト版はその間、起動が待つ。ベアメタル版はコア 0 が進め、その間も 10ms ごとにディスクのイメージの読み書きをする)。

PCM の LSI の出力は 66207Hz (24MHz / 725 × 2)。窓をかけた sinc の FIR (16 タップ) で 48kHz などに変えて、OPM と ADPCM の音に混ぜる。
16 タップでは遷移帯が広く、24kHz から 33kHz の成分が少し減衰しただけで 15kHz から 24kHz に折り返す (SC-55 の出力のこの帯域の
成分は小さいので、聞いて分かるほどではない。タップを増やすと Pi 5 のコア 3 の負荷が増える)。
48kHz に変えるときの特性 (`sc55_test` で FIR の表から計算する):

| 入力の周波数 | 減衰 | 48kHz の出力で |
|---|---|---|
| 10kHz | 0.0dB | そのまま |
| 15kHz | 0.3dB | そのまま |
| 20kHz | 3.6dB | そのまま |
| 24kHz から 28kHz | 11.4dB 以上 | 20kHz から 24kHz に折り返す |
| 28kHz から 33.1kHz | 27.1dB 以上 | 15kHz から 20kHz に折り返す |
| 33.1kHz より上 (66207Hz の標本のイメージ) | 75.1dB 以上 | |

ステートを読んだときと、読み終えて音源をつないだときの設定の送り直しは、SoundFont と同じく GS の音源として行う。
`midiReset()` (ステートを読んだときに鳴っている音を止める) は、16 のチャネルにオールサウンドオフ (CC 120) を送り、途中まで
受けていたメッセージ (ランニングステータスとデータ) を送り直す。

重さ (`tests/bench/sc55_bench.cpp`、48kHz、16 チャネルで和音とドラムを鳴らし続ける。速さは作った音の長さ / かかった時間):

| | `-O2` | `-O3` | 1 つのコアに占める割合 (`-O3`) | 最も遅い 0.1 秒 (`-O3`) |
|---|---|---|---|---|
| Mac (Apple Silicon) | 5.8 倍 | 6.1 倍 | 17% | 3.1 倍 |
| Pi 5 (Linux) | 1.49 倍 | 1.70 倍 | 59% | 1.68 倍 |
| Pi 3B+ (Linux) | 0.40 倍 | 0.45 倍 | 224% | 0.44 倍 |

Nuked-SC55 のファイルは `-O3` でビルドする。Pi 3B+ では実時間の半分ほどしか出ないので、Pi 3 のビルドでは `midi_out=sc55` を
使わず、ログに書いて MIDI は鳴らさない。Pi 4 は測っていない (使えるようにしてあるが、間に合わずに途切れるかもしれない)。

ベアメタル版では、SC-55 の音はコア 3 が OPM と ADPCM の記録を処理し終えた合間に作る (`Sc55Synth::pump()`、
`Emulator::runSound()`)。OPM と ADPCM を先に処理するので、SC-55 が遅れても OPM と ADPCM の音は止まらず、SC-55 の音だけが
途切れる。そのため、MIDI のバイトには受けた時刻から 1536 フレーム (32ms) あとの時刻を付け、その時刻の音を作る前に UART に
入れる (SC-55 の音は OPM より 32ms 遅れて鳴る)。間に合わなかったフレームは無音にして数え、0.25 秒より遅れたら、出力の位置から
16ms 先までの音は作らずに飛ばす (先に余裕を作り、実時間より少し遅いときも飛ばすたびに 16ms 分は鳴るようにする)。
MIDI のバイトの待ち行列は 16384 バイトで、ステートを読んだときの設定の送り直し (最大 6549 バイト。UART に入れるには MIDI の
速さで 2.1 秒ほどかかる) と、その間に届くバイトが入る。ステートを続けて 3 回読み、1 回目から 3 回目までが 1 秒より短いと、
送り直しが待ち行列を超え、超えた分のバイトを落とす (設定が一部しか戻らない。2 回までなら続けても入る)。
音の合成をコア 3 で行わないとき (`sound_core=off` か、コア 3 が動かなかったとき) は使わない。
ホスト版と試験では、要るときにその場で作る (WAV に書く音は毎回同じになる)。

Pi 5 では、コア 3 が OPM と ADPCM と SC-55 (1 つのコアの 59%) を受け持つ。足りなくなったら、SC-55 だけを別のコア (たとえば
画面の合成のコア 2 や、USB とログのコア 0 の空き時間) に移す案がある (`pump()` は別のコアから呼べるように作ってある)。

確かめたこと:

- `sc55_test` (ROM がなくても動く): ROM のファイルの選び方 (名前、大きさ、`._` のファイル、同じ大きさが 2 つ)、リセットのベクタが
  おかしい ROM を断ること、途中で読めなくなったときに解放すること、でたらめな ROM で起動させても止まらないこと、確保する量が
  上限を超えないこと、設定の送り直しの最大の量 (6549 バイト)、FIR の通過域と折り返しの減衰 (上の表)
- `sc55_test` に本物の ROM を渡したとき (`PIX68K_SC55_ROM=ROM のディレクトリ`): 周波数、音が出て止まること、鳴らす間に確保
  しないこと、同期 (その場で作る) と非同期 (コア 3 の空き時間に作る) で同じ音になること (非同期は 32ms 遅れる)、非同期で
  MIDI を受けて音を足す側と `pump()` を別のスレッドにしても同じ音になること (`-fsanitize=thread` のビルドでも通る)、非同期で
  間に合わないときに無音を足し、あとで追いつくことと、大きく遅れたら飛ばすこと、設定の送り直しの最大の量を落とさずに UART に
  入れること (量が待ち行列の半分に収まることは ROM なしで確かめる)、送り直しを 2 回続けても落とさず、3 回続けると落とすこと、
  周波数の変換の標本の番号が 2^31 (9 時間) を超えたら引き戻し、同じ音を作り続けること (同期と非同期。2^31 で引き戻すので
  2^32 には届かない)、`midiReset()` で音が止まることと、そのあとの
  ランニングステータスで鳴ること、44.1kHz、2 つ目は開けないこと。ASan / UBSan のビルドでも通る (Nuked-SC55 の負の数の左シフト
  だけは、Munt と同じく調べない)
- ホスト版で、悪魔城ドラキュラ (GS を選ぶ) の曲が鳴り、`--midi-out none` のときと比べて、GS を選ぶまでは WAV が同じで、
  選んだあとに MIDI の音が足されていること
- QEMU (raspi3b) の Pi 3 のビルドで、`midi_out=sc55` を使わないとログに出し、Human68k が立ち上がること
- 実機 (Pi 5) では確かめていない

#### 実機の音源 (UART)

`midi_out=uart` なら、MIDI ボードが送ったバイトを Pi の UART から 31.25kbps で出し、実物の MT-32 や SC-55 などを鳴らす。
音は Pi からは出ない。設定は次の 3 つ (ベアメタル版):

- `midi_uart=0`: 使う UART (Circle の `CSerialDevice` の番号)。既定の 0 は、どの機種でも GPIO 14 (ヘッダの 8 番ピン)
- `midi_uart_family=gs`: つないだ音源の種類。`gs` (GS / GM の音源、既定) か `mt32` (MT-32 / CM-32L)。ステートを読んだときの
  設定の送り直し (`src/x68k/midi_shadow.h`) と、鳴っている音の止め方を決める。実機の音源が何かは Pi からは分からないので、設定で選ぶ
- `midi=on` と `midi_out=uart`

使える UART と TXD のピン (GND は 6 番ピンなど):

| 機種 | `midi_uart=` | TXD | ログ |
|---|---|---|---|
| Pi 3 | 0 だけ | GPIO 14 (8 番ピン) | ログと同じ UART なので、ログは UART に出さなくなる |
| Pi 4 / Pi 400 | 0 | GPIO 14 (8 番ピン) | 同上 |
| | 2 / 3 / 4 / 5 | GPIO 0 (27 番ピン) / GPIO 4 (7 番ピン) / GPIO 8 (24 番ピン) / GPIO 12 (32 番ピン) | ログは GPIO 14 に出たまま |
| Pi 5 | 0 | GPIO 14 (8 番ピン) | ログは UART の端子 (HDMI の間の 3 ピン) に出たまま |
| | 1 / 2 / 3 / 4 | GPIO 0 (27 番ピン) / GPIO 4 (7 番ピン) / GPIO 8 (24 番ピン) / GPIO 12 (32 番ピン) | 同上 |
| | 10 | UART の端子 | ログと同じ UART なので、ログは UART に出さなくなる |

- Pi 3 は、Circle に PL011 のドライバしかなく、mini UART も TXD は GPIO 14 なので、ログと分けられない。ログは `syslog=` か
  ネットワークの口の `/log` で読む (Pico によるログの中継も止まる)
- Pi 4 の 2〜5 と Pi 5 の 0〜4 は、RXD のピン (TXD の次の番号の GPIO) も UART に切り替える
- ログと同じ UART を使うときは、`midi_out=uart: ... the log no longer goes to the UART` を書いたあと UART を 31.25kbps に
  切り替える。それまでの起動のログ (115200bps) も同じピンから出るので、音源はそれを壊れたバイトとして受ける。そのため、
  電源を入れたときのリセットで、まず 16 のチャネルの音を止めるバイトを送る (下)
- 速さ: PL011 のクロック (Pi 3 / 4 は既定 48MHz、Pi 5 の RP1 は 50MHz、Pi 5 の UART の端子は 44MHz、古いファームウェアの 3MHz)
  はどれも 31250 × 16 で割り切れるので、分周の端数は出ない (分周は 96、100、88、6)。Pi 3 の `core_freq` は mini UART の
  速さだけに関係し、PL011 には関係しない。config.txt に足す設定はない。ログの
  `MIDI goes out of UART n (...) at N bps (UART clock N Hz, divisor N + N/64)` は、ファームウェアが返すクロック (MHz に丸めた値) から
  計算した速さで、測った値ではない (`init_uart_clock=` を変えたときの確かめに使う。1% より違えば警告を出す)
- MIDI の端子 (DIN) につなぐには、MIDI の規格の送信の回路 (5V の電流ループ) が別に要る

バイトを UART に送るのは、音をコア 3 で作るときはコア 3 (記録を処理するたびと、空いたとき)、`sound_core=off` などで
コア 1 が音を作るときはコア 0 の主ループ (`platform/uart_midi.h`、`CKernel::ServiceMidiUart()`)。
UART の送信 FIFO にいくつ残っているかを時刻から計算し (1 バイト 320us)、12 バイトまでしか入れないので、UART に書くときに待たない。
入らなかったバイトは 16384 バイトのリングバッファに溜める (ステートを読んだときの送り直しは最大 6.4KB ほどで、送るのに 2 秒ほどかかる)。
リングバッファがあふれたら、そのバイトは捨てて数え、次のステータスバイトまでデータバイトも捨てる。待たない。
システムエクスクルーシブの途中で捨てたときは、その $F7 も捨てる (中身の欠けたものを閉じて送らない。音源には閉じていない
システムエクスクルーシブが届き、次のステータスバイトで終わる)。捨てている間に満杯のままステータスバイトも捨てたときは、
それが音源に届いていないので、ステータスバイトが実際にリングバッファに入るまで $F7 を捨て続ける。
10 秒ごとのログに `midi: uart: N bytes sent, N dropped, N flushed, N queued at most, N silenced` を出す
(dropped はリングバッファがあふれて捨てた数、flushed は再起動の前に間に合わずに捨てた数)。
送るタイミングのずれ: コア 3 は、未送信のバイトがある間は wfe で待たずに FIFO の空きを確かめ続けるので、FIFO の 12 バイト (3.8ms) が
空になる前に次を入れられる (未送信のバイトがなくなれば、これまでどおり記録が来るまで wfe で待つ)。X68000 が送った時刻からは、コア 3 が
記録を処理するまでの間 (1 フレームほどまで) 遅れる。コア 0 が送るときは、主ループが SD カードを読み書きする間や、
ログを UART (115200bps) に書く間 (Pi 4 の `midi_uart=2`〜`5` など) に数十 ms 止まることがあり、その間は送信が途切れる
(`sound_core=on` で使うのがよい)。

鳴っている音の止め方: X68000 のリセット、ステートを読んだとき、メニューを開いて X68000 を止めたとき、再起動の前に
(止めたときと再起動の前は、頼んだときに溜まっていたバイトを送り終えてから。メニューをすぐ閉じて再開しても、再開したあとの
バイトは止めるバイトのあとに送る)、
16 のチャネルに `gs` ではオールサウンドオフ (CC 120) とオールノートオフ (CC 123) を、`mt32` ではホールドペダルを離す
(CC 64 = 0) とオールノートオフを送る (MT-32 は CC 120 を受けず、ホールドペダルを踏んだままではオールノートオフで音が
止まらないため。`mt32` ではホールドペダルの状態も変わる)。システムエクスクルーシブの途中なら先に $F7 で閉じ、残りのデータは
次のステータスのバイトまで捨てる。チャネルメッセージの途中なら、止めたあとにそのステータスと受けたデータを送り直す
(ランニングステータスを変えないため)。前に止めてからチャネルメッセージを送っていなければ、何も送らない。
再起動の前は、止めるバイトを UART が送り終えるまで (FIFO の分も含めて) 300ms まで待つ。300ms に送れるのは 937 バイトなので、
止めるバイト (最大 84 バイト) を除いて 850 バイトほどより多く溜まっていれば (ステートを読んだ直後の送り直しなど)、送る側が
溜まったバイトを捨てて、止めるバイトを先に送る (それより少なければ全部送ってから止める)。捨てたときは、途中まで送った
チャネルメッセージは送り直さず、システムエクスクルーシブは $F7 で閉じる。
止めるバイトを送り終えたかは、頼みごとに付けた番号で見る (送る側が止めるバイトを作る前に「終わった」と読まないように)。

ホスト版では、UART の代わりにファイルに書ける (試験用): `--midi --midi-out uart --midi-dump FILE` で、ベアメタル版が UART に
送るのと同じバイト列 (止めるバイトを差し込んだもの) を書く (`--midi-uart-family gs|mt32`)。`--midi-out uart` 以外で
`--midi-dump FILE` を付けると、音源に渡したバイト列を書く。

mt32-pi (Circle で Munt / FluidSynth を動かす Pi) につなぐときの例: pix68k の TXD (上の表) を mt32-pi の RXD (GPIO 15、10 番ピン) に、
GND どうしをつなぐ (どちらも 3.3V なので直結できる)。mt32-pi の側は次のとおり (mt32-pi のソースで確かめた):

- `mt32-pi.cfg` の `[midi]` の `gpio_baud_rate = 31250` (既定のまま)
- `cmdline.txt` に `logdev=ttyS1` を書かない (書くと UART をログに使い、GPIO の MIDI を受けない)
- USB の MIDI インタフェースや USB シリアルの装置をつながない (つなぐとそちらに切り替わり、GPIO の MIDI を受けなくなる)
- config.txt に UART のための設定は要らない (Circle が PL011 を GPIO 14 / 15 に割り当てる)
- 鳴らす音源は `[system]` の `default_synth` (`mt32` か `soundfont`) で選ぶ。pix68k の `midi_uart_family=` もそれに合わせる

確かめたこと:

- `uart_midi_test`: 9000 バイトを一度に受けても、Pi の UART を真似たもの (FIFO 16 バイト、1 バイト 320us) があふれず、
  1 バイトも落とさず順に送ること。0.1ms / 1ms ごとに送る処理を呼べば、送信が途切れず 9000 × 320us で送り終えること。3ms ごとでもあふれないこと。
  MIDI ボードより少し遅い速さで受け続け、ときどき 19ms 呼ばれなくても追いつくこと。リングがあふれたときの捨て方と数。
  リセットのときの止めるバイト (メッセージの途中、システムエクスクルーシブの途中、`mt32`、送らなくてよいとき)、
  メニューと再起動のときの順番 (溜まったバイトを送ってから音を止めること。頼んで 100ms 後に再開して送り続けても、頼んだときの
  3000 バイトのすぐあとに止め、再開後のバイトはそのあとに送ること)、送るものが残っている間は `idleWork()` が true を返すこと、
  ステータスのないデータを捨てること、書き手と読み手が別のスレッドのとき。
  再起動の前に 3000 / 6400 バイト溜まっていても、溜まったバイトを捨てて 300ms 以内に止めるバイトを出し終えること (100 バイトなら捨てない)。
  チャネルメッセージ、システムエクスクルーシブ、システムコモンの途中から捨てたときの閉じ方。
  別のスレッドで送り続ける間に 3000 回頼み、「終わった」と読んだときには必ず止めるバイトを書き終えていること
  (終わったことを書く前に見せるように変えると落ちることも確かめた)。送る側が頼みの番号を読んでからリングの書き込み位置を
  読むまでの間に、ノートオンと頼みが入っても、ノートオンを止めるバイトのあとに送らないこと (読む順を逆にすると落ちることも
  確かめた)。ASan / UBSan と TSan のビルドで 2 万回ずつ 10 回回しても通る。
  リングの位置が 2^31、2^32、2^63 を過ぎたあとに頼んでも順番が崩れないこと (位置は 64 ビット)。期限つきで頼んだあとに入った
  バイトは捨てず、ステータスから送り始めること。システムエクスクルーシブのデータとステータスを続けて捨てたあとの $F7 を捨てること
- `config_test` (`midi_uart=`、`midi_uart_family=`)、`host_midi_uart` (電源を入れたときに 80 バイトの止めるバイトを書く)
- ホスト版で悪魔城ドラキュラ (GS を選ぶ) を 6000 フレーム動かし、`--midi-out uart --midi-dump` のバイト列が、
  音源に渡したバイト列 (`--midi-out none --midi-dump`、7164 バイト) の前に電源を入れたときの止めるバイト (80 バイト) を足したものと
  同じになること (`--midi-uart-family mt32` でも)
- QEMU (raspi3b) の Pi 3 のビルドで、`-serial` に、ログを止めたあと 31.25kbps に切り替えて、止めるバイトと設定の送り直し
  (`midi_shadow.h` の `emit()`) のバイトが出ること。音をコア 3 で作るとき (コア 3 が送る) と `sound_core=off` (コア 0 が送る、
  `midi_uart_family=mt32`) の両方。QEMU の UART は速さを真似ないので、速さの配分は `uart_midi_test` で見ている
- 実機では確かめていない (オシロも音源もない)

## 画面の合成

テキスト、グラフィック、スプライト / BG の重ね合わせは `src/x68k/render.cpp` で 1 ラスタずつ行う。

根拠は「Inside X68000」(桑野雅彦、ソフトバンク、1992 年) の画面制御の章。グラフィックは、本のコラム
「グラフィックページ間プライオリティ制御のからくり」のとおり、4 ビットずつの 4 つのブロックを R1 ($E82500) の
GP0〜GP3 で優先順位に割り当て、色モードで組み合わせる作りにしている (標準でない設定でも、その作りのとおりに出る)。
本に書かれていない動きは、ほかの資料とゲームの画面、書き直す前の版の出力との比較から決めた。決めたことと理由は
`render.cpp` の先頭の注釈にまとめてある。実機で測ったデータはない。

### 透明なドットと重なり

- テキストとスプライト + BG はパレットが 1 つなので、パレットを引く前に 1 つの色コードにまとめる (優先順位の高いほうの
  色コードが 0 でなければそれ、0 なら低いほう)。スプライト + BG は、パターンのドットが 0 の所が色コード 0
  (BG のブロックやスプライトの色コードの上位 4 ビットが 0 でなくても、上位 4 ビットだけの色コードにはしない)
- まとめた色コードでテキストパレットを引く。その色コードを出した画面がグラフィックより手前なら、色が $0000 で
  なければその色、$0000 ならグラフィックの色を出す。グラフィックより奥なら、グラフィックの色が $0000 でなければ
  グラフィックの色、$0000 ならテキストパレットを引いた色を出す
- 色が $0000 のドットが透明。グラフィックは色コードによらない (グラフィックパレット 0 が $0000 でなければ、
  色コード 0 の所も透明でない)
- どの画面も透明な所には、テキストパレット 0 の色が出る
- テキストもスプライトもグラフィックより手前にあるとき、テキストパレット 0 が $0000 でなければグラフィックは見えない

色が $0000 で透明になることは Seafy 氏の「CRTC の設定 その他」(1993 年) による。テキストパレット 0 の扱いは、
悪魔城ドラキュラのパレットの使い方からの推測 (注釈に書いた)。

### 特殊プライオリティと半透明 (ビデオコントローラ R2、$E82600 の上位バイト)

| ビット | 名前 | 意味 | pix68k |
|---|---|---|---|
| 15 | Ys | ビデオカット | 何もしない (ビデオ画像の入力がない) |
| 14 | AH | テキストパレット 0 との半透明 | ほかのビットによらず、領域のドットをテキストパレット 0 の色と混ぜる |
| 13 | VHT | ビデオ画像との半透明 | 何もしない (ビデオ画像の入力がない) |
| 12 | EXON | 特殊プライオリティ / 半透明を有効にする | bit10 も 1 のときに働く |
| 11 | H/P | 0 = 特殊プライオリティ、1 = 半透明 | |
| 10 | B/P | 1 = ベースページの最下位ビットで領域を指定する | 0 のとき (本では未定義) は、bit12 の機能を行わない |
| 9 | G/G | 半透明: セカンドページと | |
| 8 | G/T | 半透明: テキスト / スプライトと | |

ビットの名前は Data Crystal の X68k:IOMAP のもの。

- ベースページは、グラフィックの一番手前のページ (16 色なら GD0、256 色なら GD1:GD0、65536 色と実画面 1024x1024 は
  画面全体)。そのデータの最下位ビットが 1 のドットが領域。機能が働いている間、ベースページは最下位ビットを 0 にした
  色コードで表示する (特殊プライオリティでも同じとした)
- 混ぜ方は本のとおり: RGB の 5 ビットずつを足して 1 ビット右にずらす (端数は捨てる)。輝度ビットは相手のもの
- 半透明: G/G ならセカンドページ (16 色は GD1、256 色は奥のページ) の色と混ぜる。セカンドページの色コードも
  最下位ビットを無視し、グラフィックパレットの奇数番の色を使う (Inside X68000 p.209 図 30)。G/T なら、
  テキスト / スプライトがグラフィックより奥のときに、その色と混ぜる。両方ならセカンドページ、テキスト / スプライトの順に混ぜる。
  グラフィックより手前のテキスト / スプライトは、混ぜた結果の上に重なる
- 特殊プライオリティ: 領域のドットを、テキストやスプライトより手前に出す

本に書かれていない場合の扱い (最下位ビットを 0 にすると 0 になるドットなど) は
`render.cpp` の先頭の注釈にある。

画面の合成を別のコアで行うとき (ベアメタル版のコア 2、`--render-thread`) も、レジスタへの書き込みは記録を通して写しに
届くので、同じ規則で描く。試験は `video_test` (本の説明から作った期待値と、注釈の決まり)。

## ベアメタル版 (Raspberry Pi)

低レベル部分 (起動、USB、HDMI、SD カード、割り込み) は [Circle](https://github.com/rsta2/circle) (Step51.1.1、`external/circle` の submodule) を使う。

```sh
git submodule update --init
brew install aarch64-elf-gcc qemu mtools
tools/build_baremetal.sh 3 --qemu   # QEMU 用の Pi 3 版 → build/baremetal-raspi3-qemu/app/kernel8.img
tools/qemu_smoke.sh                 # QEMU raspi3b で起動し、SD カード・USB 入力・マルチコアの動作をログで確かめる
tools/qemu_human68k.sh              # QEMU raspi3b で Human68k を起動し、DIR を打って一覧が出るか、USB マウスの動きが届くかを確かめる (ROM がなければ飛ばす)
RENDER_CORE=off tools/qemu_human68k.sh  # 同じことを、画面の合成をコア 1 で行う設定 (render_core=off) で行う
SOUND_CORE=off tools/qemu_human68k.sh   # 同じことを、音の合成をコア 1 で行う設定 (sound_core=off) で行う
FAIL_CORE=2 tools/qemu_human68k.sh  # 同じことを、コア 2 以降が起動しなかったことにして (pix68k_fail_core=2) 行う
FAIL_CORE=3 tools/qemu_human68k.sh  # 同じことを、コア 3 が起動しなかったことにして (pix68k_fail_core=3) 行う
SOUND_OUT=off tools/qemu_human68k.sh  # 同じことを、音を出さない設定 (pix68k_sound=off。コア 3 を使わない) で行う
BOOT=hd tools/qemu_human68k.sh      # 同じことを、起動ディスクから作った SASI のイメージ (hd0=) で行う
WRITEBACK=1 tools/qemu_human68k.sh  # DIR のあとにファイルを作り、イメージのファイルに書き戻されたか (SD カードのイメージの中と、もう一度起動して TYPE) を確かめる
BOOT=hd STREAM=1 WRITEBACK=1 tools/qemu_human68k.sh  # 同じことを、SASI のイメージを全体を読まずにチャンクだけ読む設定 (pix68k_stream_min=0) で行う
WRITEBACK=1 REBOOTKEY=1 tools/qemu_human68k.sh  # ファイルを作ったあと書き戻しを待たずに Ctrl + Alt + Delete を送り、書き戻してから再起動するかを確かめる
MENU=1 tools/qemu_human68k.sh       # DIR のあとに設定メニューを開き、設定の保存、ステートの保存と読み込み、FD0 の入れ替え、リセット、Restart を確かめる
WFE=0 tools/qemu_human68k.sh       # 同じことを、待つ間を wfe で眠らせずに空回りで待つ設定 (pix68k_wfe=0) で行う
HOSTNET=1 tools/qemu_human68k.sh    # ネットワークの口 (net=on) を動かし、DHCP、curl でのファイルの読み書き、/log、/screen.ppm、/type、/key、syslog、/reboot を確かめる
tools/build_baremetal.sh 3          # 実機の Pi 3 版 → build/baremetal-raspi3/app/kernel8.img
tools/build_baremetal.sh 4          # 実機の Pi 4 / Pi 400 版 → build/baremetal-raspi4/app/kernel8-rpi4.img
tools/build_baremetal.sh 5          # 実機の Pi 5 版 → build/baremetal-raspi5/app/kernel_2712.img
```

Linux では、Ubuntu のパッケージの aarch64-linux-gnu-gcc でビルドできる (CI の `baremetal` の job で使っている。実機では確かめていない。
QEMU の `tools/qemu_smoke.sh` は通る)。接頭辞を `PREFIX64` で渡す。

```sh
sudo apt install gcc-aarch64-linux-gnu g++-aarch64-linux-gnu qemu-system-arm mtools rsync
PREFIX64=aarch64-linux-gnu- tools/build_baremetal.sh 3 --qemu
tools/qemu_smoke.sh
```

`tools/build_baremetal.sh` は、コンパイラが Linux 向け (`gcc -dumpmachine` の答えに `-linux-` がある) なら、`Config.mk` に
`-mno-outline-atomics` を足す。Linux 向けの GCC は、LSE のない CPU (Pi 3、Pi 4) ではアトミックな操作を libgcc の関数の呼び出しにし、
その関数が `__getauxval()` を使うので、足さないと Pi 3 / Pi 4 版がリンクできない (Circle のライブラリに渡すため。アプリの部分には、
どのコンパイラでも `baremetal/Makefile` が同じオプションを付けていて、重なっても問題ない)。aarch64-elf-gcc では `Config.mk` に足さず、
Circle のライブラリのビルドは変わらない。

カーネルの大きさには上限がある。Circle は、.bss まで含めたカーネルの終わり (リンカの `_end`) が `0x80000 + KERNEL_MAX_SIZE`
を超えていると、起動の直後に何も表示せずに止まる。Circle の既定は 2MB で、Pi 3 / Pi 4 / Pi 5 版は 68030 / 68060 の命令表 (512KB ずつ)
などで 2MB を超えた (Pi 4 / Pi 5 版の `_end` は 3MB 余り。今の値はビルドの最後に出る) ので、`tools/build_baremetal.sh` で 8MB に
している (Circle の `configure --kernel-max-size 8` で渡す。`Config.mk` に `-DKERNEL_MAX_SIZE=0x800000` が入り、Circle のライブラリと
アプリの C++ とアセンブラのすべてに渡る。Circle のソースは変えない)。そのぶん、スタックとヒープの始まりが 6MB 上に動く。
`tools/build_baremetal.sh` はビルドの最後に `_end` と上限を比べ、超えていればカーネルのイメージを消して失敗する (CI の baremetal
の job でも同じ)。ELF がない、2 つ以上ある、`nm` が失敗した、`_end` がないときも、確かめられないのでイメージを消して失敗する。
前のビルドのイメージはビルドの始めに消すので、途中のどこで失敗しても (Circle の設定の確かめ、ライブラリ、アプリ)、古いイメージは残らない。
成功したときは `_end 0x...... (上限 0x880000、残り .... KB)` の形で残りを出す。

`memcpy` / `memset` とアトミックな操作 (ベアメタル版の速さ): Circle は `-ffreestanding` でビルドするので、そのままでは GCC が
`memcpy` などを組み込み関数として扱わず、大きさが定数の 4 バイトや 8 バイトの写しも Circle の関数の呼び出しになる。Circle の
AArch64 の `memcpy()` (`lib/util_fast.S`) は、128 バイト未満のときと、どちらかの番地が 8 バイトにそろっていないときは 1 バイトずつ写す。
`baremetal/Makefile` は次のことを行う (Circle のライブラリと addon のビルドは変えない)。

- `baremetal/builtin_mem.h` を pix68k と同梱のライブラリ (Munt、Nuked-SC55、TinySoundFont) のすべてのソースに `-include` で読ませ、
  `memcpy` / `memset` / `memmove` / `memcmp` / `strlen` を組み込み関数として扱わせる。大きさが定数の小さいものは、その場のロードと
  ストアになる。`-fbuiltin` は使わない (`printf` が `putchar` の呼び出しに書き換えられてリンクできない。数学の関数も組み込み関数として
  扱われるようになるが、結果が変わるかどうかは確かめていない)
- 大きさが変数のものは関数の呼び出しのまま残るので、`memcpy()` と `memset()` は `baremetal/mem_fast.cpp` のものを使う
  (リンクのときに Circle のものより先に使われる)。長さに関係なく 8 バイトずつ (dest と src の番地の下位ビットが 4 バイトだけ
  ずれていれば 4 バイトずつ) 写す。2 バイト以上の読み書きは、その大きさにそろった番地だけで行う (フレームバッファは Device の
  メモリで、そろっていない読み書きは例外になる。Circle のものと同じ)。128 バイト以上の `memcpy()` は Circle と同じ 32 バイトずつのループ。
  `memcpy()` は 1 回分 (多くて 32 バイト) を全部読んでから書き、番地の小さいほうの回から順に進む (Circle の `memmove()` が、dest が src より
  小さくて重なるときに `memcpy()` を呼ぶため)。`memmove()` と `memcmp()` は Circle のまま (呼び出しが少ない)。ホストでは `mem_fast_test` が同じソースを試験する
- 組み込み関数の `memcpy` などは引数がヌルでないものとして扱われ、写したあとのヌルの検査を GCC が消すことがあるので、
  `-fno-delete-null-pointer-checks` を付ける
- Pi 3 / Pi 4 (LSE のない Cortex-A53 / A72) 向けでは、GCC がアトミックな操作 (`__atomic_exchange_n` など) を libgcc の関数
  (`__aarch64_cas4_acq_rel` など) の呼び出しにするので、`-mno-outline-atomics` でその場の命令 (LL/SC) にする

オブジェクトファイルの中の呼び出しの数は `tools/baremetal_memcalls.py build/baremetal-raspi5/app` で数えられる (`--detail` でファイルごと)。
Pi 5 版のアプリの部分で、`memcpy` / `memset` / `memmove` / `memcmp` / `strlen` の呼び出しは 704 か所から 344 か所になり、大きさが定数で
128 バイト未満のものは 301 か所から 1 か所になった (残る 1 か所は HTTP の処理の中の、長さが 0 になる分岐)。
Pi 3 / Pi 4 版のカーネルのアトミックの関数の呼び出しは 53 か所から 2 か所になった (残りは Circle と libsupc++ の中。
アプリの部分は、同じ道具の `atomic` の列で 0 か所)。
`tools/build_baremetal.sh` は、ビルドの最後にカーネルの逆アセンブルを調べ (`tools/baremetal_hot_mem.sh`)、次のどれかがあれば失敗する:
名前に `m68k::` か `x68k::` がある関数の中の、大きさが 128 バイト未満の定数の `memcpy()` の呼び出し。`memcpy()` / `memset()` の中の、
ほかの関数の呼び出し、NEON / 浮動小数点のレジスタ、スタックの使用。Circle の `util_fast.o` のリンク。
Pi 5 の実機 (PR #91 のコメントの測定) では、テキスト画面が主の場面で、コア 2 が 1 フレームを合成する時間が 2162us から 1351us になった。
ゲームの場面 (悪魔城ドラキュラ) のコア 2 と、コア 1 (CPU のコアの `memcpy` は PR #84 でなくなっている)、コア 3 は変わらなかった。Pi 3 / Pi 4 の実機では測っていない。

実機で動かすには、SD カードの FAT のパーティションに Raspberry Pi のファームウェア (Circle の `boot/` で取得できる) とカーネルのイメージを置く。
`config.txt` は Circle の `boot/config64.txt` をもとにする (`arm_64bit=1`。Pi 4 と Pi 400 は同じカーネル `kernel8-rpi4.img` で、
`[pi4]` の節で選ぶ)。`[pi4]` の節の `armstub=armstub8-rpi4.bin` の行は消す。この armstub は FIQ を使うときだけ要り、pix68k は使わない
(消さずに使うなら、Circle で `make armstub64` を実行してできたファイルを置く。Pi 4 / Pi 400 での起動はまだ実機で確かめていない)。
Pi 5 では、`[pi5]` の節に `framebuffer_depth=32` と `framebuffer_ignore_alpha=1` を必ず書く (`config64.txt` ではコメントになっている)。
pix68k は 32 ビットのフレームバッファを使うので、この 2 行がないと Circle が画面を作れず、何も表示せずに止まる
(ネットワークも出ない。UART には `pix68k: cannot create the 32-bit framebuffer; ...` の 1 行だけを出す)。
Circle のソースや文書に理由が書いてあるわけではなく、Pi 5 8GB の実機で確かめた結果。2 行のどちらか片方で足りるかは確かめていない。

```
[pi5]
kernel=kernel_2712.img
framebuffer_depth=32
framebuffer_ignore_alpha=1
```

UART のログ (115200bps) は、Pi 3 と Pi 4 / Pi 400 では GPIO 14/15、Pi 5 では HDMI 端子の間にある 3 ピンの UART 端子に出る。
USB は、Pi 3 は SoC の DWHCI、Pi 4 / Pi 400 は PCIe の先の VL805 (xHCI)、Pi 5 は RP1 の xHCI を Circle が使う。
キーボード、マウス、ゲームパッドはどの機種でも Circle の同じドライバ (`ukbd1`〜、`mouse1`、`upad1`〜) から受け取る。
boot パーティションの `/pix68k/` (ROM はルートでもよい) に次のファイルを置くと、X68000 をコア 1 で実時間で動かし、画面 (32 ビットのフレームバッファの真ん中) と USB キーボードをつなぐ。
画面の合成はコア 2 で行う (コア 1 は VRAM などへの書き込みとラスタの区切りをリングに入れ、コア 2 はそれを Video の写しに当てながら 1 ラスタずつ描く。
コア 1 だけで合成したときと同じ画面になる。リングが満杯か、コア 2 が 2 フレーム以上遅れたらコア 1 が待ち、フレームは飛ばさない)。
音 (OPM と ADPCM) の合成はコア 3 で行う (コア 1 は OPM と ADPCM への書き込みと進めたクロック数をリングに入れ、コア 3 がそれを当てて音を作る。
OPM のタイマや割り込み、ADPCM の転送の要求など CPU から見える状態はコア 1 が計算する。コア 1 だけで作ったときと同じ音になる)。
コア 2 / 3 が起動しなければ、その仕事はコア 1 が行う。コア 1 が起動しなければ止まる。
コア 0 は USB、SD カード、ログ、画面への転送、音の出力を受け持つ。

CZ-6BM1 (YM3802)」を参照)。`net=on` で Pi の Ethernet に HTTP のサーバと syslog の送信を動かす (`net_ip=`、`net_token=`、`syslog=` など。下の「ネットワークの口」を参照)。`scsi_ex=on` で外付け SCSI ボードをつなぎ (ROM は `SCSIEXROM.DAT`。`scsi_ex_rom=` SCSI。イメージは使うチャンクだけを読む。書き込みはファイルに書き戻す。上の「増設メモリ、外付け SCSI ボード、CD-ROM」と「ディスクの書き戻しと大きなイメージ」を参照)。`write_back=off` でディスクの書き戻しをやめ、`write_protect=fd1,sc0` で書き込み禁止にするディスクを並べる。`keyboard=` でキーボードの種類を選ぶ (既定の `auto` ではつないだキーボードの VID:PID から決める。`usb` は普通の USB キーボード、`pi400us` / `pi400jp` は Pi 400 の英語版 / 日本語版。下の「Pi 400 のキーボード」を参照)。`hat=0` / `hat=1` でゲームパッドのハットの値の範囲を 0-7 / 1-8 に固定する (既定の `auto` | `SRAM.DAT`、`SRAM.BAK` | SRAM。起動時に読み、書き換えられたら書き戻す (5 秒に 1 回まで)。電源投入のたびに、SRAM に書かれたメインメモリの容量 ($ED0008) をエミュレータのメモリの容量に合わせる (XEiJ の説明書 parameter.htm の modifymemorysize と同じ働き。`pix68k.cfg` の `sram_memsize=keep` で止められる)。書いている途中で電源が切れても前の内容が残るよう、2 つのファイルに世代番号と CRC を付けて交互に書き、正しくて新しいほうを読む (形式は `src/x68k/sram_file.h`。先頭の 16KB は SRAM そのもので、16KB だけの SRAM.DAT も読める) |

音は HDMI に出す。`cmdline.txt` の `pix68k_sound=pwm` で PWM (Pi 3 と Pi 4B は 3.5mm のジャック、Pi 5 は GPIO 12 / 13。Pi 400 にはジャックがない)、
`pix68k_sound=i2s` で I2S の DAC (下の「I2S の DAC」を参照)、`pix68k_sound=off` で出さない。QEMU 用のビルドでは既定で出さない (QEMU の raspi3b は HDMI の音を持たない)。
`pix68k_sound=null` は試験用で、音を作って、コア 0 が実時間に合わせて取り出して捨てる (`tools/qemu_human68k.sh` が使う)。

ARM のクロックは最大にする (Circle の既定は低いクロックで、Pi 3B+ では 1.4GHz (3B では 1.2GHz) ではなく 600MHz になる。最大は Pi 4B で 1.5GHz (後期の版の基板は `config.txt` に `arm_boost=1` を書くと 1.8GHz。Raspberry Pi OS の `config.txt` には書いてあるが、Circle の `config64.txt` にはない)、Pi 400 で 1.8GHz、Pi 5 で 2.4GHz)。温度を見てクロックを下げること (Circle の `CCPUThrottle::Update()`) はしていない。熱くなったときはファームウェアがクロックを下げるはず (Pi 3B+ の Linux では 60 度で 1.2GHz になった。ベアメタルではまだ確かめていない)。ファームウェアが電圧不足や温度でクロックを下げると、10 秒ごとのログに `cpu: throttled ...` の警告を出す。

Pi 5 では、ファンのコネクタ (Active Cooler、Case Fan) のファンを回す。Linux では pwm-fan ドライバが回すが、ベアメタルでは誰も回さず、4 つのコアを使い続けると温度が上がってファームウェアがクロックを下げるため。つなぎ方と速さは Raspberry Pi の Linux の device tree ([bcm2712-rpi-5-b.dts](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm64/boot/dts/broadcom/bcm2712-rpi-5-b.dts) の `cooling_fan`、`rp1_pwm1`、`thermal_trips`) に合わせた:

- ファンの PWM は RP1 の GPIO45 (alt0、PWM1 のチャネル 3。チャネルは 0 から 3 の 4 本)。出力は反転で、GPIO45 が Low の間が「回す」。周期は 41566ns (約 24kHz)
- 速さは温度で 4 段階に変える。50 / 60 / 67.5 / 75 度以上で段階 1 / 2 / 3 / 4 (速さは 255 を全開として 75 / 125 / 175 / 250) に上げ、上げた温度より 5 度下がったら 1 つ下げる。50 度に届くまでは止めている。温度は 2 秒ごとに読む。温度が読めないときは段階 4 にする
- 起動してから主ループに入るまで (数秒) は全開で回す
- PWM1 のクロックを動かせなかったときは、GPIO45 をふつうの出力にして、回す (全開) か止めるかだけにする (ログに `fan: PWM1 clock failed; on/off only`)
- `cmdline.txt` に `pix68k_fan=full` を書くといつも全開、`pix68k_fan=off` を書くとファンに触らない (既定は `pix68k_fan=auto`。ファンのコネクタがない基板や、GPIO45 をほかのことに使う基板では `off` にする)。Circle の `gpiofanpin=` を書いたときも触らない
- 10 秒ごとの `cpu:` の行の最後に、段階、速さ (255 が全開)、RP1 が測った回転数を出す (`cpu: 2400 MHz set, 2400 MHz measured, throttled 0, 52 C, fan level 1 (75/255), 2890 rpm, mem 8192 MB, heap low 150/958 MB used, high 0/7168 MB used`。数字は例)。起動のときには、ファームウェアが残した PWM1 の設定を `fan: PWM1 before: ...` の行に出す
X68000 が動き始めたら、ログは UART だけに出す。10 秒ごとに速さと、その 10 秒のフレームごとの時間
(`frames:` の行。1 フレームの CPU サイクル数、処理時間の平均と最悪、次のフレームまでの残り時間の最小値、遅れたフレームの数、起動してからコア 1 がコア 2 の合成を待った回数)、
ARM のクロック (要求した値と実測の値)、ファームウェアがクロックを下げているか (`PROPTAG_GET_THROTTLED` の値)、温度、メモリとヒープの使った量を出す (`cpu:` の行。Pi 5 はファンの段階と回転数も出す)。
ヒープは、`mem` がメモリ全体、`heap low 使った量/大きさ` が 1GB より下のヒープ (`new` と `malloc` が使う)、`high` が 1GB より上のヒープ (Pi 4 / Pi 5 でメモリが 1GB より多いときだけ。大きなディスクのイメージのキャッシュに使う)。
Circle のヒープは解放したブロックを大きさごとに取っておいて使い回すだけなので、「使った量」は今使っている量ではなく、起動してから一度でも切り出した量 (いちばん多く使ったときに近い)。残りは一度も使っていない部分で、解放した分はここに入らない。
X68000 のメモリ、ディスクのイメージ、MIDI の音源の ROM と SoundFont を読み終えて主ループに入る前に、そのときの量を `mem: after loading: ...` の行に 1 回出す (それぞれの大きさは読んだときの行に出る)。続けて `mem: framebuffer 0x...-0x... (... KB, pitch ...), ARM memory 0x0-0x... (... MB; total ... MB), heap low 0x...-0x...; framebuffer outside the ARM memory` の行に、フレームバッファの番地、ARM のメモリ (キャッシュを通る、1GB より下) とヒープの範囲を出す。フレームバッファが ARM のメモリの中にあれば `INSIDE`、ヒープと重なれば `OVERLAPS the heap` と出る (ふつうはファームウェアが ARM のメモリの外に置く)。
Pi 5 の 2GB のモデルで足りるかは、`heap low` の使った量で見当が付く (`heap low` の大きさはメモリの量によらず 1GB より少し小さい)。`high` は 2GB のモデルでは約 1GB になる。`high` に置くディスクのイメージのキャッシュは空きに合わせて大きさを決めるので、8GB のモデルの `high` の使った量は 2GB のモデルとそのまま比べられない。
`cmdline.txt` に `pix68k_textdump=1` を書くと、1 秒ごとにテキスト画面を読み、変わっていれば `text|...` の行でログに出す (`tools/qemu_human68k.sh` が使う)。`pix68k_fail_core=N` は試験用で、N 番以降のコアを起動しなかったものとして扱う。`pix68k_wfe=0` を書くと、コア 0 とコア 1 が待つ間を wfe で眠らせずに空回りで待つ (前の動きと温度や速さを比べるため。既定は wfe で眠る)。`tools/qemu_human68k.sh` では `WFE=0` を付けると渡す。`pix68k_gpu_scale=` と `pix68k_fb_rows=0` は下の画面の説明を参照 (`tools/qemu_human68k.sh` では `GPU_SCALE=`、`FB_ROWS=0`)。
USB マウスは X68000 のマウス (SCC につながるシリアルマウス)、USB ゲームパッド (2 台まで) はジョイスティック 1、2 になる。
Circle が配置を知っているゲームパッドは十字キーが上下左右、A / X がトリガ A、B / Y がトリガ B。知らないものは最初のハットと最初の 2 本の軸 (遊び 40%) が上下左右、ボタン 1 / 2 がトリガ A / B。
ハットの値が 0-7 の機種と 1-8 の機種がある (Circle は論理最小値を引かずに渡す)。Circle が配置を知っている機種は 0-7 として扱い、知らない機種はつないだときに HID のレポート記述子を読み直して論理最小値を調べる (HID 記述子に書かれた正確な長さで頼む)。読めなければ値から決める (`platform::HatDecoder`): 0 と 8 のうち先に来たほうを離した値とみなし、8 なら 0-7、0 なら 1-8 の機種とする。9 以上の値が来たら 0-7 に直す。見誤るのは押したままつないだときだけ。0-7 の機種で上を押したままつないだときは、離したときに 15 などを返す機種なら直るが、離したときに 8 を返す機種では離しても左上が入ったままになる。1-8 の機種で左上を押したままつなぐと、離しても上が入ったままになる。どちらも、つなぎ直すか `hat=` で固定すると直る。`pix68k.cfg` の `hat=0` (0-7) / `hat=1` (1-8) で固定できる。
X68000 のキーボードの LED は、つないでいるすべての USB キーボードの LED に出す (CAPS → Caps Lock、かな → Scroll Lock、INS → Num Lock。ほかは出さない。Pi 400 では INS を Num Lock に出さない。下を参照)。
フレームバッファの大きさは HDMI の解像度のまま (`cmdline.txt` の `width=768 height=512` で変えられる)。X68000 の画面は、コア 0 (USB を探している間は画面を合成するコア) がフレームバッファに写すときに整数倍に拡大し、真ん中に出す (`pix68k.cfg` の `scale=auto`、既定。`src/platform/frame_scale.h`)。
倍率の決め方: 768x512 を縦横同じ整数倍 (2 倍まで) で拡大して、フレームバッファに入る最大の大きさを枠とする。各画面モードの横と縦の倍率は、それぞれ枠に入る最大の整数にする。
1920x1080 では 768x512 が 2x2、512x512 が 3x2、256x256 が 6x4 で、どれも 1536x1024 になる (横と縦の倍率が違うのは、X68000 の 512 ドットや 256 ドットのモードの画素が横に長いため)。
1280x720 では、768x512 と 512x512 は拡大せず、256x256 は 3x2 で 768x512 になる。拡大は最近傍 (同じ画素を並べる) で、ぼかさない。
フレームバッファに枠がまるごと入らないときは、小さい倍率にする (はみ出す分を切り出して大きくはしない。`config.txt` の `disable_overscan=1` を参照)。3840x2160 でも 2 倍まで (1536x1024) にする (3 倍、4 倍では写す量が 9 倍、16 倍になるため)。大きく出したいときは `cmdline.txt` で `width=1920 height=1080` などにすると、ファームウェアが HDMI の解像度に引き伸ばす (縦横比と、ぼけ方は確かめていない)。
`scale=off` で拡大しない (今までどおり 1 倍で真ん中に出す)。X68000 の画面の外は黒で塗る。10 秒ごとのログに、1 フレームを写すのにかかった時間 (平均と最大、`screen: copy to the framebuffer ...`) を出す。 コア 2 で画面を合成しているときは、コア 2 が 1 フレームを合成するのに使った時間 (`screen: core 2 composed a frame in ... us on average, ... us at most`) を、コア 3 で音を合成しているときは、コア 3 が 1 フレーム分の音を合成するのに使った時間 (`sound: core 3 synthesized a frame of sound in ...`。MIDI の音源が音を作る時間を含む) も出す。記録を処理した時間だけを足したもので、待っている時間は入らない。 合成するコアが遅れて何フレーム分かの記録をまとめて処理し、フレームの区切りを 1 度に 2 つ以上見つけたときは、その間の時間をフレームの数で割った値を 1 フレームの時間とする。そのときの `at most` は、フレームごとの最大ではなく、この割った値になる。
写すときは、前に写したときの X68000 の画面の写しをふつうのメモリに持ち、1 行ずつ比べて、変わった行だけをフレームバッファに書く (`platform::FrameRowCache`。起動の間やディスクを読む間など、画面がほとんど変わらないときに写す時間が減る)。ログの `copy to the framebuffer` の行の終わりに、変わっていないので書かなかった行の割合を出す。すべての行が変わるフレーム (スクロールするゲームなど) では、フレームバッファに書く量は前と同じで、比べる時間と写しを作る時間 (768x512 で 1.5MB の読み書き) が足される。`cmdline.txt` に `pix68k_fb_rows=0` を書くと、前と同じく毎回すべての行を書く (比べるため)。
`pix68k.cfg` の `scanline=on` (既定は `off`。ベアメタル版だけ) で、縦 2 倍以上に拡大したとき、拡大した各行の最後の 1 行を半分の明るさにして、ブラウン管のスキャンラインのように見せる (1920x1080 の 768x512 なら 2 行に 1 行、256x256 なら 4 行に 1 行)。設定メニューでは Scale の行で `off`、`auto (integer)`、`auto + scanlines` から選び、すぐに反映する (主のページの行は増やせないため、Scale の行にまとめた。`scale=off` で拡大しないときは暗くしない。`off` を選んでも `scanline=` は変えない)。
縦の倍率が 1 のとき (`scale=off`、1024 ラインの画面、`pix68k_gpu_scale=2` でフレームバッファの中の倍率が 1 になるとき) は何もしない。ホスト版 (SDL2) は `scale=` と同じく使わない (ウィンドウへの拡大は SDL2 に任せているため)。
暗くした行は、拡大した 1 行と同じくふつうのメモリで作ってから書くので、フレームバッファに書く量と、読み戻しのないことは変わらない。増えるのは 1 行を暗くする計算 (1920x1080 の 768x512 で 1 フレーム 1536x512 画素) で、10 秒ごとのログの `copy to the framebuffer` の行の終わりに `; scanlines` を付けるので、あり / なしで比べられる。画面の右上の数字 (`osd=`) を X68000 の画面に重ねるときも、数字は暗くしない。
暗くする行はフレームバッファの行に合わせて入れるので、ファームウェアがフレームバッファを整数でない倍率で表示に引き伸ばすとき (`cmdline.txt` の `width=` `height=` を HDMI の解像度より小さくしたときなど) は、暗い行の間隔がそろわず、縞 (モアレ) が出ることがある。
`cmdline.txt` に `pix68k_gpu_scale=2` を書くと、フレームバッファを表示の大きさの縦横 1/2 (1920x1080 なら 960x540) にし、表示への 2 倍の拡大はファームウェア (GPU) に任せる。倍率は表示の大きさで決めるので、768x512、256x256、384x256 の画面は今と同じ 1536x1024 に出て、フレームバッファに書く量は 1/4 になる。512x512 の画面は、フレームバッファの中で 1.5 倍にはできないので 1 倍にし、1024x1024 に出る。フレームバッファより大きい画面 (1024x1024 のモードなど) は、今は 1920x1080 にそのまま入るが、960x540 からはみ出す分は切れる (真ん中を出す)。`pix68k_gpu_scale=1x2` なら縦だけ GPU が 2 倍にする (1920x540。512x512 も 1536x1024 に出て、書く量は 1/2)。表示の大きさが割り切れないか、768x512 が入らなくなるとき (オーバースキャンで 1824x984 になっているときなど) は使わず、ログに出す。既定は使わない。
GPU の拡大の補間は `config.txt` の `scaling_kernel` で決まり、何も書かないとドットがにじむことがある。`scaling_kernel=8` で最近傍になるはず (実機ではまだ確かめていない)。`pix68k_gpu_scale=1x2` で、ファームウェアがフレームバッファを縦横比を変えて表示いっぱいに引き伸ばすかも、実機ではまだ確かめていない。`tools/qemu_human68k.sh` では `GPU_SCALE=2 FB_SIZE=1920x1080` で試せる (QEMU は拡大せず、960x540 のまま出す)。
X68000 の画面の右の余白 (16:9 のモニタで左右に余る黒いところ) に、直近 1 秒の数字を出す (`pix68k.cfg` の `osd=`。既定は `on`。設定メニューの OSD でも切り替えられる)。
1 項目ずつ縦に並べ、上から次の順に出す:

```
RPi5 2.4GHz    Raspberry Pi のモデルと ARM のクロック (10 秒ごとのログの cpu: の行で測った値。測れなければ要求した値)
68030 25MHz    MPU とクロック (68000 10MHz / 16MHz、68030 25MHz、68060 50MHz など。pix68k.cfg の cpu= と clock= で決まる値)
55.5/55.4/0    直近 1 秒に合成したフレームの fps / 画面に写したフレームの fps (0.1 まで) / 写す前に次のフレームに置き換わった数
       100%    X68000 の速さ (実時間の何 %)
   HEAP 52M    1GB より下のヒープの使った量 (MB。下の「ログ」の cpu: の行の heap low と同じ値で、一度でも切り出した量)
      52.3C    SoC の温度 (℃、0.1 度まで。127.9 度まで出す)
FAN 2200rpm    ファンの回転数 (止まっていれば FAN 0rpm)。Pi 5 でファンを動かしているときだけ。段階はログの cpu: の行と /thermal で見る
  THROTTLED    ファームウェアが ARM のクロックを下げたか、電圧が足りないとき (10 秒ごとのログの cpu: の行で読んだ値)
```

- fps は、コア 1 が X68000 のフレームを終えるたびに記録するフレームの数と時刻から求める (X68000 の 55.46Hz なら 55.5)。写した fps は、合成した fps に「写した数 / 合成した数」を掛けた値。fps と置き換わった数で 11 文字を超えるとき (`55.5/55.4/12`、100fps 以上など) は、fps を四捨五入した整数で `56/55/12` のように出す。fps は 999.9、置き換わった数と速さは 999 まで
- 回転数は 100rpm に丸め、前に出した値から 100rpm 以上変わったときだけ変える (回転数は毎秒少しずつ変わるので、そのたびに描き直さないため)。10000rpm 以上は `FAN 12.3k` のように 0.1k (100rpm) 単位で出す (20000rpm まで)
- Raspberry Pi のモデルの名前は Circle の `CMachineInfo` から決める: `RPi3` (3B)、`RPi3+` (3B+)、`RPi3A+` (3A+)、`Zero2` (Zero 2 W)、`CM3`、`CM3+`、`RPi4` (4B)、`Pi400`、`CM4`、`CM4S`、`RPi5`、`Pi500`、`CM5`、`CM5L` (CM5 Lite)、ほかは `Pi`。クロックは 1GHz 以上なら 0.1GHz 単位 (`2.4GHz`)、より下なら `700MHz`。11 文字に入らなければ、空白を詰め (`RPi3+1.4GHz`。名前が数字で終わるときは詰めない)、それでも入らなければ `GHz` を `G` にする (`Pi400 1.8G`、`RPi3A+ 1.4G`)
- MPU とクロックの行は、3 桁の MHz なら `68060 100M` のように縮める。値は起動したときと設定を変えたときにしか変わらないので、この行のために描き直すことはない (描き直すのは、ほかの数字が変わったときの 1 秒に 1 回まで)
- 最高速モード (`max_speed=on`) のときは、MPU の行のクロックを実効の値 (クロック × 今の速さの % / 100) にして `~` を付ける (`68060 ~210M`、`68000 ~20M`、`68000 ~9MHz`、1000MHz 以上は `68060 ~1.2G`)。上 2 桁に丸め (100MHz より下は 1MHz 単位)、前に出した値から、丸めの単位、出した値の 5% (MHz に四捨五入。52MHz なら 3MHz、89MHz なら 4MHz、210MHz なら 11MHz)、2MHz のいちばん大きい幅以上変わったときだけ変える (40MHz より下は 2MHz。10MHz の 204% と 205% を行き来しても 20 のまま)。丸めるのはクロック × % を kHz で求めたあとの 1 回だけ (75MHz の 286% は 214.5MHz なので 210) (速さは 0.25 秒ごとに少しずつ変わるので、丸めの境目で数字が行き来しないため)。060turbo の値は、選んだクロックの実機の 68060 で何 MHz にあたるか。ホスト版は横 1 行で MPU の行を出さないので、変わらない

- 文字の大きさは余白の幅で決める。1 行は 11 文字 (88 ドット) で、右に 8 ドット空けるので、余白が 96 ドットあれば 1 倍、192 ドットあれば 2 倍、288 ドットあれば 3 倍 (上限) の文字にする。1920x1080 で X68000 の画面を 2 倍にしたときは、右の余白が 192 ドットなので 2 倍の文字になる
- 右に余白がないとき (X68000 の画面がモニタの横いっぱいのとき): 上に余白があれば、そこに横 1 行 (`55.5/55.4/0 100% 52.3C THR`。MPU、ヒープ、ファンは幅を取りすぎるので出さない) で出す。上にもなければ、`osd=on` では出さない。`osd=fps` では、右上に横 1 行で X68000 の画面に重ねる。横 1 行の幅は 23 文字 (184 ドット。いちばん長い `999/999/999 999% 127.9C` が入る) で、`THR` は出すときだけ、その分 (4 文字) 広げる
- `osd=off` で出さない
- 既定の `osd=on` で出るかは、モニタの大きさと X68000 の画面モードで決まる (`tests/unit/osd_test.cpp` の `testCoverage()` が表にする)。16:9 のモニタ (1280x720 以上。`pix68k_gpu_scale=2` / `1x2` の 1920x1080 も) では、どの画面モードでも縦に並べて出る (`pix68k_gpu_scale=2` の 1024x1024 の画面を除く)。1920x1200、1280x800、1280x1024 でも縦に並ぶ。1600x1200 の 768x512 などは上の余白に横 1 行で出る。出ないのは、余白が左右とも 96 ドットより狭く、上下も 20 ドットより狭いとき (1680x1050 で 768x512 を 2 倍にしたとき、640x480 のモニタなど) で、そのときは `osd=fps` にすれば X68000 の画面に重ねて出る
- 描くのは、X68000 の画面をフレームバッファに写すところ (`src/platform/osd.h`)。X68000 の VRAM や合成した画面には描かないので、`/screen.ppm`、ステート、エミュレーションの結果は変わらない。余白に出すときは、数字が変わったとき (1 秒に 1 回) だけ描く

数字はコア 0 が 1 秒ごとに数え、変わったときだけ描き直す。重ねるときは、X68000 の画面をフレームバッファに 1 行ずつ写すときに、数字と重なる部分だけを数字の絵に差し替える (X68000 の画面のデータは変えない)。

ホスト版でも同じ設定で出せる (ウィンドウの右上に横 1 行。`osd=on` では X68000 の画面に重なるときは出さない。合成したフレームはすべて出すので置き換わった数は 0 で、温度は出さない)。

ROM がないとき (M0 の動作) は、boot パーティションのファイル一覧と `/pix68k/hello.txt` の中身、コア 1 での CPU コアの速度計測、USB キーボード・マウス・ゲームパッドの入力をログに出し、画面の右上にカラーバーを描く。

Linux の入った実機 (ssh で入れるもの) では、`tools/deploy_pi.sh <3|4|5> <ホスト名> <秒数>` でベアメタル版を 1 回だけ起動できる。
ベアメタル版は指定の秒数動いたら、ログを boot パーティションの `/pix68k/log.txt` に書いて再起動し、Linux に戻る。スクリプトはそのログを取ってきて表示する。
ファームウェアの tryboot (次の 1 回だけ `tryboot.txt` で起動する機能、全モデル対応) を使うので、ベアメタル版が止まっても次の再起動で Linux に戻る。止まったときはウォッチドッグ (15 秒) で再起動する。

Homebrew の `aarch64-elf-gcc` は C ライブラリのヘッダを持たないので、FatFs が使う `<string.h>` は `baremetal/shim/` で Circle の関数に置き換えている。

### I2S の DAC

`pix68k_sound=i2s` で、GPIO につないだ I2S の DAC に 48kHz の音を出す (Pi 3 / Pi 4 / Pi 5。Pi 5 は RP1 の I2S で、ピンは同じ)。
Pi がビットクロックと LR クロックを出し、DAC はそれに従う。実機ではまだ確かめていない (#107)。

| DAC の端子 | Pi の GPIO | ヘッダのピン |
| --- | --- | --- |
| BCK (BCLK) | GPIO 18 | 12 |
| LRCK (LCK、WS) | GPIO 19 | 35 |
| DIN (DATA) | GPIO 21 | 40 |
| SDA (I2C で設定する DAC だけ) | GPIO 2 | 3 |
| SCL (同上) | GPIO 3 | 5 |
| VIN / GND | 3.3V か 5V (基板に合わせる) / GND | 1 か 2 / 6 など |

GPIO 20 (ヘッダの 38 番ピン) も I2S の入力として割り当てるので、ほかの用途に使わない。

`pix68k_i2s_dac=` で DAC の設定のしかたを選ぶ。

- `auto` (既定): I2C (GPIO 2 / 3) で PCM512x (PCM5122 など、番地 0x4C / 0x4D) と WM8960 (0x1A) を探し、見つかれば
  設定する。どれもなければ、設定の要らない DAC として音を送る。
- `none`: I2C を使わない (GPIO 2 / 3 に触らない)。PCM5102A のような、設定の要らない DAC 向け。
- `0x4c` のような I2C の番地: その番地の PCM512x か WM8960 を設定する。見つからなければ音を出さない。

PCM5102A の基板は、SCK を GND につなぐ (基板の SCK のジャンパーかはんだのパッド) と、BCK から内部でクロックを作る。
ほかの端子は FLT = L、DEMP = L、XSMT = H (L だと消音のまま)、FMT = L (I2S) にする (裏のはんだのパッドが開いたままの基板もある)。WM8960 の基板は MCLK の水晶を持つもの
(Waveshare の WM8960 Audio HAT など) を想定している。起動時のログの `sound:` の行に、I2C で DAC を見つけて設定したか
(`sound: i2s DAC configured over I2C`)、設定せずに送っているか (`sound: i2s without DAC control ...`) が出る。
QEMU (raspi3b) では、`pix68k_sound=i2s` も `pwm` も音のデバイスを動かすところで止まり、X68000 が動き出さない。

### SD カードの用意

1. SD カードを FAT32 でフォーマットする (MBR の第 1 パーティション)
2. Raspberry Pi のファームウェア (`bootcode.bin` (Pi 3 だけ)、`start*.elf`、`fixup*.dat`、Pi 4 / Pi 400 / Pi 5 は `bcm27*.dtb` も。Circle の `boot/` で `make` を実行するとダウンロードする) と `config.txt` (上を参照) をルートに置く
3. `tools/build_baremetal.sh <3|4|5>` で作ったカーネル (`kernel8.img`、`kernel8-rpi4.img`、`kernel_2712.img`) をルートに置く
4. `/pix68k/` を作り、ROM (`IPLROM.DAT`、`CGROM.DAT`。X68030 は `IPLROM30.DAT`) と、ディスクのイメージを置く。ROM はルートに置いてもよい
5. 必要なら `/pix68k/pix68k.cfg` を書く (下の例と、上の表の `pix68k.cfg` の行を参照)

```
# /pix68k/pix68k.cfg (1 行に 1 つ「キー=値」。# から行末までは注釈)
fd0 = HUMAN302.XDF
fd1 = GAME.XDF
clock = 16
ram = 4
```

pix68k.cfg のキーは `src/platform/settings.h` の `kSettingKeys` の表に 1 か所にまとめてある (ベアメタル版、ホスト版の `--config`、設定メニューが同じ表を使う)。
fd0 / fd1 / hd0 / sc0〜sc6 / cd / scsi_ex_rom はファイル名 (`/` で始まらなければ `/pix68k/` から)。
clock (68000 では 10、16。68060 では 50、75)、cpu (68000、68030、68060)、ram (1〜12)、high_mem (0〜16)、local_mem (0〜256)、cd_id (0〜6)、speed060 (5〜3200)、max_speed_limit (0〜3200) は数。
max_speed、render_core、sound_core、scsi_ex、write_back は on / off。write_protect はディスクの名前 (fd0 fd1 hd0 sc0〜sc6) を「,」か空白で区切って並べる。sram_memsize は fix / keep、hat は auto / 0 / 1、keyboard は auto / usb / pi400us / pi400jp。
知らないキーと正しくない値は、ログに警告を出して無視する。数のあとに文字が付いた値 (`high_mem=8MB` など) も正しくない値として無視する (前は数の部分だけを読んでいた)。
`fd0=` / `fd1=` を空で書くと、ドライブを空にする (`fd0.xdf` などを探さない。メニューで取り出してから「Save settings」を選ぶとこう書く)。ほかのファイル名のキー (`hd0=`、`sc0=` など) は、空なら指定しなかったのと同じ。

### USB メモリから読み書きする

SD カード (Pi 5 は NVMe も) がないか、その boot パーティションに `/pix68k` のディレクトリがないときは、USB メモリの
最初の FAT のパーティションの `/pix68k/` を、SD カードのときと同じように使う (ROM、`pix68k.cfg`、ディスクのイメージ、SRAM、
ステートの読み書き。置くファイルは上の表と同じ)。Linux を入れた USB メモリなら、1 つ目のパーティション
(Linux では `/boot/firmware`) がそれに当たるので、Linux から `/boot/firmware/pix68k/` にファイルを置ける
(カーネルを LAN から起動し、SD カードを挿していない Pi 4 など)。

- 選ぶ順は NVMe (Pi 5)、SD カード、USB メモリ。`/pix68k` のディレクトリがある最初のドライブを使う。どれにもなければ、
  マウントできた最初のドライブを使う (`src/platform/boot_drive.h`、ctest の `boot_drive_test`)。
  NVMe か SD カードに `/pix68k` があれば USB メモリは探さず、起動の流れは前と変わらない
- `cmdline.txt` の `pix68k_drive=usb` / `sd` / `nvme` で、使うドライブを 1 つに決められる (ほかのドライブは初期化しない。既定は `auto`)
- 使うドライブはログの `boot drive: USB:` の行に出る。USB メモリを探したときは、その前に
  `USB drive: mounted 1234 ms after the USB scan started (/pix68k found)` が出る (2 本目からは
  `USB drive: USB2: (umsd2) mounted 1500 ms after the USB scan started (/pix68k found)` の形。`/pix68k/id.txt` があれば、その値も出る)
- USB メモリは Circle の USB 大容量記憶のドライバ (`umsd1`〜`umsd3`) と FatFs の `USB:`、`USB2:`、`USB3:` のボリュームで
  読み書きする。FatFs はパーティション表 (MBR) の 4 つのうち、最初の FAT のパーティションをマウントする (2 つ目以降の
  ext4 は読まない。GPT のパーティション表と exFAT には対応していない)
- USB メモリは 3 本まで調べ、上と同じ規則で 1 本を選ぶ: `/pix68k` のある最初のもの (`cmdline.txt` に `pix68k_id` があれば、
  `/pix68k/id.txt` の値が一致するもの)、どれにもなければマウントできた最初のもの。Linux の入った USB メモリと、データ用の
  USB メモリを両方挿していても、`/pix68k` を置いたほうを使う (どちらが `umsd1` になるかは USB のポートとつなぐ順で決まる)。
  選ばなかった USB メモリはアンマウントし、読み書きしない
- USB の装置は、ふだんは X68000 を動かし始めてから探すが、USB メモリを使うときは ROM を読む前に探すので、
  最初の画面が出るのはその分遅くなる。探し終えたあとも、規則で決まる USB メモリ (`/pix68k` があるか、`pix68k_id` の値が
  一致する) が出てくるか、USB メモリが出てきて装置の構成が 0.5 秒変わらなくなるまで待つ (ハブの先の USB メモリは、直結の
  ものより遅れて出てくるため)。長くても `cmdline.txt` の `pix68k_usb_wait=ミリ秒` (既定 2000) まで
- USB メモリを使っている間は、ほかの USB の転送 (キーボードやハブをつないだり外したりしたときの処理、キーボードの LED) の
  途中では、ディスクのイメージを読み書きしない (転送から戻ってから行う)。SD カードのときは、前と同じく途中でも読み書きする
- USB メモリの FAT のパーティションには Linux の起動ファイルが入っていることがあるので、USB メモリでは `/pix68k/` の下だけに書く
  (`pix68k.cfg`、SRAM、ステート、ディスクの書き戻し、deploy のログ)。`pix68k.cfg` に `/` で始まる名前で書いた `/pix68k/` の外の
  イメージは、読めるが書き込み禁止になる。ネットワークの口 (`net=on`) からの `/pix68k/` の外への書き込みと削除は断る (403)。
  SD カードと NVMe のときは前と同じで、制限しない
- ハードディスクと SCSI のイメージの書き戻しは、ファイルの大きさを変えずに中身を上書きするので、空きを使わない。
  フロッピーディスクのイメージ、`pix68k.cfg`、ステートは、別の名前 (`.new`) に書き終えてから置き換えるので、空きが足りずに
  失敗しても前のファイルが残り、書きかけのファイルは消す。USB メモリでは、新しく書くファイル (ステート、`pix68k.cfg`、SRAM、
  フロッピーディスクのイメージの `.new`、ネットワークの口からのファイル) は、書いたあとに 32MB の空きが残るときだけ書く。
  deploy のログ (`log.txt`) と `/pix68k` のディレクトリを作るときも同じ。書く大きさは FAT のクラスタの倍数に切り上げ、
  新しい名前を作る操作 (新しいファイル、`.new` / `.part`、名前の変更、途中で止まった置き換えを戻す名前の変更、
  ディレクトリの作成) には、ディレクトリが伸びる分の余裕として 64KiB (クラスタに切り上げ、最低 4 クラスタ) を足して数える。
  FAT は、ディレクトリのエントリが埋まっていると名前を足すときにディレクトリを伸ばす。長い名前は最大 255 文字で
  20 エントリ (640 バイト) なので、1 回の保存の作成と名前の変更を合わせても 64KiB で足りる (伸びるかどうかは調べず、
  いつも足す)。0 バイトのファイルも同じ。余裕が残らなければ、途中で止まった置き換えも戻さず、そのままにする。
  ネットワークの口から受け取っている途中のファイルは、まだ書いていない残りも使ったものとして数える
  (受け取りの途中でステートを保存しても、両方が終わったあとに 32MB が残る)
- 空きは FatFs の `f_getfree()` で読む。FAT32 では FSInfo に書かれた空きの数をそのまま使うので、Linux が正しく
  アンマウントせずに終わったあとなどは、実際の空きとずれていることがある
- SD カードか NVMe をマウントできたが `/pix68k` のディレクトリがないとき (ROM をルートに置いているとき) も、ROM を読む前に
  USB の装置を探し、USB メモリを待つ。このときは、キーボードやマウスの登録が、USB の装置を探した直後ではなく、
  X68000 を動かし始めたあとの主ループの最初の周回になる
- 動かしている間は USB メモリを抜かない (開いているディスクのイメージを読み書きできなくなる)

### 設定メニュー

PC につながずに、ディスクの入れ替えや設定の変更ができる。X68000 の画面の上にメニューを重ねて出す。

- 開く / 閉じるキー: USB キーボードの Scroll Lock、Application (右 Windows キーの隣のメニューのキー)、Menu。Pi 400 ではラズベリーのキー + M。
  どれも X68000 のキーに割り当てていないので、メニューのために使えなくなる X68000 のキーはない (F12 は X68000 の XF2 なので使わない。ホスト版だけは F12 でも開く)
- 操作: ↑↓ で項目を選ぶ、←→ で値を変える、Enter で決める、Esc (か Backspace) で戻る / 閉じる。↑↓←→ は押し続けると繰り返す
- 項目:
  - FD0 / FD1: `/pix68k/` にあるフロッピーディスクのイメージ (`.xdf`、`.dim`、`.d88`、`.hdm`、`.2hd`) の一覧から選ぶと、すぐに入れ替える。一覧の先頭の [Eject] で取り出す。読めないイメージを選んだときは、入っているディスクはそのまま
  - HD0 (SASI): `.hdf` の一覧から選ぶ。次の起動から
  - CD-ROM: `.iso` と `.cue` の一覧から選ぶ。CD-ROM 装置をつないで起動していれば、すぐに媒体を入れ替える ((none) で取り出す。読めないイメージを選んだときは、入っている媒体はそのまま。ベアメタル版で、前の媒体を外したあとにメモリが足りなかったときは、装置は空になり、そう出す)。つないでいなければ次の起動から (外付け SCSI ボードか、X68030 / 060turbo の内蔵 SCSI が要る)
  - SCSI board (68000 のとき): 外付け SCSI ボード (`scsi_ex`)。次の起動から
  - SC0〜SC6: SCSI のハードディスクのイメージを `.hds` の一覧から選ぶ。次の起動から。CD-ROM と同じ ID ならそう出す (CD-ROM を使う)
  - CPU、Clock (68000 のとき)、RAM、High memory (68030 のとき)、Local memory (68060 のとき)、Max speed: 次の起動から。動いている値と違う項目には「*」を付ける
  - Boards: Enter で拡張ボードのページに入る (Esc か Back で戻る)。主のページには、つなぐボードの名前を出す
    - FPU board、Mercury Unit、Neptune-X、MIDI board: 拡張ボード (`fpu_board`、`mercury`、`neptune`、`midi`) の on / off (FPU board は off、on、2)。次の起動から。どの CPU でも出す
    - MIDI out (MIDI board が on のとき): MIDI の行き先 (`midi_out`、SoundFont / UART / none / MT-32 / SC-55)。次の起動から。その環境で使えないもの
      (Pi 3 のビルドの SC-55、`--midi-dump` を付けていないホスト版の UART) は選べない。SoundFont や ROM のファイル名 (`midi_sf2` など)、
      Neptune-X の MAC アドレスと送受信の先はメニューでは変えられないので、pix68k.cfg に書く (ファイル名を書いていない行き先を選ぶと、要るキーを出す)
  - Scale (ベアメタル版だけ): 画面の拡大とスキャンライン (`scale` と `scanline`。off / auto (integer) / auto + scanlines)。変えるとすぐに反映する (保存するには Save settings)
  - OSD: 画面の右上の数字 (`osd`、off / on / fps)。メニューを開いている間は出さず、on か fps にしてメニューを閉じると 1〜2 秒で出る (数え直すため)。保存するには Save settings を選ぶ
  - State slot、Save state、Load state: ステートの保存と読み込み (下を参照)
  - Reset: X68000 をリセットする (電源を入れ直したときと同じ)
  - Save settings: pix68k.cfg に書く。変えた項目の行だけを書き換え (なければ最後に足す)、ほかの行、注釈、知らないキー、改行の形 (CRLF) はそのまま残す。
    書いている途中で電源が切れても前の設定が残るよう、`pix68k.new` に書いてから `pix68k.cfg` と置き換える
  - Restart: 設定を pix68k.cfg に書いてから再起動する (SRAM も書く)。「*」の付いた項目はこれで反映する
- メニューを開いている間は X68000 を止める (CPU も周辺機器も、音も止まる)。閉じると続きから動く。止めていた時間は取り戻さないので、X68000 の時計は止めていた分だけ遅れる。
  止めるのは、ディスクの入れ替えやステートの保存をフレームの途中でしないため
- 開いている間、キー、マウス、ゲームパッドは X68000 に送らない。開くときに押しているキーは X68000 には離したことにし、閉じるときに押していたキー
  (閉じるのに押した Enter など) は、一度離すまで X68000 に送らない
- 画面: コア 1 はフレームの切れ目で、コア 2 (画面の合成) とコア 3 (音の合成) が受け取った記録を処理し終えるのを待ってから止まる。
  コア 0 が最後に受け取った X68000 の画面をフレームバッファに写し、その上にメニューを描く。コア 2 の合成とフレームの受け渡しには手を入れないので、
  メニューを閉じたあともフレームは飛ばさない

ステート: X68000 の実行状態 (CPU (68000 / 68030 / 68060 と FPU)、メモリ、SRAM、画面、音、周辺機器、外付け SCSI ボード、数値演算プロセッサボード (2 枚まで)、まーきゅりーゆにっと、Neptune-X) を `/pix68k/state0.p68` から `state9.p68` に保存する
(ホスト版は `--state-dir`、既定 `~/.cache/pix68k`)。ファイルの頭に版番号 (`src/x68k/state.h` の `STATE_VERSION`) と機種の組み合わせ (CPU、メモリの容量、クロック、
IPL ROM と SCSI ROM の CRC32、拡張ボードの有無) と中身の CRC32 を置き、合わないファイルは読まない (メニューに理由を出す。X68000 は変えない)。
版 2 のファイル (拡張ボードを足す前) は、数値演算プロセッサボードもまーきゅりーゆにっともつないでいなければ読む。版 3 のファイル (大きなイメージを足す前) も読む。
ディスクのイメージの中身と、どのイメージを入れているかはステートに入れない。読み込んだときに入っているディスクをそのまま使うので、保存したときと同じディスクを入れてから読む。X68000 の時計 (RTC) も保存したときの時刻に戻る。
全部が 0 のメモリのページは 1 バイトにするので、Human68k を起動したところで約 0.5MB (4MB の機種)。メモリを使うほど大きくなる (4MB の機種で最大約 6MB の見積もり)。
版 9 から、68060 の MMU が有効な間は、表を引いた結果を覚えている TLB と ATC も入れる (空から始めると、読んだあとに同じページを使うたびに
表を引き直すので、サイクル数がずれ、PFLUSH せずに書き換えたデスクリプタが使われて、保存しなかったときと結果が変わる)。版 8 までのファイルも読む
(TLB と ATC は空から始まる)。
版 10 から、68060 のサイクル数の数え方の状態 (同時実行の相手、分岐の折りたたみ、分岐キャッシュ、命令の取り出しの位置) も入れる
(入れないと、保存したところから続けたときと、読み込んで続けたときで、サイクル数が変わる)。版 9 までのファイルも読む (空から始まる)。
版 16 で、2 枚目の数値演算プロセッサボードを入れられるようにした (2 枚目をつないでいるときだけ入る)。0 枚か 1 枚なら版 15 と同じ並びで、版 15 までのファイルも読む。
2 枚のステートは 1 枚の X68000 では読まず、その逆も読まない (ボードの組み合わせが違う)。
版 13 で、ADPCM (MSM6258) の状態の並びを変えた。版 12 までのファイルも読むが、ADPCM は「再生中か」だけを引き継ぐ
(再生の途中で保存したファイルは、波形を中心に戻して、続きのデータから再生する。止まっていたファイルは止まったまま)。
CRC が合っていても値が取りうる範囲にないファイルの扱いは、値によって 2 通りある。
- X68000 を変える前に断るもの (理由は layout does not match): 配列の添字や個数、フェーズ、0 か 1 の値、フラグと割り込みのレベル、時間の端数、
  マウスの移動量、数値演算プロセッサボードの受け渡しの長さ、OPM と ADPCM の、表の添字やシフトの数に使う値。
- 読んだうえで直すもの: MIDI ボード (FIFO の位置と個数、覚えている音源の設定を範囲に収める)、CPU のサイクル数から離れすぎた時刻 (今に合わせる)、
  SASI / SPC / FDC / 数値演算プロセッサボードの、組み合わせが合わない転送の途中の状態 (その転送を捨てる。SPC がつながっていないのに残っている
  フェーズや ACK を消す)、68060 の TLB と ATC の、戻せない項目 (捨てる)。
  CPU の時刻 (電源を入れてからのサイクル数) が上限を超えていれば、小さい値 (2^40 サイクル + 上限の半分で割った余り) に直し、時刻で持っている
  ほかの値 (ラスタ、キーボード、マウス、MIDI ボード) も同じだけ戻す。今より 2^40 サイクル (50MHz で 6 時間ぶん) 以上前の時刻でなければ、
  値どうしの差は変わらないので、続きは同じに動く。64 ビットの上限の近くでは、進める先の時刻の足し算があふれて止まるため。
  上限は、68000 が 2^62 サイクル (16MHz で 9 千年ぶん。手で作らないかぎり、超えるステートはできない)、68030 / 68060 が 2^49 サイクル
  (中では 1/12800 サイクルの単位で数えるので、64 ビットに入るのは 1.4 x 10^15 サイクルまで。2^49 サイクルは 50MHz で動かし続けて 130 日ぶんで、
  そこからあふれるまではさらに 203 日ぶんある。版 14 までのステートは 1/800 サイクルの単位で、読むときに直す)。
  ステートを読まずに続けて動かしたときも、上限を超えたら次のフレームの初めに同じ戻し方で時刻を戻す (`Machine::rebaseTime()`) ので、あふれて止まることはない。上限ちょうどのステートから動かして保存したもの (時刻は上限を超えている) も読める。今つないでいるディスクや機器と合わない転送の途中の状態も、その転送だけを捨てる
  (媒体を取り出してある CD-ROM 装置は、装置があるので、コマンドの受け取りや INQUIRY、REQUEST SENSE の応答の途中を続ける)。
確かめているのは、添字、個数、シフトの数、繰り返しの回数になる値 (MFP のプリスケーラの残り、OPM のタイマと BUSY の残り、音のサンプルの中のクロック、
時間の端数など) と、足し引きであふれる値 (音のフィルタ、マウスの移動量) で、68030 / 68060 の PC が奇数のものも断る (命令の語を偶数の前提で読むため。68000 は読むたびに確かめてアドレスエラーにする)。
ほかの CPU のレジスタとメモリの中身は確かめない。
確かめ方 (ctest の `state_test`、`sasi_test`): 68030 の MMU のレジスタ、68060 の MMU が有効で TLB と ATC に項目がある状態、SASI / FDC / ADPCM と DMAC /
MIDI ボード / 外付け SCSI ボードの動作の途中のすべての区切りで保存し、読んで続けた結果 (CPU のサイクル数とレジスタ、RAM、VRAM、画面、ディスクのイメージ、
終わりのステート) が、保存しなかったときと同じこと。途中で切れたファイル、大きさや機種の違うファイル、中身を書き換えて CRC を合わせ直したファイルを
読ませても、断ったときに X68000 が変わらず、読んだときに範囲の外を読み書きしないこと (ASan / UBSan のビルドで `state_test --corrupted` を、
`STATE_TEST_ROUNDS` で回数を増やして回す。乱数で書き換えるものと、決め打ちの組み合わせの両方)。`state_test_human68k`、`state_test_human68k_x68030`、`state_test_human68k_060turbo` (060turbo.sys を組み込んだ 060turbo) は、Human68k の起動の途中と、
起動したあとの場面 (ユーザモードの計算、グラフィックと OPM、フロッピーディスクの読み込み) の途中で保存し、4 秒ほど動かして比べる。

ホスト版: `--config FILE` で設定ファイルを読むと、メニューの「Save settings」はそのファイルに書く。ディスクのイメージの一覧は `--image-dir` (既定は設定ファイルの
ディレクトリ、なければ `~/.cache/pix68k/disk`) から作る。「Restart」は設定ファイルに書かずに、選んだ設定で X68000 を作り直す。
メニューを開いている間は画面を 768x512 に引き伸ばしてメニューを重ねる。`--press menu,down,enter --press-after 600` のように、試験用にキーを押せる。

### 起動にかかる時間

ベアメタル版は、起動の各段階の時刻をログに出す (`boot time: ... at N ms since power-on (+M ms)`。+M は、時刻がすぐ前の段階からの時間。
`first frame shown` は USB の装置を探し終えてから出すので、ログの順と時刻の順は違う)。
時刻は Circle が読む ARM のカウンタの値で、電源を入れたときから数えているはずだが、ファームウェアの時間がどこまで入るかは実機で確かめていない。
段階は次のとおり。

| ログ | 中身 |
| --- | --- |
| `kernel started` | カーネルに入った (ファームウェアの時間がここに入るかは未確認) |
| `screen, serial and timer ready` | HDMI の画面、UART、割り込み、タイマを用意した |
| `boot drive mounted` | SD カード (Pi 5 は NVMe も) を初期化してマウントした |
| `reading pix68k.cfg` | 設定を読み始める |
| `ROMs read` | IPL ROM と CGROM を読み終えた |
| `X68000 set up` | X68000 を用意し、音の出力を始めた |
| `disk images read` | フロッピーディスクのイメージを読み、ハードディスクのイメージを開いた |
| `core 1 started` | コア 1 で X68000 が動き始めた (IPL ROM が動き出す) |
| `first frame shown` | X68000 の最初の画面を出した |
| `USB devices scanned` | USB の装置を探し終えた |
| `keyboard attached` | 最初のキーボードが見つかった |

起動を速くするためにしていること:

- USB の装置は、X68000 を動かし始めてから探す。Circle は装置を探すときにハブの電源を入れて 510ms 待つなど決まった時間を待つので、
  Pi 3B+ (ハブが 2 段と LAN7800) では 2 秒ほどかかる見込み (QEMU では 2.6〜2.9 秒)。探している間もコア 1 は X68000 を動かす。
  コア 0 は探し終えるまで USB の転送で止まるので、その間は画面を合成するコア (コア 2。`render_core=off` のときと、コア 2 が
  起動しなかったときはコア 1) が、合成したフレームを自分でフレームバッファに写す。コア 0 は Circle の待ち (`CTimer::MsDelay()`) の間に、
  ハードディスクのイメージのチャンクを読み、書き戻す (`tools/build_baremetal.sh` が Circle の写しの `timer.h` を書き換え、
  `MsDelay()` から pix68k の関数を呼ぶ)。探し終えたあとも、装置をつないだり外したりしたあとの処理 (`UpdatePlugAndPlay()`。QEMU で
  0.1 秒ほど) と、キーボードの LED を送る転送 (QEMU で 30ms ほど) の間は、同じように合成するコアが写す。設定メニューを開く途中と
  開いている間は、コア 0 がメニューを重ねて描くので任せない。写す役の受け渡しの順序は `src/platform/frame_handoff.h` に書いた。
  QEMU では、最初の 10 秒に表示する前に置き換わったフレームは 0 (ログの `screen: ... replaced before shown`。コア 0 が待ちの間にだけ写して
  いたときは、探している 3 秒ほどの間に 35〜90 フレーム)。コア 1 が写すときは、1 フレームにつき画面を 1 回写す分だけ X68000 を動かす時間が減る
  (実機では測っていない)。
  キーボードなどは探し終えてから使える。あとからつないだキーボードも使える (QEMU で、何もつながっていないときと、ハブとマウスだけのときに確かめた)。
  キーボードが見つかるのは IPL ROM が動き出してから 2〜3 秒後なので、IPL ROM が電源を入れた直後に見るキー (OPT.1 を押したまま
  起動するなど) は X68000 に届かない (実機では確かめていない)。
  Pi 3 で `neptune=on` のときだけは、有線の Ethernet が USB につながっているので、X68000 を動かす前に探す。
  Pi 4 の Ethernet (GENET) は USB を通らない。Pi 5 の Ethernet (MACB) と PWM / I2S の音 (`pix68k_sound=pwm` / `i2s`) は RP1 を使うが、
  RP1 (Circle の `CSouthbridge`) は Circle の `sysinit()` が `main()` の前に初期化するので、USB より前に使ってよい
  (`CUSBSubSystem` の中の `CSouthbridge` は、初期化済みかどうかを返すだけ)
- ハードディスクと CD-ROM のイメージは全体を読まず、使うチャンクだけを読む (上の「ディスクの書き戻しと大きなイメージ」を参照)
- 起動のときに ACT LED を 3 回点滅させるのをやめた (Circle の `CActLED::Blink()` は点滅の間 2.1 秒待つ)
- Circle の遅延ループの較正 (`CALIBRATE_DELAY`) をしない (QEMU で 0.2 秒、Pi 3 の 600MHz では 0.5 秒ほどの見込み。
  較正の結果を使う `nsDelay()` は Circle も pix68k も使っていない)。ログの `timer: SpeedFactor is ...` は出なくなった

QEMU (raspi3b) で、Human68k 3.02 のフロッピーディスクとハードディスク (20MB の SASI のイメージ) から起動したときの時間 (ms。3 回ずつ):

| | core 1 started | first frame shown | 「A>」が出る |
| --- | --- | --- | --- |
| 変える前、FD | 5480〜5560 | 5590〜5630 | 12500〜12600 |
| 変えたあと、FD | 250〜300 | 270〜330 | 7000〜7200 |
| 変える前、HD | 9670〜10080 | 9750〜10160 | 19200〜20300 |
| 変えたあと、HD | 310〜420 | 360〜490 | 11700〜14100 |

測ったマシンはほかの作業で負荷が高く (ロードアベレージ 20 前後)、QEMU の速さがばらついた。HD の行は、変える前と後を交互に起動して測った。
「A>」はテキスト画面を 1 秒ごとに読んで見ているので、さらに 1 秒ほどの幅がある。QEMU の値は目安で、実機の値はまだ測っていない。

ファームウェアの設定 (実機では確かめていないので、推奨にとどめる):

- `config.txt` の `disable_overscan=1`: ファームウェアのオーバースキャン (画面の上下左右を空けて、フレームバッファをその分小さくする) をやめる。
  書かないと、1920x1080 の HDMI のモードではフレームバッファが 1824x984 などになり、768x512 の 2 倍 (1536x1024) が入らないので、X68000 の画面を拡大しない
  (Pi 3B+ と 1920x1080 のキャプチャ装置で、書いていないときに 1 倍になった)。起動時のログの `screen: overscan ...` でオーバースキャンが有効かが分かる
- `config.txt` の `disable_splash=1`: 虹色の画面を出さない
- `config.txt` の `boot_delay=0`: カーネルを読む前に待たない。Pi 3B+ の Raspberry Pi OS で `vcgencmd get_config boot_delay` は、
  書いていなくても 0 だったので、いまのファームウェアでは書かなくても同じかもしれない
- Pi 4 / Pi 400 / Pi 5 は、EEPROM の `BOOT_ORDER` で SD カード (または NVMe) を先に探すようにする (ネットワークや USB から起動しようとして待たない)
- 試す価値はあるが、確かめていないもの: `config.txt` の `initial_turbo=N` (起動から N 秒、クロックを上げる。Circle の `config64.txt` は
  `initial_turbo=0` にしている)、`cmdline.txt` の `usbpowerdelay=N` (Circle がハブの電源を入れてから待つ時間 (既定 510ms。Pi 4 / Pi 5 の
  xHCI のポートは 300ms) を N ms にする。短すぎると見つからない装置があるかもしれない。いまは X68000 が動き出すまでの時間には入らず、
  キーボードが使えるようになるまでの時間だけが変わる)

参考: Pi 3B+ の Raspberry Pi OS の起動 (`sudo vclog -m` のファームウェアのログ) では、start.elf が 1.27 秒から動き、
10MB の Linux のカーネルを 1.7 秒かけて読み、5.95 秒で ARM を動かしていた。pix68k のカーネルは 0.7MB で、initramfs もないので、もっと短いはず。

### USB キーボードと Ctrl + Alt + Delete

USB キーボードは 4 台まで使える (Circle の `ukbd1`〜`ukbd8` のうち、つないだ順に 4 台)。

- すべてのキーボードの入力を合わせて X68000 に送る。同じキーを 2 台で押したときは、両方を離すまで押したまま
- あとからつないだり外したりしてもよい。外したキーボードで押していたキーは離したことにする (ほかのキーボードで押しているキーはそのまま)
- キーボードの種類 (Pi 400 の本体のキーボードか) はキーボードごとに決める。Pi 400 に外付けの USB キーボードをつなぐと、
  外付けのほうは普通の USB キーボードとして扱う (`pix68k.cfg` の `keyboard=` を `auto` 以外にしたときは、すべてのキーボードがその種類になる)
- LED は、つないでいるすべてのキーボードに送る (1 回の主ループで 1 台ずつ)。Circle の USB の制御転送 (Pi 3 の DWHCI など) には
  タイムアウトがないので、LED の要求に答えないキーボードがあると主ループが回らなくなり、Ctrl + Alt + Delete も受け付けない (前からある制約)
- 合わせたあとの押しているキーが 6 つを超えても、すべて X68000 に送る。1 台のキーボードが ErrorRollOver (押しすぎ) を送ってきたときは、
  そのキーボードの前の状態のままにする
- 接続したときのログに `keyboard attached (0627:0001, country 0, layout usb, auto, ukbd1, keyboard 1)` のように、
  Circle の装置の名前と、何台目の枠に入れたかを出す

USB キーボードの Ctrl + Alt + Delete で Raspberry Pi を再起動する (離れた場所にある pix68k 専用の Pi を、USB キーボードとして動く
マイコンなどから再起動するため)。

- Ctrl (左右どちらでも) と Alt (左右どちらでも) を押したまま Delete を押すと、メニューの Restart と同じく、書き戻していないディスクと
  SRAM を書いてから再起動する。Delete は X68000 に送らない。押していた Ctrl と Alt (X68000 の CTRL と XF1 / XF5) は、X68000 には
  離したことにし、一度離すまで送らない。3 つのキーは別々のキーボードで押してもよい
- 次のときは再起動せず、X68000 にそのまま送る:
  - Delete を先に押してから Ctrl と Alt を押したとき
  - GUI (Windows / Command のキー。X68000 の OPT.1 / OPT.2) も押しているとき。X68000 のリセット (ホットリスタート、CTRL + OPT.1 + DEL) は
    Ctrl + GUI (Windows / Command) + Delete で打つ。Pi 400 では Ctrl + ラズベリー + O + Delete (ラズベリー + O が OPT.1。O を Delete より先か同時に押す。
    OPT.1 を押している間は置き換えないので、Delete は INS にならない)
  - F11 か F20 (どちらも X68000 の XF1) も押しているとき。Ctrl + F11 + Delete と Ctrl + Alt + F11 + Delete は、X68000 に CTRL + XF1 + DEL として
    そのまま送る (Alt も XF1 になるが、F11 を押していなければ Pi の再起動になる)。X68000 のリセットにはならない (実機の Human68k では
    CTRL + XF1 で ASK68K (かな漢字変換) が動く)
  - Pi 400 でラズベリーのキーを押しているとき (ラズベリー + Delete は INS になる)。置き換えはキーボードごとなので、ラズベリーを本体で、
    Ctrl + Alt + Delete を外付けのキーボードで押したときは再起動する。`keyboard=pi400us` などに固定すると外付けのキーボードの左 GUI も
    ラズベリーのキー (切り替えのキー) になるので、外付けの Ctrl + GUI + Delete は X68000 のリセットにならない (Ctrl + 左 GUI + Delete は
    Ctrl + INS になる。Pi 400 の本体と同じく Ctrl + 左 GUI + O + Delete で打つ)
- 設定メニューを開いていても再起動する。ROM がないとき (M0 の動作) も再起動する
- ディスクか SRAM を書けないとき (SD カードに空きがないときなど) は再起動せず、ログに警告を出して X68000 を動かし続ける。
  断ったあと 60 秒以内にもう一度 Ctrl + Alt + Delete を押すと、書き戻しをもう一度試し、それでも書けなければ書かずに再起動する
  (メニューの Restart を 2 回選んだときと同じ)。書いている間 (最大で数秒) に押し直した分は、断ったときに捨てる (断ったあとの 2 回目と
  取り違えないため。`platform::RebootRequest`)。X68000 を動かしているコア 1 が 5 秒たっても止まらないときも、書けないときと同じに扱う
- `tools/deploy_pi.sh` で起動したときは、ログを `/pix68k/log.txt` に書いてから再起動する。tryboot は次の 1 回の起動だけなので、
  決めた秒数がたったときと同じく Linux に戻る
- ホスト版では何もしない
- 実機 (Pi 3B+) で、USB キーボードとして動かした Raspberry Pi Pico から Ctrl + Alt + Delete を送り、書き戻し、再起動、
  キーボードの見つけ直しまで動くことを確かめた

### ネットワークの口 (HTTP と syslog)

SD カードを抜かずに、離れた場所にある pix68k 専用の Pi のカーネルや設定を入れ替え、ログと画面を見るための口。Pi の有線の Ethernet
(Pi 3B+ は USB の先の LAN7800、Pi 3B は LAN9514、Pi 4 / Pi 400 は GENET、Pi 5 は RP1 の MACB) で Circle の TCP/IP を動かし、
HTTP (80 番) のサーバと syslog の送信を行う。既定では動かさない (`net=off`)。Wi-Fi は使えない。

`pix68k.cfg` の項目 (同じ名前に `pix68k_` を付けて `cmdline.txt` に書くと、そちらを使う。例: `pix68k_net=on`):

| 項目 | 内容 |
| --- | --- |
| `net=on` | ネットワークの口を動かす (既定は `off`) |
| `net_ip=192.168.1.50/24` | 固定のアドレス (書かなければ DHCP)。`net_gw=` でゲートウェイ、`net_dns=` で DNS サーバ |
| `net_name=x68000` | DHCP で送るホスト名 (既定は `pix68k`)。ルータがこの名前を DNS に載せれば、`http://x68000/` で届く |
| `net_allow=192.168.1.0/24,10.0.0.5` | 使ってよい相手のアドレス (CIDR か 1 つのアドレスをカンマで並べる)。書けば、ほかのアドレスからは読むこともできない |
| `net_token=好きな文字列` | 書き込み (ファイルの書き込みと削除、再起動、キー入力) と、ファイルの読み出しに要るトークン。HTTP のヘッダ `X-Pix68k-Token:` で渡す |
| `syslog=192.168.1.2:514` | ログを UDP の syslog (RFC 5424) で送る先 (ポートを省くと 514) |
| `rs232c=tcp:2324` | X68000 の RS-232C を TCP の 2324 番で待ち受ける (上の「RS-232C (SCC のチャネル A)」を参照。`cmdline.txt` の `pix68k_rs232c` は読まない) |

`net_allow=` と `net_token=` のどちらも書かなければ、読むことだけができ、書き込みは断る。両方書けば、両方を満たしたときだけ書ける。

`net_token=` を書くと、ファイルを読む (`GET /files/...`) のにもトークンが要る。トークンは `pix68k.cfg` か `cmdline.txt` に書いてあり、
読めればそのまま書き込みと再起動に使えるため。その写し (`.new`、`.part`、`.old` や手で作った控え) もあるので、名前で選ばずに
ファイルはすべてトークンを求める。`/log`、`/thermal`、`/screen.ppm` はトークンなしで読める (`net_allow=` は効く)。

HTTP の口:

| 要求 | 内容 |
| --- | --- |
| `GET /` | 使い方の一覧と、syslog に送った行の数 |
| `GET /files/<パス>` | SD カード (起動したドライブ) のファイルを読む (`net_token=` があればトークンが要る)。`/` で終われば一覧 (1 行に `名前`、タブ、バイト数。ディレクトリは `名前/`) |
| `DELETE /files/<パス>` | ファイルを消す (トークンが要る。ディレクトリと、X68000 が使っているディスクのイメージは断る) |
| `PUT /files/<パス>`、`POST /files/<パス>` | ファイルを書く (トークンが要る)。`<パス>.part` に書き、受け取り終えたら `<パス>` と入れ替える (元のファイルは `<パス>.old` にしてから消す)。途中で切れたら元のファイルは変えない。大きさの上限はない (SD カードに 32KB ずつ書く)。`Content-Length` が要る (`Transfer-Encoding` は chunked でもほかでも断る、400) |
| `GET /log` | 起動してからのログ (UART と同じもの。最新の 64KB) |
| `GET /thermal` | 温度、ARM のクロック、ファームウェアがクロックを下げているか、ファン (Pi 5)。`名前=値` を 1 行ずつ返す (下に詳しく書いた) |
| `GET /screen.ppm` | X68000 の画面 (PPM)。X68000 が動いていれば、次に合成し終えたフレームを待って返す (下に詳しく書いた) |
| `POST /reboot` | ディスクと SRAM を書いてから再起動する (トークンが要る。Ctrl + Alt + Delete と同じ手順。書けなければ断り、60 秒以内にもう一度頼むと書かずに再起動する) |
| `POST /type` | リクエストの本体 (ボディ) の文字列を X68000 のキーとして打つ (トークンが要る。JIS 配列。押してから 40ms で離し、40ms 空けて次を打つ。`\n` は Enter、`\t` は TAB、`\b` は BS、`\e` は ESC。4096 バイトまで) |
| `POST /key?down=XX&mod=YY`、`POST /key?up=XX`、`POST /key?up` | USB キーボードの usage ID (16 進) でキーを押す / 離す / すべて離す (トークンが要る。`mod=` は USB の修飾キーのビット。01 左 Ctrl、02 左 Shift、04 左 Alt、08 左 GUI) |
| `POST /message?sec=N` | 本体の文字列 (UTF-8) を画面の左上に重ねて N 秒出す (トークンが要る。既定 10 秒、`sec=0` なら消すまで、上限 86400)。本体が空 (空白と改行だけ) なら消す。下に詳しく書いた |

```sh
# 例はどれも net_name= を書いていない (既定の名前 pix68k の) とき。net_name=x68000 なら http://x68000/ にする
# カーネルを入れ替えて再起動する (カーネルを置いた手元の機械から)
curl -H 'X-Pix68k-Token: 好きな文字列' -T kernel8.img http://pix68k/files/kernel8.img
curl -H 'X-Pix68k-Token: 好きな文字列' -X POST http://pix68k/reboot
# 設定を読む / 書く
curl -H 'X-Pix68k-Token: 好きな文字列' http://pix68k/files/pix68k/pix68k.cfg
curl -H 'X-Pix68k-Token: 好きな文字列' --data-binary @pix68k.cfg http://pix68k/files/pix68k/pix68k.cfg
# ログ、温度、画面
curl http://pix68k/log
curl http://pix68k/thermal
curl -o screen.ppm http://pix68k/screen.ppm
# キー入力 (X68000 のリセット、CTRL + OPT.1 + DEL は Ctrl + GUI + Delete)
curl -H 'X-Pix68k-Token: 好きな文字列' --data 'dir\n' http://pix68k/type
curl -H 'X-Pix68k-Token: 好きな文字列' -X POST 'http://pix68k/key?down=4c&mod=09'
curl -H 'X-Pix68k-Token: 好きな文字列' -X POST 'http://pix68k/key?up'
# 画面の左上にメッセージを出す (30 秒) / 消す
curl -H 'X-Pix68k-Token: 好きな文字列' --data-binary '案1 (OutRun)\nいまの版' 'http://pix68k/message?sec=30'
curl -H 'X-Pix68k-Token: 好きな文字列' -X POST http://pix68k/message
```

`POST /message` のメッセージ (`src/platform/osd_message.h`):

- 4 行、1 行 40 桁 (半角の桁。全角は 2 桁) まで。はみ出した分は字の切れ目で捨てる。本体は 1024 バイトまで (超えれば 413)。
  `/type` と同じく `\n` で改行できる (`curl --data` は本体の改行を消すので、改行は `\n` か `--data-binary` で送る)
- 半角 (ASCII) は設定メニューと同じ 8x16 の字で出す。半角カタカナと全角 (JIS 第 1・第 2 水準と記号) は、X68000 の CGROM の字で出す
  (CGROM がなければ、全角は四角、半角カタカナは `?`)。JIS X 0208 にない字 (丸数字、絵文字など) は四角
- 白い字に黒の背景で、右上の数字 (`osd=`) と同じく X68000 の画面をフレームバッファに写すところで重ねる。X68000 の画面の中身には
  書かないので、`/screen.ppm` には出ない。フレームバッファの高さが 900 ライン以上 (1080 ラインのモニタなど) なら 2 倍の大きさ。右上の数字と同じ行に並ぶときは、数字にかからない
  よう右を切る。設定メニューを開いている間は出さない
- 新しいメッセージは前のメッセージを置き換える。ログに `message: "案1 (OutRun)\nいまの版" (30 s)` の 1 行を残す (改行は `\n`、
  ほかの制御文字は `?` にする。160 バイトを超えれば切る)
- 消す時刻は Pi を起動してからの時計で数える。カーネルを入れ替えて再起動すると消える
- ホスト版は `--message TEXT` (`--message-sec N`) で、同じものをウィンドウの左上に出せる (HTTP の口はない)

- X68000 につないでいるディスクのイメージ (`fd0=` などで指定したファイル) は書き換えと削除を断る (409)。書くときに使う `<パス>.part` と
  `<パス>.old` がそのイメージに当たる場合も断る。名前は、続いた `/` や大文字と小文字の違い、短い名前 (`HUMAN~1.XDF`) をそろえてから比べる
  (FatFs でディレクトリエントリの長い名前を引く)。設定メニューを開いている間の書き込みも断る (503)。受け取っている間にメニューを
  開いたり、メニューでそのファイルをつないだりした場合は、入れ替える直前にもう一度見て、受け取った内容を捨てる (503 / 409)。
  SD カードを読めず、使っているイメージと同じファイルか決められないときも断る (503)
- 設定メニューのフロッピーディスクの一覧には、名前が `.new`、`.part`、`.old` で終わるファイル (置き換えの一時ファイル) を出さず、つなぐこともしない
- 要求の頭は厳しく読む。ヘッダ名にトークンの文字以外 (コロンの前の空白など) があるもの、NUL などの制御文字 (HTAB 以外) があるもの、
  `Content-Length` の値が数字でないか重なって違うもの、`Transfer-Encoding` があるものは 400
- TCP/IP、HTTP、syslog と SD カードの読み書きはコア 0 で行う。そのタスクを動かす間は、要求がないときも、画面を写す役をコア 2
  (合成するコア) に任せる (USB を探す間と同じ)。USB の Ethernet (Pi 3B+ の LAN7800 など) は、受信を見るたびに USB の転送が
  終わるまで待つため。X68000 (コア 1)、画面の合成、音は止めない。
  コア 0 が写せずに表示されなかったフレームの数は、10 秒ごとのログの `replaced before shown` で見られる
- `/thermal` が返す行 (トークンなしで読める):
  - `temp_c=52.3`: SoC の温度 (要求のたびに読む。読めなければ `?`)
  - `clock_set_mhz=2400`、`clock_measured_mhz=2400`: ARM のクロックの要求した値と実測の値
  - `throttled=0`: `PROPTAG_GET_THROTTLED` の値 (16 進。bit0 電圧不足、bit1 クロックの上限を下げている、bit2 クロックを下げている、
    bit3 温度の上限に達している。bit16-19 は、その前の報告からの間に同じことが起きたか)
  - `throttled_since_boot=50005`: 起動してから読んだ `throttled` をすべて OR した値 (0 なら、一度も下げていない)
  - `report_age_s=3`: クロックと `throttled` を読んでからの秒数。この 2 つはログの `cpu:` の行を出すとき
    (X68000 を動かしている間の 10 秒ごと) に読んだ値で、まだ読んでいなければ `clock_set_mhz` からここまでの行は出ない
  - `fan=pwm` (Pi 5 だけ。`onoff` は PWM が使えず回すか止めるかだけ、`none` は触っていない)、`fan_level=1` (段階 0 から 4)、
    `fan_duty=75` (速さ。255 が全開)、`fan_rpm=2890` (RP1 が測った回転数)
  - `mem_total_kb=`: メモリ全体。`heap_low_kb=`、`heap_low_unused_kb=`: 1GB より下のヒープの大きさと、その中で一度も使っていない部分。
    `heap_high_kb=`、`heap_high_unused_kb=`: 1GB より上のヒープ (Pi 4 / Pi 5 でメモリが 1GB より多いときだけ)。
    解放したブロックは使い回すだけで `*_unused` には戻らない (上の `cpu:` の行の説明を参照)
- `/screen.ppm` が返す画面: 上のとおり、HTTP のタスクを動かす間は画面を写す役をコア 2 に任せており、その間に合成したフレームは
  コア 0 に渡らない。そこで、要求を受けたら写す役を一度コア 0 に戻し、フレームを受け取って HDMI に写してから、それを返す
  (返したあと、またコア 2 に任せる)。受け取るのは、ふつうは役を戻したあとに次に合成し終えたフレームで、
  コア 2 に任せる前からコア 0 に渡されたまま残っているフレームがあれば (それが最新なら) すぐにそれを受け取る。
  - フレームを待つのは、待った時間の合計で長くて 200ms。来なければ、最後にコア 0 が受け取ったフレームを返す (古いことがある)。
    このときはログに `screen: no new frame in 200 ms` の警告を出す。続けて頼まれても 10 秒に 1 回だけ出し、出さなかった回数を次の警告に添える
  - 200ms には次の時間を数えない。役を戻すときにコア 2 がフレームを HDMI に写している途中なら、写し終えるまで待つ時間
    (ふつうは 1 フレーム、残っていたフレームを先に写していれば 2 フレームを写す時間)。受け取ったフレームを HDMI に写す時間と、
    下の SD カードの読み書きの時間も数えない。そのため、要求から返すまでの時間は 200ms より長くなることがある
  - 大きなハードディスクのイメージのチャンクの読み込み (コア 0 が SD カードから読む) をコア 1 が待っていると、読み込むまでフレームが来ない。
    そのため、SD カードの読み書きが残っていれば、40ms 待ってもフレームが来ないたびに、役をコア 2 に任せてから読み書きし、また待つ
  - X68000 を止めていて設定メニューを開いていないとき (再起動の前の書き戻しなど) は、待たずに最後に合成し終えたフレームを返す
    (コア 2 が自分で写してコア 0 に渡らなかったものでも)。HDMI には写さない。コア 2 が自分で写したフレームは、
    コア 2 が次のフレームを描くのと同じバッファにあり、X68000 は次のフレームの表示期間に入ったところで止まるので、
    頭の数ラスタが次のフレームのもので上書きされていることがある
  - 設定メニューを開いている間は、メニューの下に描いているフレームを返す。メニューは写らない
- 同時に受け付ける接続は 1 つ。要求の頭は全体で 10 秒、`/type` などの小さな本体も全体で 10 秒まで。ファイルの本体は、10 秒ごとに 4KB 届かなければ切る (SD カードに書いている時間は 10 秒に数えない)
- `Host:` ヘッダが Pi のアドレス (`192.168.1.50` など) か `net_name=` の名前 (既定は `pix68k`。後ろに `:80` が付いてもよい) でなければ、GET も含めて断る (403)。
  ほかのドメインの名前を Pi のアドレスに向けて (DNS リバインディング)、ブラウザのページから読み書きさせないため。
  `curl http://192.168.1.50/` と、`net_name=` を書いていなければ `curl http://pix68k/` が通る。ルータが付けるドメイン付きの名前 (`pix68k.lan` など) は断るので、アドレスか `net_name=` の名前で送る。
  `Host:` のない HTTP/1.0 の要求は受ける
- `Origin:` ヘッダの付いた書き込み (ブラウザのページから送られたもの) は断る (403)。`net_allow=` だけでトークンなしの設定でも、ほかのサイトのページから書き込みや再起動をさせないため
- PUT / POST の送り先が既存のディレクトリなら断る (400)。`/files/pix68k` のようにファイル名を書き忘れて、ディレクトリを置き換えないように
- X68000 が使っているディスクのイメージも GET で読めるが、書き戻しと重なると中身が揃わないことがある
- `pix68k.cfg` の読めない値をログに出すとき、`net_token=` の値は出さない (`/log` はトークンなしで読めるため)。
  ほかの読めない行 (項目の名前を打ち間違えたものなど) は、そのままログに出るので `/log` から読める。トークンを書いた行は名前を打ち間違えないこと
- ネットワークは USB を探したあとに動かし始める (起動にかかる時間は変わらない)。アドレスが決まると `net: address 192.168.1.50` をログに出す
- キー入力は、USB キーボードと同じく、すべてのキーボードと合わせてから X68000 に送る (仮想のキーボードとして 1 枠を使う)。Ctrl + Alt + Delete を送ると Pi を再起動する
- syslog には UART と同じ行を送る (`/log` と同じリングから読む)。送った行の数と失敗した数は `GET /` の最後に出る。最初の 1 行を送れたら `net: syslog: sending to ...`、送れなければ `net: syslog: cannot send (...)` をログに出す
- 認証は簡単なもの (平文のトークンと相手のアドレス) なので、家の中のネットワークだけで使う
- Neptune-X (`neptune=on`) で Ethernet を使うとき (`neptune_link=eth`) は、ネットワークの口は動かさない (ログに警告を出す)。
  どちらも同じ Ethernet のデバイスを使うため。宛先の MAC アドレスで振り分けて両方を動かす作りは、まだない
- QEMU 用のビルド (`tools/build_baremetal.sh 3 --qemu`) では、Circle の DWHCI (Pi 3 の USB ホストコントローラ) のドライバを書き換えて、
  `-device usb-net` からフレームを受け取れるようにしている。QEMU の DWC2 は、データが届いて転送が終わったときも割り込みの状態 (HCINT) の NAK のビットを消さないので、
  そのままでは受け取った長さが 0 になる。Circle の `USE_NAK_USB_FIX` で避けると、こんどは QEMU が止めたチャネルでフレームを受け取って
  捨ててしまい、HTTP の要求がほとんど届かない (#117)。実機のビルドは書き換えない
- QEMU 用のビルドでは、Circle の UDP の接続 (`lib/net/udpconnection.cpp`) も書き換えて、閉じた接続が届いたパケットを受け取らないようにしている。
  Circle の DHCP は、ポート 68 の接続を閉じて作り直してから DISCOVER を送るが、閉じた接続は次の処理の回まで一覧に残る。QEMU は OFFER を
  すぐ返すので、その残った接続が OFFER を捨ててしまい、4 秒後の送り直しでやっとアドレスが決まっていた (`dhcp: No response from server. Retrying.`。#136)。
  DHCP サーバの答えが速ければ実機でも起きうるが、確かめていないので、実機のビルドは書き換えない

### Pi 400 のキーボード

Pi 400 の本体のキーボードは、Pi の中では USB の HID キーボードとして見える (VID:PID は `04d9:0007` のはず。下を参照)。
X68000 にしかないキーを置ける余りのキーがないので、ラズベリーのキー (左 GUI) を押している間、ほかのキーを X68000 のキーに置き換える
(`src/platform/key_remap.h`)。Fn はキーボードの中で処理されて USB に出てこないので、切り替えには使えない。
置き換えた先は、普通の USB キーボードの F13〜F24 などと同じ usage ID なので、X68000 の側は区別しない。

| X68000 のキー | 普通の USB キーボード | Pi 400 (英語版、日本語版) |
| --- | --- | --- |
| XF1 | 左 Alt、F11、F20 | 左 Alt、F11、ラズベリー + 1 |
| XF2 | F12、無変換、F21 | F12、ラズベリー + 2 (日本語版は 無変換 も) |
| XF3 | 変換、F22 | ラズベリー + 3 (日本語版は 変換 も) |
| XF4 | カタカナひらがな、F23 | ラズベリー + 4 (日本語版は カタカナひらがな も) |
| XF5 | 右 Alt、F24 | 右 Alt、ラズベリー + 5 |
| かな | F16 | ラズベリー + K |
| ローマ字 | F17 | ラズベリー + R |
| コード入力 | F18 | ラズベリー + C |
| 記号入力 | F13 | ラズベリー + S |
| 登録 | F14 | ラズベリー + T |
| HELP | F15、Help | ラズベリー + H |
| ひらがな | Mac の かな (LANG1) | ラズベリー + G |
| 全角 | F19 | ラズベリー + Z (日本語版は 半角/全角 も) |
| OPT.1 | 左 GUI (Windows / Command) | ラズベリー + O |
| OPT.2 | 右 GUI | ラズベリー + P |
| COPY | Print Screen、Copy | ラズベリー + Y |
| BREAK | Pause、Stop | ラズベリー + B |
| UNDO | End、Undo | ラズベリー + U、ラズベリー + → |
| CLR | Num Lock (テンキーの左上) | ラズベリー + L |
| INS | Insert | ラズベリー + Delete |
| HOME | Home | ラズベリー + ← |
| ROLL UP | Page Down | ラズベリー + ↓ |
| ROLL DOWN | Page Up | ラズベリー + ↑ |
| _ (JIS の ろ) | ろ、ISO 配列の左 SHIFT の右 | ラズベリー + / (日本語版は ろ も) |
| ¥ | ` (JIS の 半角/全角 の位置)、¥ | 英語版は `、日本語版は ¥ |
| テンキー | テンキー | Num Lock を点けたときのキーボードのテンキー (下を参照) |

ほかのキーは普通の USB キーボードと同じで、JIS 配列で同じ位置にある X68000 のキーになる。
`tests/unit/key_remap_test.cpp` で、Pi 400 にある (と分かっている) キーだけで X68000 のキーがテンキー以外すべて打てることを確かめている。

- ラズベリーのキーは、それだけでは何も送らない。Pi 400 では OPT.1 にならない
- ラズベリー + O / P (OPT.1 / OPT.2) を押している間は、ほかのキーを置き換えない (ラズベリー + O + C は OPT.1 + C になる)
- 置き換え先はキーを押した時点で決め、離すまで変えない。ラズベリー + K を押したままラズベリーを先に離しても、K を離すまで かな を押したまま。
  K を押したままラズベリーを押しても K のまま。ラズベリー + O + C のあと O を先に離しても、C は C のまま
- Raspberry Pi の説明書によると、Pi のキーボードは Num Lock がオンの間、一部の文字のキーがテンキーとして動く。
  X68000 の INS の状態に合わせて Num Lock をオンにすると文字が打てなくなるので、Pi 400 では INS の状態を Num Lock の LED に反映しない。
  Num Lock のキーは X68000 に送らず、Num Lock のオンとオフ (LED と、キーボードの中のテンキー) を切り替える。CLR はラズベリー + L で打つ
- Pi 400 の上で、接続したキーボードの VID:PID が `04d9:0007` なら Pi 400 のキーボードとして扱う (`04d9` は Holtek の VID でほかのキーボードにもあるので、ほかの機種では自動で切り替えない)。英語版と日本語版は VID:PID が同じなので、HID 記述子の
  `bCountryCode` (国のコード) が 15 (日本) のときだけ日本語版とする。日本語版で処理が変わるのは、半角/全角 のキーを ¥ ではなく 全角 にすることだけ。
  自動で見分けられなければ、`pix68k.cfg` に `keyboard=pi400jp` と書いて選ぶ。`keyboard=usb` と書くと置き換えをしない
- 外付けの USB キーボードもいっしょに使える。置き換えをするのは、Pi 400 の本体のキーボード (`04d9:0007`) だけ (`keyboard=auto` のとき。上の「USB キーボードと Ctrl + Alt + Delete」を参照)
- 接続したときのログに `keyboard attached (04d9:0007, country 0, layout pi400us, auto, ukbd1, keyboard 1)` のように、VID:PID、`bCountryCode`、選んだキーボードの種類を出す
- Ctrl + Alt + Delete は Raspberry Pi の再起動になる。X68000 のリセット (ホットリスタート、CTRL + OPT.1 + DEL) は Ctrl + ラズベリー + O + Delete で打つ (ラズベリー + O を押してから Delete。ラズベリーを押していても、OPT.1 を押している間は Delete を INS に置き換えない)

実機で確かめていないこと:

- Pi 400 のキーボードの VID:PID (`04d9:0007` は [pi400kb](https://github.com/Gadgetoid/pi400kb) の説明による)
- 日本語版の `bCountryCode` の値
- Num Lock のキーの位置と、Num Lock のオンとオフでキーボードの中のテンキーが切り替わるか
- Fn + Delete (Insert) 以外の Fn の組み合わせ (Home、Page Up など) で送られる usage ID。
  Fn の組み合わせを使わずに打てるよう、HOME、ROLL UP、ROLL DOWN、INS もラズベリーのキーとの組み合わせに割り当てた

## ほかのエミュレータとの関係

pix68k のソースには、ほかの X68000 エミュレータのソースコードは入っていない。

- XEiJ (https://stdkmd.net/xeij/) は、次の使い方をしている。
  - XEiJ の説明書 (HTML) を、仕様の資料の 1 つとして読んだ。
  - XEiJ に付いている試験プログラム (`misc/instructiontest.x`、`misc/fputest.x`) を pix68k の上で動かし、出力を比べる相手にした。
    試験プログラムはリポジトリに入れておらず、各自の XEiJ のものを使う。
  - XEiJ に付いている `IPLROM30.DAT` と、XEiJ が作る IPLROM 1.6 は、それぞれ X68030 と 060turbo の IPL ROM (起動用の ROM) として使える。
    これらの ROM は、リポジトリにも配布物にも入れない。
- 開発の初めに、XEiJ のソースを読んだうえで書いた部分があった。その部分は、XEiJ のソースを見ずに、
  データシート、SCSI-2 などの規格、Inside X68000 などの書籍、XEiJ の説明書、公開されている資料 (X68k:IOMAP、x68000-dev-guide など)、IPL ROM の逆アセンブル、ソフトの動き、試験プログラムの結果を根拠に書き直した。資料で決まらない細かい所は、書き直す前の版と同じ場面を動かして出力を比べ、同じになるように決めた所がある (その所では、書き直す前の版のソースは見ていない)。x68000-dev-guide の一部は MAME のソースを出どころにした第三者の資料で、MAME のソースそのものは読んでいない。
  公開リポジトリは書き直したあとのコードから作り、それより前の変更の履歴は入れていない。
- 68000 の CPU コアは、SingleStepTests (680x0。命令ごとの試験データ) の結果と合わない所で、
  WinUAE (Amiga のエミュレータ) の動作か実機の計測値に合わせている。試験ごとの理由は `tests/sst/expected_failures.txt` に、分け方の規則は `tools/classify_sst.py` にある。
