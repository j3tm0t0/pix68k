# X68030 (68030 と 68882)

X68030 の構成で動かす方法と、68030 / 68882 のコアの作りと確かめ方。

`--cpu 68030` で X68030 として動かす (68030 25MHz、FPU は 68882、IPL ROM 1.3)。IPL ROM は `IPLROM30.DAT` を読む
(`--ipl` で場所を指定できる。XEiJ の `data/IPLROM30.DAT` が使える)。内蔵 SCSI の ROM ($FC0000) は IPL ROM から作る
(X68030 の SCSI のドライバは IPL ROM にあり、$FC0000 には入り口のアドレスと `SCSIIN` の文字列だけを置く)。XEiJ の説明書の
更新履歴 (history.htm) にも、SCSIINROM.DAT を IPLROM30.DAT から作るとある。この作りで IPL ROM 1.3 が SCSI のディスクから
Human68k を起動することは、ctest の `x68k_boot_scsi30_stream` で確かめている。
ホスト版の SRAM の既定は `~/.cache/pix68k/sram30.dat`。`--high-mem 16` で $01000000 から 16MB のハイメモリを置く。

```sh
./build/pix68k --cpu 68030 --ipl ~/x68k/xeij/data/IPLROM30.DAT -0 ~/.cache/pix68k/disk/HUMAN302.XDF
./build/machine_bench --cpu 68030 --ipl ~/x68k/xeij/data/IPLROM30.DAT
```

68030 のコア (`src/m68k/cpu020.*`) は 68000 のコアとは別のクラスで、68000 のコアの処理は変えていない。
命令単位で動かし、サイクル数は概算 (68000 で同じ命令にかかるサイクル数の 3/5)。実機で測った値ではない。
68020 / 68030 の命令 (ビットフィールド、CAS / CAS2、CHK2 / CMP2、PACK / UNPK、64 ビットの乗除算、拡張したアドレッシングなど)、
例外のフレーム、VBR、CACR / CAAR に対応する。ベアメタル版では Raspberry Pi 3 / Raspberry Pi 4 / Raspberry Pi 5 のどのビルドにも入れる (`pix68k.cfg` の `cpu=68030`、
SRAM は `SRAM30.DAT`)。`PIX68K_CPU020=0 tools/build_baremetal.sh 3` のように実行すると、68030 / 68060 のコアを入れない
68000 だけのカーネルになる (`PIX68K_NO_CPU020`)。

68030 / 68060 では、CPU を止めて周辺機器を進める間隔の上限を、X68000 の時間で 25.6us にしている (68030 は 640 サイクル、
68060 は 1280 サイクル。10MHz の 68000 の 256 サイクルと同じ時間。`Machine::run()`)。周辺機器の割り込みは、周辺機器を
進めたときに CPU に届くので、割り込みの要求が出てから CPU に届くまでの遅れは、割り込みの種類で次のようになる:

- ラスタに合わせて起きるもの (H-SYNC、V-DISP、CRTC のラスタ割り込み、V-DISP を数える MFP のタイマ A): その時刻で CPU を
  止めるので、要求が出たときに実行していた命令が終わったところで届く (68000 の機種も同じ)
- MFP のタイマ (ディレイモード) と OPM のタイマ: 要求を出す時刻を先に計算し、その時刻でも CPU を止める (`Machine::nextTimerIrq()`)。
  見るのは、割り込みが許可されていて (MFP の IER) マスクされていない (IMR) タイマだけ (OPM は、$14 の IRQEN が立っていて、
  MFP が GPIP3 の割り込みを受け付ける設定のとき)。MFP の GPIP から TDDR までのレジスタか、OPM の $10-$14 を書いた命令でも
  CPU を止めて、時刻を計算し直す (`Cpu020::endRun()`)。これで、要求が出たときに実行していた命令が終わったところで届く。
  ctest の `timer_irq_test` は、割り込みの処理ルーチンの最初の命令で MFP のタイマのカウンタ (1us ごとに 1 減る) を読んで確かめる:
  200us の周期のタイマ C では、要求が出てから読むまでがいつも 68030 で 2us、68060 で 1us (この時刻で止めないと 1us から 21us の間でばらつく)
- DMAC、FDC、SASI、SCSI、SCC、MIDI ボード、ネットワークボード、キーボード (MFP の USART): 時刻を先に計算していないので、
  次に周辺機器を進めるまで待つ。遅れは最大 25.6us (10MHz の 68000 と同じ)

68000 の機種は 256 サイクルごと (10MHz で 25.6us、16MHz で 16us) のままで、MFP と OPM のタイマの割り込みもその間隔まで遅れる。
Raspberry Pi 3 Model B+ (1.4GHz) でも 68030 25MHz は実時間で動く。Human68k のコマンド行で 1 フレームの処理は 8.4ms (16.7ms のうち)、
最高速モードでは 25MHz の 211% (52.75MHz 相当) まで上がった。起動とフロッピーディスクを読む間は 68000 より重く、
起動から 10 秒の区間で遅れたフレームが 130 あった。グラフィックの多いゲームはまだ確かめていない。
060turbo (`cpu=68060`) は Pi 3 でも起動するが、実時間には届かない (Human68k のコマンド行で 1 フレームの処理が平均 87ms。
68060 のサイクル数を実機に合わせる前の値。合わせたあとの Pi での値は未確認。1 フレームに実行する命令の数は、ホスト版で
数えるとコマンド行で前の 0.13 倍 (キャッシュ無効) から 0.37 倍 (キャッシュ有効)。[060turbo.md](060turbo.md) の「68060 のサイクル数」を参照)。
060turbo には Pi 4 か Pi 5 を使う。

確かめ方:

- XEiJ の `misc/instructiontest.x` (実機の 68030 の結果を持つ) を `build/run_x --cpu 68030 instructiontest.x all` で動かし、
  548 個がすべて通る (未定義のフラグも比べる `hard` の指定でも通る)。ctest の `m68030_instructiontest` はその一部を動かす
- `tests/m68k/musashi_diff.cpp` で Musashi の 68030 と 1 命令ずつ比べる。`tools/fetch_musashi.sh` で Musashi を
  `~/.cache/pix68k/musashi` に置くとビルドし、ctest の `musashi_diff` で 20 万命令を比べる (CI でも動かす)。
  違いはすべて、XEiJ と実機の結果に合わせた動きか、Musashi の誤りだった。命令ごとの違いの数と理由は
  `tests/m68k/musashi_expected.txt` に書き、これより増えたら失敗にする
- ctest の `x68k_boot_x68030` は X68030 で Human68k を起動して DIR を打つ

FPU (`src/m68k/fpu.*`、計算は `src/m68k/fpu_math.*`) は、拡張精度 (64 ビットの仮数) を整数で計算する。
単精度、倍精度、拡張精度、パック 10 進、整数のすべての形式を読み書きでき、超越関数は 128 ビットの仮数で計算して最後に 1 回だけ丸める。
精度:

- XEiJ の `misc/fputest.x` の既定の設定 (最後のビットの 1 単位 = 1 ulp までの差を許す) で、すべての命令が通る。
  XEiJ の説明書によると、fputest.x の期待値は計算で求めた値で、実機の 68882 の結果と一致するとは限らない (FMOVECR は次の項目)。
  丸め、例外のフラグ (アンダーフローを丸めの前に判定するか後か、正確な結果でも INEX2 を立てるかなど) も fputest.x の期待値に合わせた
- FMOVECR のマニュアルにないオフセット ($01〜$0A、$10〜$2F) は、FMOVE.X で書き出した値と条件コードを fputest.x の期待値に合わせた。
  XEiJ の説明書によると、fputest.x の FMOVECR の期待値は実機の値 (合わなければエラーにする)。$08 は、fputest.x では
  見分けられない bit62 を 0 にした (シグナリング NaN。FMOVE.X では bit62 を立てて書く)。bit62 の実機の値は確かめていない。
  このため、$08 を読んだあとの FMOVE.X や演算は FPSR の SNAN と AIOP を立て、SNAN の例外を許可していればベクタ 54 になる。
  $08 のほかのオフセットは次のとおり。
  - $09、$0A、$10〜$2F は、FMOVE.X で書き出した値が fputest.x の期待値 ($43F3/$E000…、$4072/$C000…、0) になる、
    正規化した形でレジスタに持つ。FMOVEM で書き出したときの形とレジスタの中の値は、実機で確かめていない
  - $03 は正規化しない形 ($2000/$7FFFFFFF…) のまま FMOVE.X で書き出す (fputest.x の期待値)
- 1 ulp の差も許さない `hard` でも、すべての命令が通る (`build/run_x --cpu 68030 fputest.x hard all` で 3028872 件)
- ctest の `fpu_math_test` は、四則演算と平方根が倍精度でホストの計算とビット単位で一致すること (4 つの丸めのモードすべて)、
  超越関数が libm との差 1 ulp 以内 (tan は 2 ulp。macOS の libm の tan が 2 ulp ずれる) に収まることを確かめる

できていないこと:

- MMU のアドレス変換はしない (レジスタの読み書きと PMOVE などの命令はあるが、変換は常に切ったまま)。X68030 の MPU は MMU のない MC68EC030
  (XEiJ の説明書 feature.htm の機種の節)
- 命令キャッシュとデータキャッシュの動き (CACR の値は保つが、キャッシュの内容は持たない)
- FPU と CPU の並行動作 (FPU が計算している間に CPU が先に進むこと)。FSAVE は NULL と IDLE のフレームだけを書く (命令の途中の状態は持たない)
- 68030 のサイクル数とメモリのウェイトは概算。I/O とスプライトの読み書きは、実機の si.r の system performance に合わせて
  1.6 マイクロ秒ごとの区切りまで待たせる ([060turbo.md](060turbo.md) の「X68030 と 060turbo の本体のバス」)。グラフィック VRAM とテキスト VRAM の
  ウェイトは入れていない
- バスエラーのフレームはいつも長いフレーム ($B)。RTE は命令を始めからやり直す (命令の途中で動かしたアドレスレジスタは、
  フレームを積む前に命令の始めの値に戻す)。処理ルーチンが SSW の DF を 0 にして RTE したときは、バスエラーになった
  アクセスだけを行わずに命令を終える。ただし、1 つの命令にバスエラーになるアクセスが 2 つ以上あると (MOVE.L (A0),(A1)
  で両方など)、毎回 DF を 0 にして RTE しても命令が終わらない。実機と違う点は `src/m68k/cpu020.cpp` の `pushBusFault()` の注釈を参照。
  処理ルーチンから見えるアドレスレジスタは命令の始めの値 (MOVE.L (A0)+,D0 のバスエラーなら A0 は進む前) で、
  MC68030UM はこの値を決めていないので、実機と同じかは分からない。RTE で戻らずに (An)+ の An からバスエラーの
  番地を知るソフト (メモリの大きさを調べるものなど) では、結果が実機と違うかもしれない
- FPU の例外は MC68881/MC68882 UM 6 章の表のとおり、FPn に書く命令の例外は次の FPU の命令 (FMOVEM、FMOVE の制御レジスタ、
  FSAVE、FRESTORE を除く) を始めるときに起こす。FMOVE FPn,<ea> の例外と BSUN はその場で起こす

X68030 で動かないソフト:

- Human68k 3.00 より前 (1.00、2.0x) で起動するディスク。たとえば Gradius (Human68k 1.00) や test_sion2 (Human68k 2.03) は、
  DOS コールの途中で止まる。Human68k 1.00 / 2.03 の DOS コール ($FFxx の命令。F ライン例外の処理ルーチンで受ける。2.03 では
  $7F58 から) は、例外のフレームを 68000 の 6 バイトとして読み (68030 は 8 バイト)、スーパーバイザモードから呼ぶと引数を
  2 バイトずれたところから読む。`_SUPER` もフレームを 6 バイトとしてコピーする。MPU の種類を見ていないため、実機の X68030 でも同じく止まるはず (実機では確かめていない)。
  68000 (`--cpu 68000`) で動かすか、Human68k 3.0x のディスクで起動する
