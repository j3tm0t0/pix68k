# 060turbo (68060)

060turbo の構成で動かす方法、68060 のサイクル数、X68030 と 060turbo の本体のバス、最高速モード。

文中の #番号 は、開発用の非公開リポジトリの issue と PR の番号。

`--cpu 68060` で、X68030 に 060turbo (68060 50MHz) を載せた構成で動かす。$10000000 から 060turbo のローカルメモリを置く
(`--local-mem MB`、既定 128MB、最大 256MB)。$10000000-$1FFFFFFF のうちメモリのないところは、読むと $FF で書き込みは捨てる
(060turbo.sys が書いて読み直して容量を調べるため)。`--ram MB` で本体のメモリを変えられる (既定 4MB、最大 12MB)。
ホスト版の SRAM の既定は `~/.cache/pix68k/sram060.dat`。ベアメタル版は `pix68k.cfg` に `cpu=68060`
(`local_mem=128` でローカルメモリの容量、SRAM は `SRAM060.DAT`)。

```sh
./build/pix68k --cpu 68060 --ram 12 -0 human060.xdf   # human060.xdf は 060turbo.sys を CONFIG.SYS で組み込んだ起動ディスク
./build/pix68k --cpu 68060 --clock 75 -0 human060.xdf # 68060 を 75MHz にする
./build/machine_bench --cpu 68060
```

68060 のクロックは 50MHz (既定、実機の 060turbo) と 75MHz から選べる。75MHz は、実機の 060turbo をオーバークロックして
使う人がいる構成。ホスト版は `--clock 75`、ベアメタル版は `pix68k.cfg` に `clock=75` (`cpu=68060` のとき。設定メニューの
Clock でも 50 / 75 を切り替えられる)。`clock=` は CPU ごとに読む: 68000 では 10 / 16、68060 では 50 / 75 で、CPU に合わない値
(`cpu=68060` で `clock=16` など。`clock=` を書かなければ 16 のまま) はその CPU の既定 (68060 は 50MHz) にする。
クロックで変わるものは次のとおり (`Machine::Config::setClockMHz`):

- X68000 の時間とサイクル数の換算は `Config::cpuHz` で行う。75MHz では X68000 の 1 秒が 7500 万サイクルで、周辺機器
  (MFP、OPM、画面のタイミングなど) の時間は 50MHz と同じ。命令のサイクル数 (MC68060UM の表) は変えないので、同じ時間に
  実行する命令の数は 1.5 倍になる
- 本体のバスに出す読み書き 1 回のサイクル数 (`busWait060`) は 6 から 9 にする。本体のバスは 68060 のクロックを上げても
  25MHz のままで、1 回 (25MHz の 3 クロック、120ns) の時間は変わらないため
- I/O の読み書きが終わる時刻をそろえる周期 (`busArea` の `period`、1.6 マイクロ秒) は、80 サイクルから 120 サイクルにする
  (下の「X68030 と 060turbo の本体のバス」。これも本体の時間で、クロックでは変わらない。si.r の system performance は 75MHz でも 177.82%)
- キャッシュを切ったときのメモリの読み書きの時間 (下の「68060 のサイクル数」) も、時間が同じになるようサイクル数を
  1.5 倍にする (本体のメモリ 10.5 → 15.75 サイクル、ローカルメモリ 6 → 9 サイクル)。ローカルメモリは、実機でクロックを
  上げたときの値が見つかっておらず、DRAM の時間で決まるものとした推定
- IOCS のワークの $0CB8 は、50MHz の 8333 をクロックに比例させて 12500 にする (cpuHz / 6000。si.r の表示は 75.0MHz)。
  IOCS `_MS_ONTM` の待ちのループの回数は $0CB8 から決まるので、1 単位は 75MHz でも 1ms になる (`iocs_wait060 --clock 75` で
  1000 単位 999.4ms)。75MHz の実機の 060turbo で $0CB8 がいくつになるかは確かめていない
- `speed060`、`max_speed_limit`、最高速モードの速さは、選んだクロックの実機の 68060 を 100 とした % (75MHz の 100 は、
  命令の速さでは 50MHz の 150 にあたる)。最高速モードのログと終了時の表示は「max speed: N% of a real 68060 (75 MHz)」になる。
  OSD とログの速さの % (実時間の何 % か) は X68000 の時間で数えるので、クロックによらず 100% が実時間
- ステートのヘッダには CPU のクロックが入っているので、50MHz と 75MHz のステートは互いに読まない (「CPU clock differs」)。
  ステートの版は変えていない

60MHz や 66MHz などは入れていない。足すときは `Config::valid060MHz()` と `settings.h` の `kClockValues` に値を足し、
設定メニューの切り替え (`menu.h` の `I_CLOCK`) を直す。時間で決まる値は上のとおり `cpuHz` から決まる。

IPL ROM は 68060 で動くもの (`IPLROM060.DAT`) を先に探し、なければ X68030 の `IPLROM30.DAT` を使う。
X68030 の IPL ROM (1.3) は 68060 にない命令 (MOVEP) を使い、060turbo.sys は IPL ROM のバージョンが 1.4 以上でないと
組み込まれない。そのため `IPLROM30.DAT` を使うときは、メモリの上で次の 6 つを変える (ファイルは変えない。`x68k/machine.cpp` の `patchIplFor060`):

- IOCS `_ROMVER` が返す値を $13921127 から $14921127 にする
- ベクタ 61 (未実装整数命令) が IPL ROM を指している間は、68060 にない整数命令をその場で実行する。060turbo.sys が
  060SP (Motorola の M68060 Software Package) を組み込んだ後は、060SP が実行する。その場で実行するときの CHK2 / CMP2 の
  未定義の N と V は、V を 0、N を Rn の符号にする (持ち主の決定)。資料の裏付けはない (060SP は N と V を変えない。68060 の実機の値もない)
- 起動時に IOCS のワークの MMU の有無 ($CBE) を「あり」にする (IPL ROM 1.3 は 68030 の命令で MMU を調べるので、
  そのままでは IOCS `_SYS_STAT` が MMU なしと答える)
- 起動時に IOCS のワークの $0CB8 (ROM の上の dbra のループの 1ms あたりの回数) を 8333 にする。実機の 060turbo は si.r が
  50.0MHz と表示し、si.r は $0CB8 x 6 を MHz の 1000 倍として表示するので、8333 は実機の表示から逆算した推定の値
  (実機の $0CB8 を読んだわけではない。IPL ROM 1.3 が pix68k で測る値は 16683。下の「68060 のサイクル数」)
- IPL ROM が CACR に書く 68030 の値 (ビット 0 = 命令キャッシュ、ビット 8 = データキャッシュ) を、68060 の CACR の EIC (ビット 15) と
  EDC (ビット 31) に読み替える (起動時、IOCS `_SYS_STAT` のキャッシュの設定と取得、IOCS `_MS_ONTM` / `_MS_OFFTM` の待ちのループ)。
  そのままでは 68060 のキャッシュが無効になる。待ちのループの前 (68030 では命令キャッシュだけ有効) は、EIC と EDC の両方を
  立てる (68060 では本体のメモリの読み込みがデータキャッシュなしだと遅く、待ちが長くなりすぎるため)。060turbo の ROM が
  どうしているかは資料がなく、どれも推定の手当て。実機 (060turbo.sys がキャッシュを設定した 68060) とは次のところが違う:
  起動時と `_SYS_STAT` の設定は EIC と EDC だけを決め、ストアバッファ (ESB) と分岐キャッシュ (EBC) は有効にしない
  (060turbo.sys を組み込むと、060turbo.sys が設定し直す)。待ちのループの間は ESB と EBC が落ちる (終わると戻る)。
  待ちのループの回数を決める定数 (`divu.w #834,d2`。$FFAC6E、$FFACDA) は 583 に書き換える。68060 ではループの 1 周の
  サイクル数が違い (EIC と EDC が有効で約 35 サイクル)、834 のままだと 1 単位が 1ms でなく約 0.70ms になるため。
  実機の待ちの長さは分かっていない (下の「68060 のサイクル数」)。
  IPL ROM がキャッシュを消すために $0808 を立てて書く所は、68060 ではキャッシュを消さない
- SCSI IOCS のデータの転送を、バッファが本体の 16MB の外 (ローカルメモリ) にかかるときはソフト転送にする。DMAC は
  本体のバスの 24 ビットのアドレスしか出せないので、DMA のままではローカルメモリの代わりに本体のメモリを読み書きする。
  060turbo.sys の拡張モード (`-xm`) は Human68k のメモリをローカルメモリに広げるので、これがないと SCSI のディスクから
  COMMAND.X を読み込んだところで止まる

フロッピーディスクの読み書き (DMAC のチャネル 0) には IPL ROM にソフト転送がないので、ROM は書き換えず、68060 のときは
IPL ROM によらず (`IPLROM30.DAT` でも `IPLROM060.DAT` でも)、チャネル 0 の MAR がローカルメモリの中を指していれば、DMAC の
転送をローカルメモリへ届ける (`x68k/machine.cpp` の `dmaMemAddr`)。IPL ROM 1.6 もフロッピーディスクは DMA で読むので、
`-xm` で COMMAND.X の読み込み先がローカルメモリになると、これがないと止まる。内蔵 SCSI と SASI (チャネル 1) も、68060 の
ときは同じ扱いにする。`IPLROM060.DAT` と組で使う `ROM30_060.DAT` の SCSI IOCS は、バッファがローカルメモリでも DMA で
転送するので、SCSI のディスクから `-xm` で起動すると、これがないと本体の例外ベクタを書いて止まる (#167)。`IPLROM30.DAT` の
ときは上の SCSI IOCS の書き換えでソフト転送になるので、チャネル 1 にローカルメモリのアドレスは来ない。
ローカルメモリの範囲 ($10000000-$1FFFFFFF) のうち SIMM を積んでいないところは、
CPU から見たときと同じく、読むと $FF で、書いても変わらない (本体のメモリには折り返さない)。チャネル 2 と 3 と、ほかの構成では、
MAR の下位 24 ビットだけを使う。

SCSI の書き換えとフロッピーディスクの扱いは、060turbo の ROM や実機の動きを写したものではなく (実機の DMAC はローカルメモリに
届かない)、エミュレータの側の互換の処理。SCSI の書き換えは `IPLROM30.DAT` を 68060 で使うときだけ、フロッピーディスクと
チャネル 1 の扱いは 68060 のときいつも行う。060turbo の ROM や、IPL ROM 1.6 を使う実機・XEiJ が、ローカルメモリへの転送をどう扱うかは
確かめていない。060turbo.sys には `-dv` (デバイスドライバの転送を、DMA の届く転送バッファ経由にする。大きさは `-bs`、
既定 64KB) があり、`-xm -dv` なら、この互換の処理がなくても IPL ROM 1.3 でも 1.6 でも起動する (060turbo.sys 0.56 を
逆アセンブルして確かめた)。実機は `-xm` だけではフロッピーディスクから起動せず、`-dv` が要る見込み (逆アセンブルからの
推定で、実機では確かめていない)。フロッピーディスクの互換の処理は `-dv` の代わりで、`-dv` なしでも起動できるようにする
ためのもの。SCSI も同じで、060turbo.sys の SCSI IOCS を包む処理は `-ss` (と `-np`) のフラグが立っていなければ何もせず、
`-xm` は `-ss` のフラグも `-dv` のフラグも立てない (0.56 と 0.61 を逆アセンブルして確かめた)。
`IPLROM060.DAT` と `ROM30_060.DAT` では、`-xm -ss` でも `-xm -dv` でも、チャネル 1 の互換の処理なしで SCSI のディスクから
起動した。`-xm` だけでは実機でも止まる見込み (推定で、実機では確かめていない)。X68000 の側のメモリは使わない。MAR やバッファのアドレスをそのまま物理アドレスとして見るので、060turbo.sys の `-ls`
などで 16MB より下の論理アドレスをローカルメモリに割り当てた場合は扱わない。060turbo.sys 0.61 (2025-10-31) は、
IOCS `_SCSIDRV` のベクタが IPL ROM の中 ($00FFxxxx) を指しているときは、`-ss` を付けても SCSI IOCS を差し替えない
(060turbo.sys を逆アセンブルして確かめた。`-xm -ss` でも同じところで止まる)。

SRAM が空のとき (SRAM のファイルを新しく作るとき) は、060turbo ではキャッシュの設定 ($ED0090) を命令・データとも有効 (3) に
する。X68030 の IPL ROM が空の SRAM に書く初期値では 0 (どちらも無効) で、060turbo.sys はこの値に従って CACR を設定する。
中身のある SRAM は変えない (SWITCH.X などで変えた設定はそのまま使う)。

`IPLROM060.DAT` には XEiJ の IPLROM 1.6 (060turbo のときに XEiJ が組み立てる IPL ROM) が使える。XEiJ のライセンスに従い、
ROM はリポジトリにも配布物にも入れない。各自が XEiJ から次のどちらかで取り出す:

- XEiJ を 060turbo の構成 (`-model=060turbo -iplrom16=on`) で起動し、メニューの「ROM ファイルの作成」で `XEIJIPLROM.DAT`
  ($FE0000-) と `XEIJROM30.DAT` ($FC0000-) を作る (XEiJ の説明書 iplrom16.htm)
- `python3 -I tools/make_romdump_dir.py ~/.cache/pix68k/disk/HUMAN302.XDF romdump` で、ROM を書き出すプログラム
  (`ROMDUMP.X`) を自動で動かす Human68k の起動ディレクトリを作り、
  `java -jar XEiJ.jar -model=060turbo -iplrom16=on -boot=hf0 -hf0=romdump` で起動する。`romdump` に `IPLROM.DAT` ($FE0000-) と
  `ROM30.DAT` ($FC0000-) ができる (XEiJ のウィンドウを前に出していないと進まないことがある)

できたファイルを `~/.cache/pix68k/rom/IPLROM060.DAT` と `ROM30_060.DAT` (ベアメタル版は SD カードの `/pix68k/IPLROM060.DAT`) に置く。
`ROM30_060.DAT` はホスト版と `x68k_boot` が $FC0000 からの ROM として読む (なければ X68030 と同じく IPL ROM から作る)。

68060 の違い (MC68060UM による):

- 68060 にない整数命令 (MOVEP、CHK2 / CMP2、CAS2、ずれたアドレスの CAS、64 ビットの MULU / MULS / DIVU / DIVS) はベクタ 61
- FPU にない命令 (超越関数、FMOD / FREM、FSCALE、FGETEXP / FGETMAN、FMOVECR、FScc、FDBcc、FTRAPcc など) はベクタ 11
  (フォーマット $2)、FPU が扱わない実効アドレス (#imm の拡張精度とパック 10 進、FMOVEM の動的なリスト) はベクタ 60、
  パック 10 進はベクタ 55。FSxxx / FDxxx、FSAVE / FRESTORE の 3 ロングのフレーム、PCR の DFP、条件の OR と NE の式も 68060 に合わせた
- 非正規化数・非正規化の値のオペランドはベクタ 55。アンダーフローと (丸める前にあふれる) オーバーフローは、許可されていなくても
  ベクタ 51 / 53 の例外にし、060FPSP に結果を作らせる (MC68060UM 6.5.2、6.6.4、6.6.5)。FPn に書く命令では、これらと、許可した
  SNAN / OPERR / DZ / INEX は EXCP の状態にするだけで、次の FPU の命令 (FSAVE 以外) を始めるときに例外にする (実機と同じく、
  例外の処理ルーチンが最初に FSAVE をしないと、FPU の命令のたびに同じ例外が起き続ける)。FMOVE OUT では
  すぐに命令の後の例外 (フォーマット $3) にする。拡張精度とパック 10 進の (An)+ / -(An) では An を動かさず、060FPSP が直す形の
  アドレスを積む
- 例外のフレームのフォーマット ($0 / $2 / $3 / $4。アクセスエラーは FSLW を持つ $4)。アクセスエラーなどで命令をやり直すときは、
  A0-A7 と CCR を命令の始めの値に戻してから例外にする ((An)+ / -(An) のほか、PEA、JSR、BSR、LINK、MOVEM -(An)、MOVE16 で
  動かした分も。68060 は命令を最初からやり直す)。ページの表を引く途中のバスエラーでは、もとのアクセスのアドレス、読み書き、FC、
  大きさを積む。ページをまたぐアクセスは、分けたうちのどこでエラーになっても元のアドレスと大きさを積み、FSLW の MA を立てる。
  MOVES で FC 0 / 3 / 4 / 7 を読み書きするときは、その FC を Bus に渡し、FSLW の TT を 2 にする
- 制御レジスタ (PCR、BUSCR、URP / SRP、TC、ITT / DTT、CACR)、MMU のアドレス変換 (ページテーブル、透過変換、ATC)、
  PFLUSH / PLPA、MOVE16、CINV / CPUSH (キャッシュの内容は持たないので何もしない)、LPSTOP、MOVES の FC の扱い
- サイクル数は、命令ごとに M68060 User's Manual (M68060UM/AD) の 10 章 Instruction Execution Timing の表の値を使う
  (下の「68060 のサイクル数」)。ローカルメモリ、本体のメモリ、ROM の読み書きには、CACR で命令キャッシュ / データキャッシュが
  有効な間はウェイトを入れない (キャッシュに当たったものとする)。無効な間は 1 回ごとにバスの時間を足す (下の節)。
  I/O、グラフィック VRAM、テキスト VRAM への書き込みは、キャッシュの設定によらず本体のバスを
  通るので、1 回 6 サイクル (50MHz。75MHz では 9 サイクル) を足す (`Machine::Config::busWait060`)。68030 の非同期バスの 1 回の読み書きは 25MHz で
  最低 3 クロック (50MHz の 6 サイクル) かかるため。I/O の読み書きは、そのあと本体の 1.6 マイクロ秒ごとの
  区切りまで待つ (`Machine::Config::busArea`。下の「X68030 と 060turbo の本体のバス」)。スプライトと VRAM は、本体のバスで延びる分が分からないので入れていない

確かめ方:

- `build/run_x --cpu 68060 instructiontest.x all`: 522 個がすべて通る (run_x には 060SP がないので、68060 にない命令はその場で実行する)
- `build/run_x --cpu 68060 fputest.x`: 68060 の FPU にある命令はすべて通る
- 060turbo.sys 0.56 を組み込んだ Human68k を起動し、DIR を打てる。その中で fputest.x を 060FPSP で動かした結果は issue #10 の PR の本文に書いた
- ctest: `m68060_instructiontest`、`m68060_fputest`、`x68k_boot_060turbo_plain`、`x68k_boot_060turbo_sys`、
  `x68k_boot_060turbo_xm` (拡張モード `-xm` でフロッピーディスクから起動する)、`x68k_boot_060turbo_xm_scsi` (同じく
  SCSI のハードディスクから)、`x68k_scsi_local_mem` と `x68k_scsi_local_mem_stack` (SCSI IOCS とフロッピーディスクの IOCS でローカルメモリへ読み書きする。
  後者はスーパーバイザスタックもローカルメモリに置く)、`x68k_boot_060turbo_75mhz_plain` と `x68k_boot_060turbo_75mhz_sys`
  (75MHz で、060turbo.sys なしとありで起動する)
  (060turbo.sys を `~/.cache/pix68k/060turbo/060TURBO.SYS` に置く。なければ飛ばす)

## 68060 のサイクル数

68060 の命令にかかるサイクル数は、M68060 User's Manual (M68060UM/AD、Motorola 1994) の 10 章の表から作った
(`src/m68k/cpu060_cycles.inc`。オペコードごとの表は起動時に作る)。使った節と表:

| 節 | 表 | 内容 |
|---|---|---|
| 10.1.2 - 10.1.6 | 10-1 - 10-4 | 2 命令の同時実行 (スーパースカラ) の分類と条件 |
| 10.4 | 10-5 | 実効アドレス ((bd,An,Xi) は +1、メモリ間接は +3。ほかは 0) |
| 10.5 | 10-6 - 10-8 | MOVE、MOVE16 |
| 10.6 - 10.8 | 10-9 - 10-12 | ADD などの演算、乗除算 (MULx 2、DIVx.W 22、DIVx.L 38)、イミディエイト、単項、CLR |
| 10.9、10.10 | 10-13 - 10-16 | シフト、ビット操作、ビットフィールド |
| 10.11 | 10-17 - 10-19 | Bcc / BRA / BSR / DBcc、JMP / JSR、RTD / RTE / RTR / RTS |
| 10.12 - 10.14 | 10-20 - 10-24 | LEA / PEA / MOVEM、ADDX など、SR の命令、MOVES、MOVEC、NOP、STOP など |
| 10.15 | 10-25 | FPU (FADD 3、FMUL 3、FDIV 37、FSQRT 68、FMOVE 1 など) |
| 10.16 | 10-26 | 例外 (19、割り込みは 23) |

- 分岐は、分岐キャッシュ (CACR の EBC) の予測が当たったか外れたかで変える (表 10-17: Bcc は当たって分岐すれば 0、分岐しなければ 1、
  外れれば 7。予測がなければ後ろ向きの分岐は 3、前向きで分岐しなければ 1)。当たって分岐するときの 0 サイクルは、分岐でない命令と
  同じサイクルに折りたたまれる場合の値 (10.1.2) なので、分岐でない命令をはさまずに分岐が続くときは 1 つ 1 サイクルにする。分岐キャッシュは 256 個の表で、命令のアドレスごとに
  2 ビットの飽和カウンタを持つ (マニュアルの 5.11 は「5 つの状態」とだけ書いていて、移り方は書いていないので、ここは概算)。
  CACR に CABC を書くと全部、CUBC を書くとユーザモードで覚えた分岐を消す (5.2)。CINV / CPUSH で命令キャッシュを無効にした
  ときに一緒に消えること (5.11) は入れていない
- スーパースカラ (PCR の ESS が 1 のとき) は、表 10-2 の分類と、10.1.3 から 10.1.6 の条件のうちオペコードの 1 語めで決まるもの
  (sOEP で使えない PC 相対、メモリの読み書きは 2 命令で 1 つ、前の命令の結果のレジスタを後の命令が使わない) を見て、
  前の命令と同時に進む命令を 0 サイクルにする。インデックスレジスタと、フルフォーマットの拡張語かどうかは見ない。
  リセットのあとは ESS が 0 で、060turbo.sys が 1 にする
- MOVEM と FPU の命令は、サイクル数を命令の中で足す (MOVEM はレジスタ 1 つに 1 サイクル)。命令の中で 1 サイクルも
  足さなかった命令 (レジスタの数が 0 の MOVEM など。マニュアルの式では 0 サイクルになる) は 1 サイクルにする。これは近似で、
  分岐でない命令が必ず時間を進めるようにするため (0 サイクルに折りたたまれる分岐と組み合わせたループで、時間が進まなく
  なるのを防ぐ)
- 同時実行の表と、命令の間の状態の確かめ (`cpu060_test`):
  - `testTableAgainstExecution`: 同時実行に関わるすべてのオペコード (同時実行の相手にできる命令と、sOEP に入れる命令。
    34871 個) を 1 命令ずつ、値を変えて 2 回実行し、(1) データの読み書きをしたかどうかと表の「メモリの読み書きあり」、
    (2) 値が変わったレジスタが「書くレジスタ」に入っていること、(3) 「使うレジスタ」にないレジスタの値を変えても結果が
    変わらないこと、を比べる。見ないもの: サイクル数そのもの、同時実行に関わらない命令 (pOEP-only) と例外になる
    オペコード、インデックスレジスタ (表が見ないと決めている)、`MOVE.L <ea>,Dn` の Dn (10.1.6 の例外 1 で、書く
    レジスタに入れていない)、実行しても値が変わらなかったレジスタ、同じレジスタを書く 2 命令の組
  - `testRandomSequences`: 30 種類の命令からランダムに作った並び (400 個) を続けて実行し、命令ごとのサイクル数を、
    「数え方の状態を消してから 1 命令ずつ実行したときのサイクル数」と上の規則 (同時実行と、分岐の折りたたみ) から
    計算した値と比べる。命令と命令の間で、規則にない形でサイクル数が変わらないことを見る。見ないもの: Bcc / DBcc /
    JMP / JSR (分岐は BRA だけ)、例外と割り込み (別の試験)、命令キャッシュが無効のときの取り出し (別の試験)
- CACR で命令キャッシュ (EIC) / データキャッシュ (EDC) を切っているときは、命令の取り出し (命令の並びが新しいロングワードに
  入るたび、分岐のあとは同じロングワードでも) とデータの読み書きの 1 回ごとに、バスの時間を足す (`Cpu020::updateCacheCosts`)。
  本体のメモリと ROM は 10.5 サイクル、060turbo のローカルメモリは 6 サイクル (どちらも 50MHz の値。75MHz では時間が同じに
  なるよう 15.75 サイクルと 9 サイクル)。本体のメモリの値は、下の実機の 410% に
  合わせて決めた (1 周に取り出し 2 回とデータの読み出し 1 回で、1 + 3 x 10.5 = 32.5 サイクル)。ローカルメモリは実機の値が
  見つからず、マニュアルの 10.3.4 の「2 + w」で 60ns の DRAM の読み出しを w = 4 クロックとした仮の値。
  キャッシュが有効なら、いつも当たるものとして足さない (キャッシュの中身は持たない)。バスの時間なので、下の `speed060` と
  最高速モードの倍率は掛けない。I/O とグラフィック VRAM (Bus に出す読み書き) には、この時間は足さない (上の `busWait060` と、
  I/O の `busArea`)。
  命令の取り出しとデータの読み書きを同じ 10.5 サイクルとしたこと、si.r が本体のメモリに読み込まれていたとしたことは仮定
  (実機の値が 1 つしかなく、2 つを分けられない)
- 数えていないもの: ATC のミス、整列していないアクセス、レジスタを書いた直後にアドレスの計算に使うときの待ち (10.2 の 3)、
  「<= k」と書かれた命令 (DIVx.W、CINV、CPUSH) の値による違い、FPU のオペランドの形 (整数、拡張精度) による +3 / +2

- processor performance のループは `addq.l #1,d0` / `tst.b (a0)` / `bne` (si.r のソース。[kg68k/si-ee](https://github.com/kg68k/si-ee))。
  表の値は 1 + 1 + 0 (予測が当たった分岐) で、前の 2 つは同時に進むので 1 周 1 サイクル。実機の 13348% は、XVI 10MHz の
  1 周 26.8 クロック (2.68 マイクロ秒) の 1/133.5 で、50MHz の 1.0 サイクルにあたる。実機の 410% は 1 周 約 32.4 サイクル。
  前の数え方 (68000 のサイクル数の 1/5) は 1 周 3.6 サイクルで、キャッシュが有効の実機の約 1/3.6、無効の実機の約 9 倍の速さだった
- si.r の MHz の表示は、68020 以上では測った値ではなく、IOCS のワーク ($0CB8。ROM が起動時に dbra の空ループを 1ms に
  何回回せるかを入れる) の 6 倍 (68030 の dbra は 6 クロックという前提)。060turbo.sys 0.56 のバイナリの中で $0CB8 を指すのは
  読み出しの 1 か所 (6 倍して返す処理) だけで、書き込みはない。実機の 50.0MHz ($0CB8 = 8333) は、060turbo の ROM 1.50 が
  入れた値と考えられる (測った値か決めた値かは未確認)。pix68k は、IPL ROM が測った値を 8333 に置き換える (上の
  `patchIplFor060` の説明)。置き換えなければ、IPL ROM が起動時に dbra のループで測った値が入る。測るときは命令キャッシュと
  データキャッシュが有効で (IPL ROM が起動時に有効にする)、分岐キャッシュは無効なので、dbra の 1 周は表 10-17 の
  「予測なし、後ろ向き」の 3 サイクルになり、$0CB8 は 16683、表示は 100.1MHz になる (8333 に置き換える処理だけを外して
  測った値)。50MHz と表示させるには 1 周を 6 サイクルにしなければならず、表の値と合わないので、サイクル数の側では
  合わせていない
- X68030 の IPL ROM (1.3) の IOCS `_MS_ONTM` / `_MS_OFFTM` の待ちのループ ($FFAC86 から) は、$0CB8 から回る回数を決める
  (1 単位は $0CB8 x 100 / 834 周。68030 では 1 周 50 クロックで、1 単位 1ms)。回っている間は CACR に 1 (68030 の
  「命令キャッシュだけ有効」) を書く。68060 にそのまま書くと、1 はどのキャッシュのビットでもないので、命令キャッシュ、
  データキャッシュ、分岐キャッシュがすべて無効になる (1 周 294 サイクル、1 単位 約 5.9ms)。pix68k は、この値を 68060 の
  EIC と EDC に読み替え (1 周 約 35 サイクル、834 のままなら 1 単位 約 0.70ms)、回数を決める 834 を 583 に書き換えて、
  1 単位を 1ms にする (上の `patchIplFor060` の説明。`iocs_wait060` で測ると 1000 単位で 999.5ms。ctest は 950ms から
  1050ms に入ることを確かめる)。1ms は IOCS の呼び出しの決まりの長さで、実機の 060turbo で測った値ではない。実機は ROM が
  違い (IPL ROM 1.50)、060turbo.sys 0.56 は `_MS_ONTM` / `_MS_OFFTM` を差し替えない (組み込んだあとも IOCS のベクタは
  ROM のまま) ので、実機の待ちの長さは ROM 1.50 の作りで決まる。その作りと、実機で測った値は見つかっていない
- IPL ROM 1.6 (68060 で動く IPL ROM) では、`_MS_ONTM` / `_MS_OFFTM` の 1 単位は 1ms にならず、50MHz で約 2.17ms、
  75MHz で約 3.12ms になる (`iocs_wait060 --any-rom` で 1000 単位 2170.7ms と 3117.0ms。#123)。pix68k は ROM に手を入れて
  いない (`patchIplFor060` は 1.3 のときだけ書き換える)。逆アセンブルで確かめた理由は次のとおり:
  - 回数の決め方は 1.3 と同じ ($FFAC6E と $FFACDA の divu.w #834。1 単位は $0CB8 x 100 / 834 周)
  - $0CB8 は、ROM が起動時に MFP のタイマ C / D で dbra のループの時間を測り、68060 では「1ms に回る回数 / 6」を入れる
    ($FEA930 からの MPU ごとの定数の表)。pix68k では 50MHz で 8329、75MHz で 12495 で、クロックに比例している
  - 回っている間のキャッシュは、ROM の $FEC706 が 68030 と同じ「命令キャッシュだけ有効」を 68060 の CACR に直して書く
    (EIC は立て、EDC は落とす。`iocs_wait060 --any-rom` が出すループの間の CACR は $20808000)。データキャッシュが
    無効なので、1 周に本体の RAM ($0A7A からの IOCS のワーク) を 9 回読み、どれも本体のバスに出る
  - 本体のメモリの読み出し 1 回は 210ns (50MHz の 10.5 サイクル。この節の上の、実機の si.r のキャッシュ無効の値から決めたもの) なので、
    1 周は 9 x 210ns = 1.89 マイクロ秒に、CPU の約 14 サイクルを足した長さになる (50MHz で約 2.18 マイクロ秒、
    75MHz で約 2.08 マイクロ秒)。周の数はクロックに比例して増えるのに、1 周の長さはほとんど縮まないので、75MHz の方が長い。
    試しに読み出し 1 回を 0 にすると 1000 単位 280ms、6 サイクル (120ns) にすると 1359ms で、この見積もりと合う
  - 本体のバスの最短のバスサイクル (120ns) でも 1 単位は約 1.36ms (上の 1359ms。バスの時間だけで約 1.08ms、それに CPU の
    サイクルが加わる) で、本体のメモリをデータキャッシュなしで読む限り、
    060turbo でこのループが 1ms になることはない。2.17ms という値は ROM の作りと、si.r から決めた読み出しの時間から出したもので、
    IPL ROM 1.6 を積んだ実機の 060turbo で測った値ではない
  1.3 のように回数を書き換えて 1ms にすることはしない。1.6 はもともと 68060 で動かすための ROM で、待ちの作りはその ROM の
  ままにした。1ms に合わせるなら、834 をクロックごとに変える (50MHz で約 1810、75MHz で約 2600) ことになる
- system performance と machine performance (RTC を読むループ。割り込みを止めて測るのが system、止めずに測るのが machine) は、
  I/O の読み書きを 1.6 マイクロ秒ごとの区切りにそろえて実機に合わせた (下の「X68030 と 060turbo の本体のバス」)。前は `busWait060`
  (120ns) だけで、キャッシュが有効のとき 2032.27%、無効のとき 508.07% だった
- cpupower.r (TOMY さん。XVI 10MHz 比) は、キャッシュが有効のとき CPU 7150.00%、I/O ($E8A001) 736.36%、GV-RAM 663.64%、
  TV-RAM 3850.00%。無効のとき CPU 325.00%、I/O 289.29%、GV-RAM 260.71%、TV-RAM 220.00%。前はどちらの設定でも
  CPU 2860.00%、I/O 675.00%、GV-RAM 608.33%、TV-RAM 3850.00%。実機の 060turbo の cpupower.r の値は見つけられなかった
  (これらは I/O を 1.6 マイクロ秒ごとの区切りにそろえる前の値で、そのあとは測り直していない。I/O は RTC を続けて読むので、
  1 回 1.6 マイクロ秒になり、XVI 10MHz の約 1.01 マイクロ秒に対して 63% 前後になるはず)
- 命令ごとの表を持たずに、68000 のサイクル数を一定の割合に縮める概算は採らなかった。その方式では実機の si.r の値と
  合わないので、実機の値を優先した

1 フレーム (50MHz の約 90 万サイクル) に実行する命令の数 (ホスト版に数える変数を足して測った) は、キャッシュの設定で
大きく変わる。

測ったときの条件:

- 「今」の値は、周辺機器を進める間隔の上限を 25.6us にし、MFP と OPM のタイマの時刻で CPU を止めるようにしたあと

- コマンド行の 2 つの値は、060turbo.sys 0.56 を組み込んだディスクを `x68k_boot --cpu 68060 --ipl IPLROM30.DAT` で起動し、

  060turbo.sys が有効にする
- machine_bench の値は、`machine_bench -s 5 --cpu 68060 --ipl IPLROM30.DAT` (ディスクは HUMAN302.XDF、SRAM は空から始まり
  $ED0090 は 3) で、場面を boot、idle、cpu、user、gfx、fd の順に続けて動かしたときの値。060turbo.sys を組み込まないので、

  (idle は 130123)。前は `-s 3` で $80008000 だった (割り込みの届く時刻が変わり、切り替わる時刻がずれた)
- コマンド行で待っている間は、CACR のデータキャッシュのビット (EDC) が何度も切り替わる (060turbo.sys なしでは $80008000 と
  $00008000、ありでは $A0808000 と $20808000 の間。IPL ROM の CACR の読み替えを入れる前に数えて、1 フレームに約 690 回)。
  場面を始めた時点でデータキャッシュが無効だと、値が変わる。boot の直後 (900 フレームめ) は $00008000 で、
  `machine_bench ... cpu` のように boot のすぐあとに cpu を動かすと、1 フレーム 約 186000 命令になる
- コマンド行でキャッシュが有効のときに前より少ないのは、上の切り替わりで、データキャッシュが無効の間のデータの読み書きに
  バスの時間が足されるため。実行する命令の内訳は、バスの時間を足さない数え方 (359305) と同じで、回る回数だけが
  約 1/3 になる。$0CB8 を書き換えても命令の数は変わらなかった。どのプログラムが CACR を書いているかは調べていない

速さは設定で変えられる。ホスト版の `--speed060 N`、`pix68k.cfg` の `speed060=N` (5 から 3200、既定 100) で、68060 の命令の速さを
実機の N% にする (1 サイクルの長さを 100/N 倍にする。命令どうしの比は変わらない)。100 より小さくすると実機より遅くなり、
ホストの負荷が下がる。`machine_bench --cpu 68060 --speed N` も同じ単位。

## X68030 と 060turbo の本体のバス

060turbo の 68060 は、ローカルメモリ以外 (本体のメモリ、VRAM、I/O) を X68030 の本体のバスを通して読み書きする。
pix68k が足す時間は 2 つ (`Machine::Config`):

- `busWait060`: Bus に出す読み書き 1 回 (16 ビット) に 120ns (50MHz の 6 サイクル、75MHz の 9 サイクル)。68030 の非同期の
  バスサイクルの最短 (25MHz の 3 クロック)。I/O、スプライト、グラフィック VRAM、テキスト VRAM への書き込みに足す
- `busArea`: I/O ($E80000-$EAFFFF、$EC0000-$ECFFFF) の読み書きは、上の 120ns のあと、
  1.6 マイクロ秒ごとの区切り (電源を入れてからの時間を 1.6 マイクロ秒で割り切れる時刻) まで待つ。外付け SCSI ボードの ROM
  ($EA0020-$EA1FFF) は I/O の範囲にあるが、ほかの ROM と同じく待たせない
- スプライト ($EB0000-$EBFFFF) は、既定では区切りまで待たせない。このとき足す時間は機種で違う。060turbo は
  `busWait060` の 120ns だけを足す。X68030 は何も足さない (X68030 の 120ns は、区切りまで待たせる場所にだけ、
  区切りを待つ前の時間として入れているので)。pix68k.cfg の `bus_sync_sprite=on` (ホスト版は `--bus-sync-sprite`) で、
  どちらの機種も I/O と同じく、120ns のあと 1.6 マイクロ秒ごとの区切りまで待たせられる。スプライトの 1.6 マイクロ秒は
  実機で測った値ではなく、RTC と同じとした仮定。前はこれを既定にしていたが、スプライトを多く書く CBX68 (Outrun) が
  1 フレームの間に書き終えられなくなり、スプライトが崩れたり消えたりしたので、既定から外した (#218)
- 本体のバスは 16 ビットなので、32 ビットの読み書きは 2 回に分かれる。待つ場所を続けて読み書きする場合、32 ビットあたり
  3.2 マイクロ秒かかる (最初の 1 回は、区切りまでの残りの時間だけ待つので短くなる)
- DMA の転送 (DMAC がするメモリと I/O の読み書き) には、どちらの時間も足さない (足すのは CPU の読み書きだけ)

どちらも本体の時間で決まるので、68060 のクロック (50 / 75MHz)、`speed060`、最高速モードでは変わらない。

`busArea` は、場所の種類ごとの表になっている。種類は、グラフィック VRAM、テキスト VRAM、I/O のデバイスごと (CRTC、DMAC、
MFP、RTC、OPM、FDC、SCC など、8KB ごと)、拡張スロット ($EC0000-$ECFFFF)。同じ 8KB の中でも、パレット ($E82000-$E823FF) と
ビデオコントローラ ($E82400 から)、スプライトのレジスタ ($EB0000-$EB07FF) と BG のレジスタ ($EB0800 から) は分ける。
スプライトの残りは PCG ($EB8000-$EBBFFF) と BG のテキストエリア ($EBC000-$EBFFFF)。種類ごとに、読みと書きで別に `pre`、
`period`、`post` (ns) を持ち、読み書き 1 回が終わる時刻を「(始まる時刻 + `pre`) を `period` の倍数に切り上げ + `post`」とする
(`period` が 0 なら切り上げない)。`pre` だけなら長さの決まった待ち、`period` だけなら上の区切りになる。
今の既定は、I/O の種類がどれも `period` = 1600 (68030 は `pre` = 120 も)、VRAM とスプライト (スプライトのレジスタ、
BG のレジスタ、PCG、BG のテキストエリア) は全部 0。`bus_sync_sprite=on` なら、スプライトも I/O と同じ値になる。場所ごとの実機の値が分かったら、この表の値だけを変える。`period` は、CPU のサイクル数に直した値が
240 の約数になるようにする (下の、ステートを読むときの時刻の直し方のため)。

X68030 (68030 25MHz) にも同じ表を使っている (25MHz の 40 サイクルごと)。待つ場所は 060turbo と同じ (スプライトは `bus_sync_sprite=on` のときだけ)。
060turbo と同じく、待つ場所の読み書き 1 回には先に 120ns (3 クロック) を足してから、次の区切りまで待つ。足さないと、
32 ビットの読み書きの 2 回目が 1 回目と同じ区切りで終わってしまう。待たない場所 (VRAM など) には何も足さない。

1.6 マイクロ秒の出どころは、実機の si.r の system performance。si.r のループは `addq.l #1,d1` / `cmp.b (a0),d0` / `beq` で、
a0 は RTC の秒のレジスタ ($E8A001)。100% は 1 秒に 351472 周 (si.r のソースの定数。[kg68k/si-ee](https://github.com/kg68k/si-ee))。
実機の値 ([X68030 / 040turbo / 060turbo のキャッシュとパフォーマンス](http://tomoretropc.blogspot.com/2020/06/x68030-040turbo-060turbo.html)):

| 機種 | 命令 / データキャッシュ | processor | system | machine |
|---|---|---|---|---|
| X68030 (25MHz) | off | 261.59% | 177.81% | 176.13% |
| X68030 (25MHz) | on | 554.13% | 177.82% | 176.61% |
| 040turbo (25MHz) | off | 345.41% | 175.78% | 175.25% |
| 040turbo (25MHz) | on | 1672.83% | 177.82% | 177.65% |
| 060turbo (50MHz) | off | 413.36% | 177.81% | 177.32% |
| 060turbo (50MHz) | on (060turbo.sys なし) | 818.65% | 177.82% | 177.52% |
| 060turbo (50MHz) | on | 13349.22% | 177.82% | 177.34% |

177.82% は 1 秒に 625000 周で、1 周がちょうど 1.6 マイクロ秒 (10MHz の 16 クロック)。CPU の種類やキャッシュの設定で
命令の時間は 1 周 0.02 マイクロ秒から約 1 マイクロ秒まで変わるのに、system は変わらない。RTC の読み出しが
「CPU が読み始めてから決まった時間で終わる」のなら、命令の時間の分だけ値が変わるはずで、たとえば 1 回 1580ns を足すだけの
作りでは、キャッシュが有効のとき 177.82% でも、無効のときは 140.85% になる (ホスト版で測った)。そこで、読み書きは本体の側の
1.6 マイクロ秒ごとの時刻で終わるものとした。こうすると、命令の時間と 120ns の合計が 1.6 マイクロ秒より短いかぎり、
1 周はいつも 1.6 マイクロ秒になる。

実機の値がなく、仮定で決めたこと:

- 待ち方: 「1.6 マイクロ秒ごとの決まった時刻で終わる」と「前の読み書きから 1.6 マイクロ秒たつまで次を始められない」は、
  si.r では区別できない。前者にした (状態を持たずに済み、ステートの形が変わらない)。続けて読み書きするときはどちらも
  同じ時間で、違うのは間のあいた 1 回だけ (前者は平均 0.8 マイクロ秒待つ)
- 周期: 0.8 マイクロ秒の周期で、読み書きに 0.76 から 0.8 マイクロ秒かかる作りでも上の表は説明できる。その場合、続けて
  読み書きするときの時間は半分になる。cpupower.r のように I/O を続けて読む測定の実機の値があれば決められるが、見つかっていない
- 場所: 実機の値は RTC の 1 か所だけ。ほかの I/O は RTC と同じとした。スプライトも RTC と同じとする値は
  (68000 の機種では、スプライトのウェイトは RTC より長い。`setupBusWaits()`)、測っていないので既定では入れず、
  `bus_sync_sprite=on` で選ぶ。グラフィック VRAM とテキスト VRAM は 120ns のまま (68000 の機種では VRAM のウェイトは
  I/O より短い。X68030 での値は見つかっていない)
- 040turbo のキャッシュが無効のときの 175.78% (1 周 1.619 マイクロ秒) だけは、この作りでは説明できない。合わせていない
- X68030 の processor performance (実機 554.13% / 261.59%) は合わせていない。pix68k の 68030 はキャッシュの有効 / 無効で
  時間を変えず、どちらも 617% になる (68030 のサイクル数は概算)

ステートを読むときに CPU の時刻を小さい値に直す量 (`state.h` の `STATE_CPU020_CYCLES_MAX`、`STATE_CPU_TIME_PAST`) は、
240 サイクル (80 と 120 の最小公倍数) の倍数にしてある。直したあとも、1.6 マイクロ秒の区切りの位置が変わらない。

X68030 の si.r 4.14 の値 (ホスト版、`x68k_boot --cpu 68030`。060turbo.sys を組み込まない Human68k 3.02):

| si.r | 実機 (キャッシュ on) | 実機 (off) | pix68k (前) | pix68k (今) |
|---|---|---|---|---|
| processor performance | 554.13% | 261.59% | 617.80% | 617.30% |
| system performance | 177.82% | 177.81% | 658.61% | 177.82% |
| machine performance | 176.61% | 176.13% | 656.13% | 177.03% |

pix68k の値はキャッシュの設定によらず同じ。processor が 0.08% 下がったのは、割り込みの処理の中の I/O の読み書きに
時間がかかるようになったため。

確かめ方: `bus_wait_test` が、ROM なしで si.r の 2 つのループを動かす (system は 50 / 75MHz、キャッシュの有効 / 無効、
`speed060` = 50、最高速モードのどれでも 0.1 秒に 62499 か 62500 周。processor は 1 周 1 サイクルのまま。68030 でも
system は 62500 周で、processor は待ちを入れる前と同じ。$EB0000 への 32 ビットの書き込みは、スプライトをそろえたとき、
68030 でも 68060 でも 0.1 秒に 31250 周)。`x68k_boot` の
`--bus-sync ns`、`--bus-sync-areas n`、`--bus-wait N` で値を変えて試せる。場所の種類ごとの値は
`--bus-area 名前=pre,period,post` (例: `--bus-area pcg=750,0,0`。値は 0 から 1000000ns) で変えられる。

ゲームの速さへの影響を、CBX68 (自作の試験用のゲーム) の、柱が並ぶ区間の描画 1600 回にかかる垂直帰線の数で測った
(ホスト版、50MHz、キャッシュ有効、プログラムはローカルメモリ。30fps で間に合えば 3200):

| そろえる場所 | 垂直帰線の数 | 速さ (3200 / 数) |
|---|---|---|
| なし (前の動き、120ns だけ) | 3913 | 81.8% |
| I/O だけ (既定) | 4265 | 75.0% |
| I/O とスプライト (`bus_sync_sprite=on`。#218 までの既定) | 5997 | 53.4% |
| I/O とスプライトと VRAM | 6156 | 52.0% |

差の大半はスプライト ($EB0000-$EBFFFF) への書き込みで決まる。スプライトを RTC と同じとするのは仮定なので、
既定では入れていない。実機の 060turbo か X68030 でスプライトや VRAM の読み書きの時間が分かれば、その値を既定にする。

## 最高速モード

ホスト版の `--max-speed`、ベアメタル版の `max_speed=on` で、ホストが実時間に間に合う範囲で CPU を一番速く動かす
(`x68k/max_speed.h`)。68000 / 68030 / 68060 のどれでも使える。CPU のクロックを上げたのと同じで、
周辺機器と画面の時間は実時間のまま、フレームも飛ばさない。0.25 秒ごとに、ホストの使った時間が X68000 の時間の 85% に
なるよう速さを変える (100 が既定のクロック、上限は 3200)。`machine_bench --speed 200` のように速さを決めて測れる
(200 でクロックを 2 倍にしたのと同じ)。
060turbo では、速さは「選んだクロック (既定 50MHz、`clock=75` で 75MHz) の実機の 68060 の何 %」で数える
(100 で命令のサイクル数が MC68060UM の表どおり)。
下限は `speed060` の値で、上限は `--max-speed-limit N` / `max_speed_limit=N` で決められる (既定の 0 は上限なしで 3200 まで。
100 にすると実機の速さを超えない。ただし上限が `speed060` より小さいときは `speed060` のほうを使うので、`speed060` を
100 より大きくしていれば、その速さのままになる)。ログと終了時の表示は「max speed: N% of a real 68060 (50 MHz)」
(75MHz では「(75 MHz)」) になる。

- 68030 / 68060 は、命令にかかるサイクル数を減らす (`Cpu020::setSpeed`)。1 サイクルのコストは 1/12800 サイクルの単位の整数なので、
  実際の速さは指定より少しだけ (3200 でも 0.5% 未満) 大きくなることがある (前は 1/800 サイクルの単位で、68030 の 1000 を超えると 2〜7% 飛んだ。#131)。
  X68030 と 060turbo の本体のバスの時間 (`busWait060` と
  `busArea`。上の「X68030 と 060turbo の本体のバス」) は縮めない。I/O の読み書きは 1 回 1.6 マイクロ秒のままなので、
  それを多く使うプログラムは、最高速モードでも命令の速さほどは速くならない (下の 68000 とは扱いが違う)
- 68000 はコアを変えず、X68000 の時間の「速さ / 100」倍のサイクル数を CPU に走らせ、走ったサイクル数を X68000 の
  時間に直す (`Machine::runCpu000Scaled`)。命令のサイクル数は速さ 100 のときと同じ。速さ 100 のときは今までと同じ処理を通る。
  VRAM や I/O のウェイトと DRAM リフレッシュの遅れ ([build-and-test.md](build-and-test.md) のホスト版の入力の `--clock` の項) も CPU のサイクル数として足すので、速さと同じ割合で縮む。
  実機をクロックアップしたときは I/O がクロックほど速くならないが、最高速モードは CPU をできるだけ速く動かすためのものなので、
  I/O の時間を実時間のまま残すことはしていない (`src/x68k/machine.cpp` の `setupBusWaits()` の注釈)
- ベアメタル版は、そのときの速さを 2 秒ごとにログ (syslog と `/log`) に出す (`max speed: 850% of 10 MHz (85.00 MHz)`)。
  ホスト版は終わるときに出す

TOMY さんの CPUPOWER.R で、10MHz の 68000 (速さ 100 で CPU 102%) を速さ 200 にすると 204%、1000 にすると 1021% になる (バスのウェイトを入れる前に測った値)。
