# 拡張ボードと RS-232C

数値演算プロセッサボード、まーきゅりーゆにっと、ネットワークボード Neptune-X、RS-232C。

文中の #番号 は、開発用の非公開リポジトリの issue と PR の番号。

## 数値演算プロセッサボード、まーきゅりーゆにっと

どちらも拡張スロットに挿すボードで、おもに 68000 の機種で使う。既定ではつながない。`cpu=68030` / `68060` でもつなぐ (数値演算プロセッサボードは $E9E000 に CIR が見えるだけで、CPU の FPU とは別)。ホスト版は `--fpu-board` / `--mercury`
(`--no-fpu-board` / `--no-mercury` で設定ファイルの指定を打ち消す)、ベアメタル版とホスト版の設定ファイルは `fpu_board=on` / `mercury=on`。
数値演算プロセッサボードは 2 枚までつなげる。2 枚目は $E9E080-$E9E09F に CIR が見える。設定ファイルは `fpu_board=2`、ホスト版は `--fpu-board 2`
(`--fpu-board` だけなら今までどおり 1 枚)。設定メニューの FPU board は off、on、2 の順に切り替わる。

数値演算プロセッサボード (CZ-6BP1 相当、`src/x68k/fpu_board.cpp`) は MC68881 を 1 個載せたボード。68000 には
コプロセッサインターフェースがないので、Human68k のドライバ (システムディスクの `\SYS\FLOAT3.X`) が $E9E000-$E9E01F の
コプロセッサインターフェースレジスタ (CIR) を読み書きして使う。CIR の動きは MC68881/MC68882 User's Manual の 7 章に従い、
中の計算は X68030 の 68882 と同じもの (`src/m68k/fpu_core.cpp`) を使う。68882 との違いは、FSAVE のフレーム
(IDLE は 6 ロング、BUSY は 45 ロング) と、評価と転送のプリミティブがいつも CA = 1 なこと。
計算はコマンドやオペランドを受け取った時点ですぐ終わり、実機の計算の時間は待たせない。
2 枚目のボードは 1 枚目と同じ作りで、レジスタも手順も別々に持つ (片方の手順の途中で、もう片方を使ってもよい)。
$E9E000-$E9FFFF のうち、2 つの CIR の外 ($E9E020-$E9E07F、$E9E0A0 から上) と、つないでいないボードの CIR はバスエラーにする。
1 枚のときに $E9E020 から上をバスエラーにしていたのに合わせたもので、実機で確かめてはいない。
2 枚目の先頭が $E9E080 なのは、前からソースの注釈にあった XEiJ の説明書の記述による。2 枚目も 32 バイトの CIR を持ち、
1 枚目と同じに動くとしたのは推測。FLOAT3.X などのドライバが 2 枚目を使うかは確かめていない。

まーきゅりーゆにっと (`src/x68k/mercury.cpp`) は 16 ビットのステレオ PCM を出すボード。$ECC080 にデータを書き、
$ECC091 のコマンドで周波数 (44.1kHz / 48kHz / 32kHz と、その半分) とステレオ / モノラル、L / R の出力を選ぶ。
データは DMAC のチャネル 2 (外部要求) で送る。ボードの中のバッファに空きがあれば転送を要求し、選んだ周波数で取り出して
OPM と ADPCM の音に混ぜる。音の合成を別のコア (ベアメタル版のコア 3) で行うときも、書き込みを記録して同じ音を作る。
レジスタは公開されている互換ボードの説明 (下の参考) から作ったもので、バッファの大きさ (8 語) などは推測。
OPN (YMF288) と割り込みは作っていない。

確かめたこと:

- `boards_test`: CIR の手順 (レジスタどうし、メモリから / メモリへ、制御レジスタ、FMOVEM の静的 / 動的なリスト、
  条件と BSUN、演算の例外、FSAVE / FRESTORE の IDLE と BUSY、パック 10 進の動的な k ファクタ)、68000 の命令からの読み書き、
  2 枚目のボード (68000 と 68030 の命令から $E9E080 を読み書きして 1 枚目と別の値になること、CIR の外のバスエラー、ステートの保存と読み込み)、
  まーきゅりーゆにっとのレジスタと周波数、DMAC のチャネル 2 の転送の速さ、記録を当てた側の音が 1 つのコアのときと同じになること、
  DMAC のチャネル 2 の CSR の PCS に L / R のクロックが見えること
- `x68k_boot_float3` (`tests/x68k/boot_float3.sh`): システムディスクの CONFIG.SYS を `FLOAT3.X` に書き換えたイメージで起動し、
  ボードがあれば FLOAT3.X が組み込まれ、X-BASIC の `print sin(1.0),exp(1.0)` が FLOAT2.X (ソフトウェア) と同じ値になる。
  ボードがなければ FLOAT3.X は組み込まれない
- PCM8PP 0.83d (Tany さん) が常駐し (44.1kHz、ステレオ、16ch)、PCM8 のファンクションコール (trap #2) で鳴らした
  441Hz の矩形波 (16 ビット、44.1kHz、モノラル、1 秒) が WAV に出る。定位を左だけにすると右は 0 になる。68000 の 16MHz / 10MHz と
  X68030 で確かめた。MKMU.R (Mercury-Unit V4 用) のあとに常駐させても同じ。mercury.x では試していない
- 拡張スロットの EXPCL は DMAC のチャネル 2 の PCL につながっていて、CSR の bit0 (PCS) で読める。まーきゅりーゆにっとは
  ここにサンプリング周波数の L / R のクロックを出す (PCM8PP は常駐するときに PCS が 1 から 0 に変わるのを待つ)

参考にした資料: MC68881/MC68882 User's Manual (Motorola / Freescale) の 6 章と 7 章、Inside X68000 (桑野雅彦、ソフトバンク)
の数値演算プロセッサの章、XEiJ の説明書 (ボードのアドレス)、yunkya2 さんの wifipcm の README と pcm.c の説明
(GIMONS さんの PilederX をもとにした互換ボード)。レジスタの位置は、上に書いた PCM8PP と MKMU.R が実際に動くことで確かめた。

## ネットワークボード Neptune-X

Neptune-X (`src/x68k/neptune.cpp`) は、拡張スロットに ISA バスをつなぎ、NE2000 互換のイーサネットのコントローラ
(National Semiconductor DP8390 と 16KB のバッファメモリ) を載せたボード。既定ではつながない。設定ファイルは `neptune=on`、
ホスト版は `--neptune` (`--no-neptune` で設定ファイルの指定を打ち消す)。

- アドレスと割り込み: $ECE000-$ECE3FF (ISA のポート $200-$3FF を 2 バイトおきに置く)。NE2000 はポート $300 にあり、
  DP8390 のレジスタが偶数番地の $ECE200-$ECE21E、データポートが $ECE220 (16 ビット)、リセットポートが $ECE23E。
  割り込みは IRQ2 (レベル 2)、ベクタ $F9。外付け SCSI ボード (同じ IRQ2、ベクタ $F6) と同時に割り込みを要求したときは、外付け SCSI を先に応答させる
- MAC アドレス: 既定は `02:68:6b:00:00:01` (ローカル管理のアドレス)。`neptune_mac=` (ホスト版は `--neptune-mac`) で変える。
  ドライバは PROM (リモート DMA のアドレス $0000-$001F) から読む
- フレームの送受信先 (`neptune_link=`、ホスト版は `--neptune-link`):
  - `echo`: ネットワークにはつながず、相手の機械が 1 台だけあるものとして、ARP の問い合わせと ping に答える (試験用。ホスト版の既定)
  - `loopback`: 送ったフレームをそのまま返す (ホスト版だけ)
  - `pcap:IF` (ホスト版だけ): libpcap で、ホストのネットワークインタフェース IF とイーサネットのフレームを送受信する。BPF (`/dev/bpf*`) を読み書きする権限が要る
    (macOS なら Wireshark の ChmodBPF を入れるなど)。有線のインタフェースで使う。Wi-Fi は、ほかの MAC アドレスのフレームを
    アクセスポイントが通さないことが多い
  - `tap:NAME` (Linux のホスト版だけ): tap デバイスに出し入れする。あらかじめ作っておく
    (例: `sudo ip tuntap add tap0 mode tap user $USER && sudo ip link set tap0 up`。ホスト側でブリッジや NAT を組む)
  - `eth` (ベアメタル版の既定): Pi の有線の Ethernet (Raspberry Pi 3 Model B+ は LAN7800、Raspberry Pi 3 Model B は LAN9514、Raspberry Pi 4 / Raspberry Pi 400 は GENET、Raspberry Pi 5 は RP1 の MACB)。ホスト版で `eth` を指定すると、警告を出して `echo` にする (ベアメタル版と同じ設定ファイルを使えるように)。
    コア 0 が Circle のネットワークデバイスでフレームを出し入れし、コア 1 とはロックのないリングで受け渡す (`baremetal/net_bridge.h`)。
    X68000 の MAC アドレス宛てのフレームを受け取るため、デバイスをプロミスキャスにする。`neptune_mac=pi` なら Pi の MAC アドレスを
    X68000 に使い、USB のもの (LAN7800、LAN9514) はプロミスキャスにせず、マルチキャストをすべて通す設定にする。Wi-Fi は使えない (Circle の WLAN はファームウェアを要し、ほかの MAC アドレスのフレームも通らない)
- ベアメタル版で `neptune_link=eth` のときは、ネットワークの口 (`net=on`。[network-api.md](network-api.md) を参照) は動かさない (同じ Ethernet のデバイスを使うため)
- ステートにはボードのレジスタとバッファメモリを入れる (ステートのヘッダで拡張ボードの有無を表すビットのうち、bit2 を使う)

作り:

- DP8390 のレジスタ (ページ 0〜2)、リモート DMA (16 ビット / 8 ビット、DCR の BOS)、受信リング (PSTART / PSTOP / BNRY / CURR、
  各フレームの前に置く 4 バイトのヘッダ)、受信のフィルタ (自分の MAC アドレス、ブロードキャスト、マルチキャストのハッシュ、
  プロミスキャス、MON)、受信リングがあふれたときの OVW と、取り落としたフレームの数 (CNTR2)、ISR と IMR による割り込み、TCR のループバック
- 受け取ったフレームは 60 バイトに満たなければ 0 で埋め、FCS (CRC-32) を付けてリングに書く。受信の時間は数えない。
  送信は、10Mbps の線で送る時間 (プリアンブルとフレームの間の時間を含む。60 バイトのフレームで約 67us) が過ぎてから送り終える
  (CR の TXP はそれまで 1 のまま)。すぐに送り終えると、ether_ne.sys 0.03 が送り終えたことを取りこぼし、二度と送らなくなる。
  受け取ったフレームは `Machine` が各ラスタの始まりで 1 つずつ取り込む。受信リングに入らないフレームは、実機と同じく捨てて ISR の OVW を立てる。ヘッダのバイト数はフレームと FCS で、ヘッダの 4 バイトは含まない (NetBSD の dp8390.c がバイト数を計算し直す式と合う)
- 資料で決められなかったところ (奇数番地、データポートのバイトの並び、リセットの後のレジスタの値など) は `src/x68k/neptune.h` の先頭に書いた

確かめたこと:

- `neptune_test`: NetBSD/x68k の起動プログラム (`sys/arch/x68k/stand/boot/ne.c`、`dp8390.c`) と同じ手順で、リセット、PROM からの
  MAC アドレスの読み出し、初期化、送信、受信リングからの読み出し (リングの終わりをまたぐもの) を行う。フィルタ、あふれ、ループバック、
  8 ビットの転送、BOS、ステート、68000 の命令からの読み書きとレベル 2 の割り込み、`echo` との ARP と ping の問い合わせと答え
- `tools/qemu_human68k.sh` の `NEPTUNE=1`: QEMU の raspi3b に USB の Ethernet (`-device usb-net`) をつなぎ、X68000 の MAC アドレスから出した
  ARP の問い合わせに QEMU のゲートウェイ (10.0.2.2) が答え、その答えがコア 0 に届く
- Human68k のドライバ ether_ne.sys 0.03 (Shi-MAD さん) と etherL12.sys (+M01 +1 +L12) を組み込み、計測技研の TCPPACKA の
  inetd.x、ifconfig.x で en0 を設定し、ping.x で `echo` の相手に 10 回 ping して 10 回とも答えが届く (`x68k_boot --neptune`。
  68000 の 16MHz / 10MHz と X68030)。`echo` はどの IP アドレスの ARP にも答えるので、本物のネットワークにつないだことにはならない。
  ether_ne.sys 0.03 では netstat.x -i がバスエラーになる (ドライバが統計のファンクションを作っていない。etherL12.sys の
  VersionUp.doc に直したとある)。実機の Pi の Ethernet では、まだ動かしていない

参考にした資料: National Semiconductor DP8390D (NIC) のデータシート、NetBSD/x68k の `neptune.c` と起動プログラムの `ne.c`、`dp8390.c`
と `GENERIC` の設定 (アドレス、ポートの置き方、割り込みのベクタ 249)。どれもコードは使っていない。範囲 ($ECE000-$ECE3FF)、
割り込みのレベル (2)、PROM の中身は、ether_ne.sys と etherL12.sys が動く値にした。実機のボードでは確かめていない。

## RS-232C (SCC のチャネル A)

X68000 の RS-232C は SCC (Z8530、$E98005 がコマンド、$E98007 がデータ) のチャネル A につながっている (チャネル B はマウス)。
相手は TCP の接続にする。既定ではつながない (`rs232c=off`)。設定ファイルは `rs232c=`、ホスト版は `--rs232c` で指定する。

- `rs232c=tcp:PORT`: TCP の PORT で待ち受け、つないできた相手 1 つとバイトをそのままやり取りする。ホスト版は 127.0.0.1 で待ち受ける。
  ベアメタル版はネットワークの口 (`net=on`。[network-api.md](network-api.md) を参照) の IP アドレスで待ち受け、`net_allow=` があればそのアドレス
  からだけ受ける (`net_token=` は見ない。家の中のネットワークだけで使う)。80 番 (HTTP) は使えない。Neptune-X が Ethernet を使うとき
  (`neptune=on` で `neptune_link=eth`) はネットワークの口が動かないので、RS-232C の TCP も使えない
- `rs232c=tcp:ADDR:PORT` (ホスト版だけ): ADDR で待ち受ける (`0.0.0.0` ならすべてのインタフェース。ほかの機械から届く)
- telnet の取り決め (IAC) はしないので、`nc` か `socat` でつなぐ (例: `nc 127.0.0.1 2324`)。`telnet` でつなぐと、取り決めのバイトが X68000 に届く
- つないでいる間は、X68000 から見た DCD と CTS が 1 になる (切れると 0)。つないでいない間に X68000 が送ったバイトは捨てる
- X68000 が受け取るのも送るのも、SCC に設定したボーレートの速さ (1 文字の時間に 1 バイト)
- 相手が読まないとき、X68000 は止めずに送り続け、あふれた分を捨てる (CTS は下ろさない)。ためておくのは、送信のリングの 4KB と、
  その先の送信待ちまで。ホスト版は送り出し待ちの 1KB と OS の TCP の送信バッファ。ベアメタル版は Circle の送信待ちで、
  上限 `TCP_CONFIG_TX_THRESHOLD` (64KB) を見てから 1KB までまとめて積むので、上限を最大で 1023 バイト超える
- X68000 が RTS (WR5 bit1) を下ろしている間は、届いたバイトを X68000 に渡さない。ホスト版は受信のリング (4KB) が満ちたら
  ソケットから読まず、OS の TCP が相手を待たせる。ベアメタル版は Circle が TCP の受信の窓を狭めない (読まなくても相手は
  送り続ける) ので、受信のリングを 64KB にしてため、あふれた分は捨てる (切れたときに捨てた数をログに出す)。
  X68000 はボーレートの速さでしか読まないので、相手が一度に 64KB を超えて送ると、RTS が上がっていても超えた分を捨てる。
  ベアメタル版につなぐ相手は、ボーレートより速く送らないか、一度に送るのを 64KB までにする
- 相手が切れたら、すぐ DCD と CTS を 0 にする (受信を止めていてリングが満ちていても)。届いてリングに入っていたバイトは
  X68000 が読むまで残す (送ってすぐ閉じる相手の最後まで届く)。ホスト版で、リングが満ちていて OS の受信バッファに残っていた分は捨てる。
  次の相手がつながったときに、まだ読んでいない前の相手のバイトを捨てる (次の相手のバイトと混ぜない)
- ベアメタル版の Pi の UART (GPIO 14 / 15) や USB シリアルにはまだつながない (UART はログと `midi_out=uart` が使っている)

```sh
# ホスト版: 2324 番で待ち受け、Human68k の AUX とやり取りする
pix68k -r ~/x68k -0 HUMAN302.XDF --rs232c tcp:2324
nc 127.0.0.1 2324
# X68000 で: ECHO HELLO > AUX (nc に HELLO が出る)、COPY AUX CON (nc で打った文字が出る。Ctrl+Z で終わる)
```

作り (`src/x68k/scc.cpp`。詳しくは `src/x68k/scc.h` の先頭):

- ボーレート: SCC のクロック (PCLK) を 5MHz とし、WR12 / WR13 の時定数 TC と WR4 のクロックの倍率 M から 5000000 / (2 × M × (TC + 2)) bps。
  1 文字の時間はスタートビット、データビット (WR5 / WR3)、パリティ、ストップビット (WR4) から数える。WR14 は見ない。同期モードは作らない
- 送信: 送信バッファとシフトレジスタ。シフトレジスタが空いたらバッファのバイトを移し、そのときに送信バッファ空の割り込み要求を出す。
  送り終えたら相手に渡す。WR5 bit3 (送信の許可) と WR3 bit5 (Auto Enables のときの CTS) を見る
- 受信: 3 バイトの FIFO。あふれたときは最後のバイトを上書きし、そのバイトが FIFO の先頭に来たら RR1 のオーバーラン (特殊受信条件) にする
- 割り込み: 受信 (最初の 1 文字 / すべての文字 / 特殊受信条件だけ)、特殊受信条件 (ベクタの符号 111、チャネル B は 011)、送信、
  外部 / 状態 (WR15 で選んだ DCD / CTS が変わったら RR0 を止めて要求を出し、Reset Ext/Status Interrupts で開く)。
  最初の 1 文字のモードの要求は、その文字を読み出したときに下ろす。01 と 11 のモードでは、特殊受信条件のバイトを読んだら Error Reset まで次のバイトを見せない。
  10 (すべての文字) のモードの特殊受信条件の要求は、そのバイトを読んだら下ろす (RR1 のオーバーランのフラグは Error Reset まで残る)
- レジスタを選ぶポインタは 2 つのチャネルで 1 つ (実物と同じ)
- ブレーク、ゼロカウント、送信アンダーランの割り込み、パリティとフレーミングの誤り (TCP の相手からは来ない) は作らない
- チャネル B (マウス) の送信は、前と同じく書いたらすぐ送り終えたことにする。チャネル B の DCD / CTS は 0 のまま
- ステートには SCC の状態をすべて入れる (送っている途中のバイトと、送り終える時刻も。ステートの版 14)。TCP の接続はステートに入らない

確かめたこと:

- `scc_test`: レジスタのポインタ、ボーレートと 1 文字の時間、送信バッファとシフトレジスタ、受信の速さと RTS、オーバーランと特殊受信条件の
  ベクタ、FIFO を止める動き、外部 / 状態の割り込み、ステート (版 13 と 14)
- `x68k_test` の `RS-232C interrupt`: 68000 の命令で SCC を設定して 1 バイト送り、送ったバイトを返す相手から受け取って、レベル 5 の割り込み (ベクタ $5C) が入る
